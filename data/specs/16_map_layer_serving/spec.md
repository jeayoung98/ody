# 16 지도 레이어 서빙 — spec

상태 🔶(1·2레이어 완료) · Jira **S15P21A405-37**(원안) · **S15P21A405-210**(레이어 인덱스) · 결정 **D14** · 2026-09-11 갱신

## 목적
지도 화면이 파일이 아니라 **DB 질의**로 돌게 한다. 좌표는 이미 `music.location vector(16)` 에 662만 행 적재돼 있다(스펙 18). 이 스펙은 그 위에 **레이어 질의가 인덱스를 타게** 만드는 부분이다.

## D14 — 레이어는 트리 노드가 아니라 좌표 쌍이다 (2026-09-11 사용자 확인)

```text
1레이어 (pc1, pc2)   2레이어 (pc3, pc4)   3레이어 (pc5, pc6)  ...  8레이어 (pc15, pc16)
```

사용자가 한 곡을 고르면 **그 근처를 다음 레이어 평면으로** 보여주는 드릴다운이다. 필터가 누적된다.

| 레이어 | 필터 | 화면 |
|---|---|---|
| 1 | 없음(첫 화면) | (pc1,pc2) |
| 2 | (pc1,pc2) 근처 | (pc3,pc4) |
| 3 | (pc1,pc2) + (pc3,pc4) 근처 | (pc5,pc6) |
| 8 | 누적 전부 | (pc15,pc16) |

**원안(깊이 6 사분할 트리의 노드 집계 `map_layer`·`track_position`)은 쓰지 않는다.** 원문은 아래 절에 보존한다. 트리 자체는 아티팩트에 그대로 있고 스펙 20 S4 가 계속 배정한다.

## 왜 표현식 인덱스인가

`music.location` 은 `vector(16)` 하나다. HNSW 는 **16차원 전체 L2 거리**용이라 "1·2번째 성분만" 보는 사각 범위 질의에는 쓰이지 않는다. 실측 **95 ms 병렬 Seq Scan**.

`pc1..pc16` 을 `real` 컬럼으로 복제하면 424 MB 가 더 든다. 대신 표현식 GiST 를 쓴다. `vector → real[]` 캐스트와 `point()` 가 둘 다 `IMMUTABLE` 이라 가능하다(`pg_proc.provolatile = 'i'` 확인).

```sql
CREATE INDEX music_l1_gist ON music USING gist (point((location::real[])[1], (location::real[])[2]));
CREATE INDEX music_l2_gist ON music USING gist (point((location::real[])[3], (location::real[])[4]));
```

같은 인덱스가 **사각 범위**(`<@ box`)와 **평면 최근접**(`<-> point`, KNN GiST)을 함께 처리한다. 빌드 각 21초, 421 MB. **테이블·컬럼 추가 0.**

### 인덱스를 8쌍 다 만들 필요가 없다
드릴다운 필터 사슬에는 **항상 (pc1,pc2) 가 들어간다.** 그게 662만 → 241,605 로 줄이고, 이후 조건은 작아진 후보에 heap 필터로 붙는다.

⚠️ **사각 범위 조건에 GiST 를 둘 다 쓰면 오히려 느려진다.** 플래너가 `BitmapAnd` 로 묶어 큰 비트맵 두 개를 AND 하는데, 그 비용이 후보를 줄이는 이득보다 크다. **145 ms → 355 ms.** 두 번째 조건부터는 `BETWEEN` 으로 쓴다. `music_l2_gist` 는 평면 최근접 전용이다.

## 첫 화면은 미리 계산한다 — `map_sample`

첫 화면에 곡을 고르게 뿌리려면 격자 대표를 뽑아야 하는데, 전 영역 실시간 집계는 662만 행을 전부 읽어 **20,941 ms** 다.

첫 화면은 사용자 입력과 무관하게 늘 같다 → **미리 계산해 테이블로.** 제목·아티스트까지 넣어 `music` 조인도 없앴다.

⟲ **2026-09-18 D19 로 칸별 선정 규칙 개정 (Jira S15P21A405-466).**

| | 원안 (2026-09-11, D14) | 개정 (2026-09-18, D19) |
|---|---|---|
| 칸당 곡 수 | **1곡** | `k = min(round(cbrt(n)), 40)`. `n` = 그 칸의 **재생 가능한** 곡 수 |
| 칸 안 선택 | 중심에 가장 가까운 곡 | **`md5(id::text)` 무작위** |
| 후보 | 전체 곡 | **`NOT is_unplayable`** (판정 정본 이전, S15P21A405-454) |
| PK | `(layer, gx, gy)` | `(layer, gx, gy, music_id)` — 칸당 여러 행을 담으려면 필요 |
| 1레이어 규모 | 1,094행 (2026-09-11) | **850칸 → 약 7,272곡** (2026-09-18 실집계) |

**왜 바꿨나.** 중심 최근접이라 점의 **83.5%** 가 칸 중심 0.25칸 안에 몰려 **바둑판**이 보였다. 그리고 칸당 곡 수 편차가 다섯 자릿수인데(`cnt` 분위 1 / 6 / 66 / 1,201 / 86,651 / 최대 98,660) 칸당 1곡이 그걸 전부 지운다. FE 는 10,000점을 요청했는데 현행 응답은 745점이었다.

바꾼 뒤 **24.7%** 로 떨어졌다(2026-09-21 운영 실측).

> ⚠️ **기대치는 25% 다.** 검증 질의가 **사각형** 판정(`|x-중심| <= 0.5 AND |y-중심| <= 0.5`)이라, 칸 폭 2.0 에서 축당 1.0 → `0.5 × 0.5 = 0.25` 가 균등분포 기대치다.
> 초안은 이 기준을 **원형** 판정값(`π×0.5² / 2.0² = 19.6%`)으로 적어 두고 검사는 사각형으로 짰다. 잣대가 서로 달랐던 탓에 24.7% 라는 **거의 완벽한 결과가 실패처럼 보였다**. 기준을 사각형 기준으로 바로잡는다(S15P21A405-497).

격자 간격 2.0 과 레이어 = 좌표쌍 구조는 **그대로다**(D14 를 뒤집지 않는다). 밀도 **정비례** 샘플링은 칸의 63~69% 를 잃는 데 비해 담긴 곡은 0.85% 만 잃어 기각했다.

⚠️ `ingest/map_grid.py` 는 **옛 규칙(중심 최근접)의 numpy 거울**이라 이제 SQL 과 일치하지 않는다. 롤백 자산으로 보존하며, `tests/test_map_layer.py` 의 "옛 규칙" 절이 그것을 검증한다.

| 단계 | 시간 |
|---|---|
| 전역 격자 실시간 | 20,941 ms |
| 미리 계산 + 조인 | 322 ms |
| **미리 계산 + 조인 제거** | **0.4 ms** |

크기 **120 kB**. 깊은 레이어는 사용자 경로마다 영역이 달라 미리 계산할 수 없고, 이미 좁혀져 있어 실시간(82~145 ms)으로 충분하다.

### 대표를 누르면 그 칸이 다음 레이어의 범위다
칸 경계는 저장하지 않는다. `gx`·`gy` 로 계산된다.

```text
x ∈ [gx * 2.0, gx * 2.0 + 2.0)
y ∈ [gy * 2.0, gy * 2.0 + 2.0)
```

첫 화면 응답에 이 네 수를 실어 보내면 FE 가 그대로 다음 레이어 질의의 `box` 로 쓴다.

**칸마다 곡 수가 크게 다르다.** 중앙은 수십만, 가장자리는 한 곡이다. 대표만 주면 FE 가 점 크기도 못 정하고 `LIMIT 1000` 에 잘렸는지도 모른다. 그래서 `map_sample.cnt` 에 칸별 곡 수를 넣는다.

## 원안 (2026-09-11 D14 로 대체. 규칙 1 — 지우지 않고 남긴다)

아래는 깊이 6 사분할 트리의 **노드 집계**(`map_layer` 5,461행)와 `track_position` 을 적재하려던 원래 계획이다. 레이어가 좌표 쌍으로 정해지면서 쓰지 않게 됐다. 줌아웃 전체 밀도를 보여주기로 하면 다시 필요해진다.

### 목적
아티팩트의 트리와 좌표를 **서빙 테이블 형태**(`map_layer`, `track_position`)로 적재해, 탐색 BE 가 파일이 아니라 질의로 지도를 읽게 한다.

트리 탐색 읽기 API 는 Backend(Spring) 담당이다(D12). 이 스펙은 **적재까지**이고, BE 는 여기서 만든 `map_layer`·`track_position` 을 읽는다. 계산 경로가 하나뿐이라 두 경로 대조는 필요 없다.

### 범위 정정 (Jira 문구와 실제 아티팩트의 차이)
Jira 37 은 "depth별 PC 축 할당(설명력 순 2개씩)" 이라고 적혀 있다. 실제 v2.1-pca16 트리는 그렇지 않다:

| Jira 37 문구 | 실제 아티팩트 |
|---|---|
| depth 마다 전역 PC 축 2개를 할당 | **노드마다 local PCA-2** (`split_axes.npz` 의 노드별 `axes(2,16)`, `median(2)`, `mean(16)`) |
| 축이 depth 로 결정 | 축이 노드로 결정. 같은 depth 라도 노드마다 다르다 |

이 스펙은 **실제 아티팩트를 따른다**. 축 정보는 depth 가 아니라 노드 단위로 적재한다. 재학습은 하지 않는다(규칙 3).

### 산출물

### `map_layer` (5,461행 = tree.json 의 노드 수)
```
node_id          string   region_code. "root" 또는 root(.[0-3]){1,6}
depth            int      0..6
parent_id        string|null
track_count      int      excluded=false 이고 길이 규칙 통과한 곡 수
track_count_all  int      tree.json 원본 size (제외 반영 전)
has_children     bool
centroid_pc1     real     노드 곡 좌표 평균 (float32)
centroid_pc2     real
local_ev_2d      real     tree.json 의 local_explained_variance_2d
axis_label       string|null   스펙 14 산출물. 없으면 null
```

### `track_position` (카탈로그 곡 수)
```
mbid       string   소문자 UUID, UNIQUE
leaf_id    string   root(.[0-3]){6}
pc1..pc2   real     아티팩트 좌표 그대로
node_d1    string
node_d2    string
```

`pc3..pc16` 은 이 테이블에 넣지 않는다. 지도 표시는 2D 다. 16차원 좌표는 `music.location` 에 넣고 이웃 검색은 BE 가 pgvector 로 한다(스펙 17·18, D12).

### 규칙
- 좌표는 **아티팩트 값 그대로**. 재계산·재학습 금지(규칙 3, Jira 35 의 좌표 불변성 게이트).
- 제외 곡을 테이블에서 빼지 않는다. `track_position` 에는 전 곡이 들어가고, 제외 여부는 카탈로그 쪽 컬럼으로 판단한다(규칙 2).
- 번들 버전이 바뀌면 테이블 전체를 다시 만든다. 부분 갱신하지 않는다(좌표 정합성).

### 원안 수용 기준 (대체됨)
- AC1 `map_layer` 행 수 == `tree.json` 의 `n_nodes`(v2.1-pca16 기준 5,461), 리프 행 수 == `n_leaves`(4,096), depth 값이 0..6.
- AC2 `track_position` 행 수 == 카탈로그 행 수, `mbid` 중복 0, `leaf_id` 가 전부 `root(.[0-3]){6}` 형식.
- AC3 불변식: 모든 내부 노드에서 **자식 `track_count` 합 == 부모 `track_count`**, `track_count_all` 도 동일, `has_children == (자식 행 존재)`.
- AC4 **좌표 불변성** — `track_position.pc1/pc2` 가 아티팩트 `coords_v2.parquet` 의 값과 100% 일치(부동소수 비교가 아니라 bit 단위 동일, 둘 다 float32).
- AC5 **멱등** — 같은 번들로 두 번 적재하면 결과 테이블이 동일하다(행 수·값·정렬 무관 집합 비교).
