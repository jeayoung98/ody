# 40 비인기 티어 — spec

상태 ⛔ **보류 (2차)** · 결정 **D5**(2026-09-07) · 1차 배포 범위 밖

## 목적
"오래됐고 아무도 안 듣는 곡" 이 지도를 채워 탐색 품질을 떨어뜨리는 문제를, **제외가 아니라 서빙 티어**로 다룬다.

D5 가 정한 것: 1차에서는 제외하지 않는다. 2차에서 티어로 낮춘다. 제외가 아닌 이유는 규칙 2(삭제 아님, 표시)와 같다 — 지도 밀도를 바꾸는 결정이라 되돌리기 어렵다.

## 왜 지금 만들지 않는가 (D5 근거)
| 후보 지표 | 왜 못 쓰나 |
|---|---|
| YouTube 조회수 | Data API 하루 100곡 수준. 6.6M 곡에 불가능 |
| 스크래핑 | 약관 위반 |
| 이름 기반 매칭 | 오매칭이 라벨 오염(규칙 8) |

쓸 수 있는 것: MusicBrainz `recording_first_release_date`(발매연도, 덤프에 있음), MLHD+ 청취 합산(`work/mlhd_p2/`), 보조로 ListenBrainz/Last.fm. 전부 API 호출 없이 로컬 덤프로 계산 가능하다.

## 산출물 (초안)
카탈로그 컬럼 2개:
```
serving_tier    int      1 (기본) | 2 (비인기)
tier_reason     string   "old_unheard" | "low_listen" | null
```

## 규칙
- **제외가 아니다.** 티어 2 곡도 카탈로그에 남고, 트리에 남고, 노드 곡 수에 포함된다(규칙 2).
- 티어 2 는 기본 검색 결과에서 **후순위**일 뿐이고, `include_tier2=true` 로 전부 볼 수 있다.
- 티어 경계값은 측정 전에 게이트에 등록한다(규칙 1).
- 좌표·트리는 건드리지 않는다(규칙 3).

## 수용 기준 (2차 착수 시 확정)
- AC1 카탈로그 전 행에 `serving_tier` 가 있고 기본값 1, null 없음.
- AC2 티어 2 비율이 사전 등록 게이트 `gates/tier_gate_v1.json` 의 상한 이하. 상한을 넘으면 경계를 다시 등록하지 않고 판정을 보존한 뒤 새 id 로 재등록(규칙 1).
- AC3 티어 2 곡이 `/songs/{mbid}` 로 직접 조회하면 정상 응답한다(숨기는 것이 아니다).
- AC4 이웃 검색에서 티어 2 는 동률일 때 뒤로 간다. `include_tier2=true` 면 순서 보정 없음.
- AC5 티어 부여 전후로 브릿지 풀 Hit@10 이 유의하게 나빠지지 않는다(±5% 기준. 측정은 2차에 별도 스크립트로 한다 — 예전 서빙 코드는 D12 로 삭제됐다).
- AC6 `pytest tests/test_tier.py`.
