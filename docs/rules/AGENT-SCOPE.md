# 모호한 요청 — 추측으로 코드를 다 읽지 않는다

토큰을 아끼는 것이 우선이다. 요청이 어느 기능·화면·파일을 말하는지 분명하지 않으면
**저장소를 훑으며 추측하지 말고 먼저 묻는다.**

## 흐름

```text
요청 도착
→ 무엇을 가리키는지 확실한가?
   ├ 예 → 그 기능에 딱 필요한 파일만 읽고 분석 (관련 컴포넌트·상수·최근 커밋 정도)
   └ 아니오 → 코드를 열기 전에 한 줄로 되묻는다
        "어느 기능(화면·컴포넌트) 얘기인가요? 예: A / B / C"
        후보가 짚이면 후보를 같이 제시해 고르게 한다
```

## 지킬 것

- 전체 디렉터리 `ls`·`grep -r` 로 후보를 넓게 뒤지는 것은 **물어본 뒤에도 못 좁혔을 때**만 한다.
- 파일을 읽을 때는 필요한 구간만 읽는다(`sed -n`, `grep -n -A/-B`). 파일 전체 `cat` 은 작은 파일이거나 전체가 실제로 필요할 때만.
- 원인을 이미 짚었으면 거기서 멈추고 고친다. "혹시 다른 곳도" 를 위해 주변 코드를 더 읽지 않는다.
- 분석 결과를 말할 때도 읽은 파일 목록을 나열하지 않는다. 결론과 근거가 된 코드 한두 곳만 짚는다.

## 예

- "호버가 이상해" → 호버가 있는 화면이 여럿이면(지도 별·검색 결과·플레이어) 어디인지 묻는다.
  현재 브랜치·최근 커밋이 한 곳을 강하게 가리키면 그곳만 열어 확인하고 답한다.
- "이거 왜 안 열려" → "이거" 가 무엇인지 묻는다. 캔버스 클릭·카드 클릭·버튼 중 어느 것인지.
