<details><summary>2026-09-18 · d230453 · 곡 수 확장 실측 (S15P21A405-438)</summary>

### 왜 늘었나 — 배경 장식이 4.7배 됐다

`drawBackground` 가 `field()` 를 **네 번** 부른다 (S15P21A405-226·227, 9/12 커밋):

| 호출 | 개수 | 위치 |

측정이 이걸 확인해 준다 — 별 `drawImage` 호출 수가 정확히 맞아떨어진다:

```
N=754   별 5,924회 = 754(곡) + 5,170(장식)
N=3000  별 8,170회 = 3,000(곡) + 5,170(장식)
```

9/11 측정 당시엔 `field()` 가 한 번(1,100)이었고, 그래서 "별 2,100회 = 1,000 + 1,100" 이었다.
PERF-LOG 에 적혀 있던 *"별 하나를 두 번 그리는 구간이 있다"* 는 **오독이다** — 중복 그리기가 아니라
곡 별과 배경 별이 같은 48px 스프라이트를 써서 `SPRITE_KIND` 한 칸에 합산된 것이다.

### 곡 수를 올리면

| 화면 안 곡 | FPS | 그리기/프레임 | 예산% | 별 호출/프레임 |
|---|---|---|---|---|
| 754 | 59.7 | 7.98ms | 47.8% | 5,924 |
| **3,000** | **48.8** | 13.61ms | **81.5%** | 8,170 |
| **7,000** | **35.4** | **20.17ms** | **120.8%** | 12,170 |

**3,000 에서 이미 60fps 가 깨지고, 7,000 은 예산을 넘는다.** 7,000 에서는 프레임 간격 중앙값이
25.1ms 이고 33ms 넘는 프레임이 62개다 — 눈에 보이게 끊긴다.

별 호출 수가 세 측정 모두 **곡 + 5,170** 으로 정확히 맞는다:

```
754곡   → 5,924 = 754   + 5,170
3,000곡 → 8,170 = 3,000 + 5,170
7,000곡 → 12,170 = 7,000 + 5,170
```

### 장식을 빼면 7,000 이 들어온다 (산술 추정)

7,000 측정에서 draw call 하나당 20.105ms / 12,170 = **1.65 μs** 다.
장식 5,170 을 걷고 곡만 7,000 그리면:

```
7,000 × 1.65μs ≈ 11.6ms   → 예산 16.7ms 안
```

**이건 측정이 아니라 산술이다.** 장식을 실제로 덜어내고 다시 재야 확정된다.
다만 방향은 분명하다 — 지금 그리기의 대부분이 곡이 아니라 장식이고, 곡을 늘리려는 목적이
"빈 하늘을 채우는 것" 이라 **장식이 하던 일을 곡이 대신하면 된다.**


엔진 계산도 같이 무거워진다:

| | N=754 | N=7,752 | 배수 |
|---|---|---|---|
| `frame()` | 0.061ms | **0.633ms** | **10배** |

### 장식을 얼마나 덜어도 되나 — 눈으로 비교

`field()` 의 개수에 런타임 배율을 임시로 걸고(실험 후 되돌림) 같은 화면을 찍어 비교했다.

### ⚠️ 곡 수를 늘려도 "꽉 차 보이게" 되지 않는다

7,000곡을 주입해 보니 화면이 오히려 **더 어두웠다.** 알파 규칙 때문이다.

| 무엇 | 알파 | 크기 |
|---|---|---|
| 대표 곡 (`chosen`) | **0.42 ~ 1.0** | `STAR_SIZE.min ~ max` |
| 장식 별 | 최대 **0.25** | 1.3 ~ 5.5px |
| **비대표 곡** | 최대 **0.13** | 2.2 ~ 5.8px |

**진짜 곡이 가짜 장식보다 어둡다.** `draw-map.ts` 주석이 의도를 밝히고 있다 —
*"집을 수 없는 별이라 눌리는 별(0.42~1)과 확실히 갈라놓는다 … 최대 알파 0.13"* (S15P21A405-283).

그리고 `chosen` 은 **격자 한 칸당 1곡**이라 화면에 9~19개뿐이고 **곡 수와 무관하다**:

```
  754곡 → 밝은 별  9개
7,000곡 → 밝은 별 19개      곡이 9배인데 밝은 별은 2배
```

나머지 6,981곡은 알파 0.13 이하의 먼지로 그려진다. **비용은 다 내면서 안 보인다.**

**따라서 "곡 수를 늘려 별이 꽉 차 보이게" 는 성립하지 않는다.** 화면 밝기를 정하는 것은
곡 수가 아니라 `pickRepresentatives()` 의 격자 선별과 알파 상한이다. 곡 수 확장은 그 규칙을
손대기 전까지는 **비용만 늘리고 보이는 것은 그대로다.**

### 배칭은 막혀 있지 않다

`globalAlpha` 가 프레임당 5,984회라 배칭이 안 되는 것처럼 보이지만, 구조상 불가능한 게 아니다.

| 방법 | draw call | 대가 |
|---|---|---|
| **배경 별밭 오프스크린 굽기** | 5,170 → 약 4 | 개별 반짝임 사라짐 |
| 알파 8단계 양자화 후 묶어 그리기 | 상태 변경 5,984 → 8 | 반짝임이 뭉툭해짐 |
| 장식 50% | 5,924 → 3,339 | **없음** (위 비교) |

가장 먼 별밭은 카메라와 무관하게 시간으로만 흐르고, 나머지 세 겹도 **같은 배열을 오프셋만
바꿔 반복하는 타일**이다. 한 타일을 구워 `createPattern` 으로 깔면 draw call 이 상수가 된다.

### 그래서

**1. 곡 수 확장은 지금 규칙으로는 목적을 못 이룬다.** 늘어난 곡의 99% 가 알파 0.13 이하로
그려져 비용만 내고 안 보인다. "꽉 차 보이게" 하려면 `chosen` 선별과 알파 상한을 손대야 하는데,
그건 S15P21A405-283 에서 **일부러 갈라놓은 규칙**이라 디자인 담당과 합의가 먼저다.

**2. 화면을 안 바꾸고 지금 당장 할 수 있는 것 두 가지가 있다.**
- 장식 50% — draw call 44% 감소, 눈으로 차이 없음
- 배경 별밭 오프스크린 굽기 — 5,170 → 약 4회. 반짝임을 일부만 남기면 체감 차이도 거의 없다

**3. 미니맵은 병목이 아니다.** 7,000곡에서도 0.2ms 다. 이 방향은 닫는다.
