# 002. 지도 앨범 커버가 늦게 뜨던 문제

- 이슈: S15P21A405-528
- 커밋 / MR: MR !401
- 날짜: 2026-09-22

## 증상

지도에 앨범 커버가 사각형으로 뜨는데, 지도가 다 그려지고 **한참 뒤에야** 하나씩 채워졌다.
그 전까지는 절차적 커버(musicId 해시로 만든 그라데이션 그림)가 보이다가 갑자기 바뀐다.

## 측정 — 개선 전

Cover Art Archive 이미지 한 장 받는 데 걸리는 시간이다.

| 지표 | 값 |
| --- | --- |
| `front-250` 1장 | 16,414 B · **2.95 s** · 리다이렉트 2회 |
| `front-500` 1장 | 50,214 B · **2.58 s** · 리다이렉트 2회 |
| `front-1200` 1장 | 188,258 B · **3.43 s** · 리다이렉트 2회 |
| `front-250` 재요청 | **2.36 s** |

**측정 방법**: 실데이터 `albumMbid` 하나(`11876cc3-481b-4f57-bbb4-375b845cd339`)로 크기만 바꿔 가며 잰다.

```bash
M=11876cc3-481b-4f57-bbb4-375b845cd339
for s in 250 500 1200; do
  curl -s -o /dev/null -L -w "front-$s http=%{http_code} bytes=%{size_download} total=%{time_total}s redirects=%{num_redirects}\n" \
    "https://coverartarchive.org/release/$M/front-$s"
done
```

## 원인

둘이다.

**1. 저쪽이 느리다. 그리고 크기 문제가 아니다.** 바이트가 3배 차이나도(16KB ↔ 50KB) 시간은 거의
같다. 전부 **리다이렉트 2회**(`coverartarchive.org` → `archive.org` → 배포 노드)와 저쪽 응답
시간이다. 그래서 `front-250` 으로 낮추는 것은 답이 아니다 — 곡 상세 배경(512px)이 같은 원본을
재사용하므로(`cover-art.ts` 의 `source` 캐시) 작게 받으면 배경만 뭉개고 시간은 그대로다.

**2. 받기 시작하는 시점이 늦었다.** `albumCover()` 는 `coverFor()` 안에서만 불렸고
(`sprites.ts`), 그건 **그 곡이 커버로 뽑혀 실제로 그려질 때** 처음 실행된다. 즉 지도가 자리를
잡고 → 커버를 뽑고 → 그때 3초를 기다리는 순서였다.

덤으로 커버 자리를 뽑는 순서도 문제였다. `map-view.tsx` 가 `weight` 내림차순 하나로 40곡을
골랐는데 실데이터는 `weight` 가 전부 0 이라 정렬이 아무 일도 안 했고, 그래서 **`albumMbid` 가
없어 절차적 그림밖에 못 그리는 곡**이 열몇 개뿐인 커버 자리를 차지했다.

## 조치

**미리 받는다.** 상주 집합이 도착해 후보 40곡이 정해지는 순간, 앞쪽 20곡(`COVER_COUNT.near`)의
커버를 바로 `albumCover()` 로 데운다 (`map-view.tsx`). 그리려고 볼 때는 이미 와 있다.
앞쪽만 데우는 이유는 화면에 동시에 뜨는 커버가 스무 개 남짓이고, 마흔 장을 한꺼번에 부르면
같은 호스트에 줄이 서서 앞엣것까지 늦어지기 때문이다.

**순서를 정한다.** `byCoverPriority` (`cover-spread.ts`) — **앨범 ID 있음 > 재생수 > 받은 순서**.
대표곡 40곡을 고를 때와 칸마다 하나씩 고를 때(`draw-map.ts`) 모두 같은 비교자를 쓴다.

버린 대안: `front-250` 으로 낮추기(위 측정대로 시간이 거의 같다), CAA 리다이렉트 건너뛰기
(최종 주소에 이미지 id 가 들어가는데 그건 CAA JSON 을 한 번 더 받아야 알 수 있다 — 왕복이 늘어난다).

## 측정 — 개선 후

| 지표 | 개선 전 | 개선 후 | 변화 |
| --- | --- | --- | --- |
| 커버 1장 받는 시간 | 2.4 ~ 3.4 s | 2.4 ~ 3.4 s | **그대로** (저쪽 사정이라 안 건드렸다) |
| 받기 시작하는 시점 | 커버로 뽑혀 그려질 때 | 상주 집합 도착 직후 | **미측정** |
| 화면에 커버가 차는 시점 | 미측정 | 미측정 | **미측정** |

**정직하게 적는다: 개선 후를 못 쟀다.** 지도 화면은 로그인이 필요한데 이 작업을 한 세션에서는
로그인된 브라우저를 띄울 수 없었다. 위 "받는 시간" 만 개선 전과 같은 `curl` 로 다시 확인했고
그건 바뀌지 않았다 — 바꾼 것은 **언제 시작하느냐**지 **얼마나 걸리느냐**가 아니다.

재려면: 로그인 후 지도에서 Network 탭을 열고 `coverartarchive.org` 요청의 시작 시각을
`/bff/map/songs` 응답 시각과 비교한다. 개선 전에는 그 차이가 지도 렌더 뒤였고, 개선 후에는
응답 직후여야 한다.

## 남은 것

- **개선 후 수치가 비어 있다.** 위 방법으로 한 번 재서 이 표를 채워야 기록이 완성된다.
- 커버가 아예 없는 릴리스가 있다 (실측 6개 중 1개는 `front-500` 이 404). 그 곡은 절차적 커버로
  떨어지는데, 404 도 2~3초를 기다린 뒤에 온다 — 실패 판정이 늦다.
- 근본 해결은 **백엔드가 커버 URL 을 미리 채워 두는 것**이다. 그러면 리다이렉트 두 번이 사라진다.
  BACKEND-NOTES 에 올려 둔 `music.cover_url` 제안이 그것이다.
