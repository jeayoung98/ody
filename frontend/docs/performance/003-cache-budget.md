# 003. 상한 없는 캐시에 상한을 걸다

- 이슈: S15P21A405-586
- 커밋 / MR: (작성 시점 미merge)
- 날짜: 2026-09-22

## 증상

**사용자 신고에서 시작한 것이 아니다.** 캐시를 점검하다 나온 것이고, 화면에서 무엇이
느려졌는지는 재지 못했다 — 아래 수치는 전부 **코드에서 읽은 것과 계산한 천장**이다.

오래 탐색할수록 브라우저가 들고 있는 것이 계속 는다. 버리는 길이 없는 캐시가 셋이었다.

## 측정 — 개선 전

**잰 것이 아니라 코드에서 읽고 계산한 값이다.** 항목 하나의 크기는 정확하고(캔버스는 픽셀당
4바이트, JSON 은 직렬화해서 잼), **몇 개까지 쌓이는지는 실제 세션에서 확인하지 못했다.**

| 캐시 | 항목 하나 | 상한 | 버리는 규칙 |
| --- | --- | --- | --- |
| `cover-art.ts` `ready` (구운 커버) | 104px 43KB · 512px 1MB | 300**개** | 넘치면 `clear()` 전부 |
| `cover-art.ts` `source` (디코딩된 500px 원본) | 약 1MB | **없음** | `ready` 가 비워질 때 같이 |
| `sprites.ts` `coverCache` (절차적 커버) | 104px 43KB · 512px 1MB | 500**개** | 넘치면 `clear()` 전부 |
| `use-map-songs-query` (지도 상주 집합) | 1000점 JSON **296KB** | **없음** (`gcTime: Infinity`) | 없음 |

**측정 방법**

캔버스 크기는 정의대로 계산했다 (`width * height * 4`). 상주 집합은 목 데이터를 직렬화해서 쟀다.

```bash
node --require ./tests/register.cjs -e "
const { allSongs } = require('./src/mocks/songs.ts');
console.log(JSON.stringify(allSongs().slice(0, 1000)).length);
"   # → 303149 (296KB)
```

배포 백엔드로는 못 쟀다 — `/bff/map/songs` 가 401 이고 쓸 수 있는 토큰이 없다. 실데이터는
제목·아티스트가 목보다 길고 `youtubeUrl` 이 검색 URL 이라 **이 값은 하한으로 본다.**

## 원인

개수로 재는 상한이 **무엇을 막는지 말해 주지 못했다.** 커버는 쓰는 자리마다 크기가 다르다
(`sprites.ts:201` 의 지도용 104px, `song-cover-backdrop.tsx:16` 의 512px). 같은 300장이
13MB 이기도 하고 300MB 이기도 하다.

`source`(`cover-art.ts:32`)에는 상한이 아예 없었다. 하는 일은 **"방금 본 곡을 다른 크기로
다시 굽기"** 하나인데(104px 로 보던 곡의 상세를 열면 512px 이 필요하다), 받은 곡을 전부
들고 있다가 `ready.size > 300` 일 때에야 같이 비웠다.

지도 상주 집합(`use-map-songs-query.ts`)은 `staleTime`·`gcTime` 이 둘 다 `Infinity` 다.
그럴 이유가 있었다 — 떠오를 때 재요청이 없어야 겹 전환 연출이 끊기지 않는다(`map-view.tsx`
는 집합이 없으면 별밭 자리표시자를 덮는다). 그런데 캐시 키가 **누적 범위**라 새 경로로 좁혀
들어갈 때마다 키가 하나 늘고, 버리는 길은 어디에도 없었다.

## 조치

**개수 대신 예산으로 재고, 통째로 비우는 대신 오래된 것부터 하나씩 버린다.**

- `lib/budget-cache.ts` — 바이트 예산으로 재는 LRU. `get` 은 순서를 최신으로 올리고 `has` 는
  건드리지 않는다(지도가 커버 후보를 훑는 것은 쓴 것이 아니다). 예산보다 큰 한 장이 들어와도
  그것만은 남긴다.
- 구운 커버·절차적 커버를 각각 **12MB** 예산으로 바꿨다. 화면이 실제로 쓰는 양은 지도 커버
  스무 장(104px, 0.9MB) + 상세 배경 한 장(1MB) 이라 여유가 크다.
- 디코딩된 원본은 **8장**으로 따로 묶었다. 밀려나도 그림을 잃지 않는다 — 구운 캔버스는
  `ready` 에 있고, 다른 크기가 필요하면 브라우저 캐시에서 다시 받는다.
- `lib/map-songs-cache.ts` — 상주 집합에 **16개** 상한(LRU). **보는 컴포넌트가 있는 집합은
  후보에서 뺀다.** 파고드는 길이 8겹이라 왕복 한 벌이 들어가고도 남는다.

`clear()` 를 버린 이유: 통째로 비우면 **지금 화면에 서 있는 커버까지 날아가** 가장 바쁜
순간에 재다운로드·재굽기가 한꺼번에 터진다.

곁들여 고친 것 둘 (같은 이슈):

- `use-video-id-query` 의 `gcTime` 이 기본 5분이라 `staleTime: 30분` 이 사실상 안 살았다.
  둘을 같은 값으로 묶었다 — **요청이 주는 쪽**이다. 이 조회는 DB 에 없으면 백엔드가 외부
  API 를 부른다.
- `query-persist` 가 `user.profile` 을 **남의 것까지** localStorage 에 24시간 남겼다. 그 안에
  `isOnline`·`nowPlaying` 이 있어 다시 열면 어제 값이 먼저 보인다. 내 것만 저장하도록 좁혔다.

## 측정 — 개선 후

| 지표 | 개선 전 | 개선 후 | 변화 |
| --- | --- | --- | --- |
| 구운 커버 캐시 천장 | 300개 × 43KB~1MB = **13~300MB** | **12MB** | 상한이 크기에 걸린다 |
| 디코딩 원본 천장 | **상한 없음** | 8장 (약 8MB) | 상한이 생겼다 |
| 절차적 커버 천장 | 500개 × 43KB~1MB = **21~500MB** | **12MB** | 상한이 크기에 걸린다 |
| 지도 상주 집합 천장 | **상한 없음** | 16개 (하한 296KB × 16 ≈ 4.7MB) | 상한이 생겼다 |
| 브라우저에서 잰 힙 | **미측정** | **미측정** | — |

**천장은 계산값이고, 실제 힙은 개선 전·후 모두 못 쟀다.** 로그인 게이트를 넘을 계정이 없어
배포·로컬 어느 쪽에서도 세션을 돌려 보지 못했다. 규칙이 지켜지는지는 단위 테스트로만 묶었다
(`tests/budget-cache.test.cjs`, `tests/map-songs-cache.test.cjs`).

## 남은 것

- **실측이 비어 있다.** 계정이 생기면 Chrome DevTools Memory 에서 5분 탐색 뒤 힙을 개선 전·후로
  재고 이 표를 채운다. 지금 값은 전부 천장이지 실제 사용량이 아니다.
- 예산 12MB·원본 8장·상주 집합 16개는 **화면이 쓰는 양의 몇 배**로 잡은 값이다. 실측이 생기면
  조정한다.
- 상주 집합을 내보낸 뒤 그 겹으로 떠오르면 다시 받는다. 16개 안쪽에서는 안 일어나야 정상이고,
  일어난다면 상한이 낮다는 뜻이다.
