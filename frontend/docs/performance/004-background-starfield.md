# 004. 배경 별밭이 지도 그리기의 88% 를 먹던 문제

- 이슈: S15P21A405-499
- 커밋 / MR: (작성 시점 미merge)
- 날짜: 2026-09-25

## 증상

`map_sample` 이 밀도 가중으로 바뀌면서 상주 곡이 **850 → 7,204 (8.5배)** 가 됐고 지도 탐색
프레임이 떨어졌다. 곡이 늘었으니 곡 때문이라고 보는 것이 자연스러웠다.

## 측정 — 개선 전

Chrome 트레이스 (로컬 dev, CPU 4x). **곡 때문이 아니었다.**

| 구간 | inclusive | drawMap 대비 |
| --- | --- | --- |
| `drawMap` | 12,784 ms | 100% |
| └ `drawBackground` | **11,232 ms** | **88%** |
| └ `drawStars` (상주 7,204곡) | 1,082 ms | 8.5% |
| └ `drawCovers` | 251 ms | 2.0% |
| └ `drawNebula` | 116 ms | 0.9% |

`drawStars` 는 draw 가 **7,204번으로 더 많은데 비용은 1/10** 이다. `kmax` 를 낮춰 곡을 줄여도
프레임은 거의 안 살아난다.

배경은 `field()` 를 프레임당 4번 부르고 각 호출이 배열 전체를 돈다.

| 겹 | draw/frame |
| --- | --- |
| 가장 먼 별밭 (카메라 무관) | 1,100 |
| 시차 중간 | 1,100 |
| 시차 원경 | 770 |
| 가까운 별먼지 | 2,200 |
| **합** | **5,170** |

**트레이스를 잘못 읽어 한 번 헛짚었다.** pid/tid 를 합쳐서 보면 노드 ID 가 충돌한다 —
`MapAxisLabels` 가 19.7초로 1위처럼 보였는데 실제로는 3.5ms 였고, 19.7초는 다른 스레드의 idle
이었다. 스레드별로 나눠 읽어야 한다.

## 원인 — 처음 세운 가설은 **틀렸다**

이슈는 원인을 **draw 한 번의 비용**으로 봤고 두 가지를 제안했다.

- **A.** 스프라이트를 필요한 크기로 미리 구워 스케일링 없이 1:1 로 찍는다 (48px → 1~8px 축소 제거)
- **B.** 반짝임 알파를 8단계로 뭉쳐 같은 단계끼리 모아 그린다 (`globalAlpha` 대입 5,170 → 8회)

**둘 다 구현해서 재 봤더니 느려졌다.**

| | ms/frame |
| --- | --- |
| 원본 | 6.43 |
| A (크기 양자화) | 7.13 |
| B (알파 8단계) | 7.05 |
| A+B | 7.40 |

- **A 가 느려진 이유**: 스프라이트가 10장(색깔별)에서 140장(색 × 크기)으로 늘었다. 별은 색과
  크기가 뒤섞여 있어 거의 매 draw 마다 텍스처가 바뀐다 — 배칭이 깨진 비용이 축소를 없앤 이득보다 컸다.
- **B 가 느려진 이유**: `globalAlpha` 는 GPU 캔버스에서 사실상 uniform 대입이라 싸다. 그걸 줄이려고
  배열에 담아 두 번 도는 비용이 더 컸다.

즉 비싼 것은 **draw 한 번**이 아니라 **draw 횟수**였다. 이슈가 "모자라면 추가 검토" 로 밀어 둔
C(오프스크린 통합)가 사실은 정답이었다.

## 조치

**시차 중간·원경 두 겹을 화면 한 장에 구워 두고 감아 붙인다** (`farFieldTile`).

- 타일 한 변이 별밭의 한 주기(`W+64` × `H+64`)라 어긋난 만큼 밀어 2×2 로 깔면 이음매가 없다.
  **시차는 그대로 살아 있다** — 제약 2를 지킨다
- 별 수는 하나도 줄이지 않았다 — 제약 1·3을 지킨다
- **밝기(`aK`)는 굽지 않는다.** 겹 깊이에 따라 `dim` 이 계속 변하는데 그때마다 다시 구우면 아무것도
  못 아낀다. 붙일 때 `globalAlpha` 로 한 번 곱한다. `lighter` 는 더하기라 전체에 한 번 곱하는 것과
  별마다 곱하는 것이 같다
- 크기 밑값(`d0`)을 별 생성 시 한 번만 잰다. 프레임당 `Math.pow` 3,300회가 사라진다

**타일은 CSS 픽셀로 굽는다.** dpr 2 로 구우면 1600×900 에서 두 장이 **49MB** 다(실측). CSS 픽셀이면
**12.2MB** 이고 대신 빨라지는 폭이 1.67배에서 1.54배로 준다. 이 두 겹이 화면에서 가장 어두운 겹이라
살짝 뭉개지는 쪽을 골랐다 — S15P21A405-586 에서 커버 캐시를 12MB 로 묶은 것과 같은 저울이다.

**버린 것: 이 두 겹의 반짝임.** 별마다 다른 위상으로 깜빡이던 것이 평균 밝기(0.775)로 굳는다.
제약 4를 부분적으로 어기는 대신, 가장 먼 별밭과 가까운 별먼지는 그대로 둬서 **화면의 반짝임 자체는
남는다.** 굳은 두 겹은 `farFieldAlpha` 가 곱해져 원래도 어두운 쪽이다.

## 측정 — 개선 후

**개선 전 트레이스와 같은 방법이 아니다.** 지도를 띄우려면 로그인이 필요한데 쓸 수 있는 계정이
없어 Chrome 트레이스를 다시 뜨지 못했다. 대신 `field()` 안쪽 루프를 같은 별 데이터(같은 시드)·
같은 캔버스 설정으로 재현해 브라우저에서 쟀다. **"drawMap 대비 %" 와는 직접 비교할 수 없다.**

측정 조건: 1600×900, dpr 2, `lighter`, 200프레임 평균 × 3회 반복의 중앙값.

| 지표 | 개선 전 | 개선 후 | 변화 |
| --- | --- | --- | --- |
| 배경 그리기 | 6.94 ms/frame | **4.52 ms/frame** | **1.54배** |
| 16.7ms 예산 대비 | 42% | **27%** | −15%p |
| `drawImage` 호출 | 5,170 | **3,308** | −36% |
| 타일 메모리 | 0 | **12.2 MB** | +12.2MB |

## 남은 것

- **이슈의 완료 조건을 못 채웠다.** AC 는 "`drawBackground` 가 `drawMap` 대비 40% 이하" 인데,
  같은 방법으로 재지 못했으므로 **충족 여부를 말할 수 없다.** 산술로만 보면 배경이 1.54배 빨라져도
  88% → 약 83% 라 40% 에는 한참 못 미친다. 거기까지 가려면 남은 두 겹(1,100 + 2,200 draw)도
  타일로 굳혀야 하고, 그러면 **화면에서 반짝임이 사라진다** — 제약 4를 통째로 버리는 선택이라
  기획 확인 없이 할 일이 아니다.
- **체감이 얼마나 달라지는지는 별개다.** 이슈가 적어 둔 대로 배포본 트레이스에서 지도 그리기는
  애니메이션 프레임의 **4%** 였고 나머지를 다른 콜백이 먹고 있었다. 로컬 dev·CPU 4x 에서 88% 인
  것과 배포본에서 4% 인 것은 다른 이야기다. **배포본에서 먼저 재는 편이 안전하다.**
- 실제 앱에서 눈으로 확인하지 못했다. 이음매·시차·반짝임이 의도대로인지는 로그인해서 봐야 한다.
