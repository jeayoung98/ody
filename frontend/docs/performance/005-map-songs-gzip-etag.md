# 005. 지도 데이터를 압축 없이 매번 다시 받던 문제

- 이슈: S15P21A405-680
- 커밋 / MR: `83ca1679` (gzip) · `ca34933d` (ETag 재검증) · `5abe6b6f` (주석 수치) · `frontend/dev` 대상 680 MR
  - `8b0cbc94` (브라우저 저장본을 먼저 그림) 는 `ca34933d` 에서 걷어냈다 — 아래 "조치"
- 날짜: 2026-09-26

## 증상

폰에서 지도가 늦게 뜬다는 제보. 배포본(`next-26`)을 로그인한 채 망·CPU 를 고정해 재 보니 폰 LTE 첫 방문 3.38초의 55%,
재방문 2.60초의 65% 가 지도 1겹 데이터(5,745곡)를 받는 시간이었다. **재방문에도 1,576KB 를 압축 없이 전부 다시 받았다.**

| 지표 | 값 |

**측정 방법**: 배포와 같은 방식(`output: "standalone"`)으로 빌드해 로컬에서 `node .next/standalone/server.js` 로 띄우고,
BFF 는 배포 백엔드를 그대로 부르게 했다(`.env.local`). **개선 전 빌드는 `route.ts` 만 `c4ed31b9` 것으로 되돌려 만들었다** —
680 에서 실행 동작이 바뀐 파일은 그것 하나다(나머지는 거기서 새로 부르는 모듈과 상수). 전·후를 같은 PC·같은 크롬·같은 조건으로 쟀다.

- 스크립트: 438 브랜치의 `scripts/login-bench.mjs` 에 세 가지를 더해 썼다
  - `ORIGIN` 환경변수로 대상 주소를 바꾼다 (`ORIGIN=http://localhost:3000`)
  - 회차마다 `visibilitychange` 를 기록한다 — 첫 곡 전에 "hidden" 이 찍힌 회차는 버린다
  - `wifi` 조건을 더했다: CPU×4 · 50Mbps / 왕복 20ms. 로컬 직결은 망이 무한히 빨라 전송 이득이 0 으로 잡히기 때문이다
- 조건: 폰 = 390x844 DPR3 · 모바일 UA · CPU×4 에 망 LTE 10Mbps/60ms · 약한 신호 1.6Mbps/150ms · 와이파이 50Mbps/20ms · 감속 없음(로컬 직결).
  데스크톱 = 1600x900 DPR2 · 감속 없음

  `--disable-renderer-backgrounding` `--disable-background-timer-throttling` `--disable-background-networking`
  `--disable-component-update`** 를 넣었다 (아래 "버린 측정")


### 버린 측정

- **플래그 없이 잰 첫 묶음**: 폰 LTE 처음 5회 중 3회가 12.8초 · 67.5초 · 끝내 안 뜸. 데이터는 3.6~4.3초에 도착했는데 첫 곡이 안
  그려졌다. 측정용 크롬 창이 다른 창에 가려져 rAF 가 멈춘 것으로 본다(추정 — 그 묶음엔 화면 상태 기록이 없었다). 플래그와
  화면 상태 기록을 넣은 뒤로는 첫 곡 전에 "hidden" 이 찍힌 2회만 뺐다.
- **묶음 사이 흔들림**: 같은 코드끼리도 첫 방문이 최대 217ms 다르다(폰 로컬 직결 1,793 vs 2,010ms). 대부분 지도를 요청하기 전
  (앱 부팅) 구간에서 생긴다 — 680 이 손대지 않는 구간이다. 그래서 아래 표에 "지도 요청을 보낸 뒤만" 비교도 같이 적는다.

## 원인

- `bff/map/songs` 가 1겹 JSON 을 압축 없이 보냈다. Next 는 라우트 핸들러 응답을 압축하지 않는다(정적 청크는 압축한다 — 배포본에
  `Accept-Encoding: deflate` 로 요청하면 청크·페이지는 deflate 로 오고, 1겹은 압축 없이 왔다).
- 캐시를 검증할 헤더(`ETag`·`Last-Modified`)가 없어 브라우저가 재방문에도 전부 다시 받았다.

## 조치

- **gzip 수준 3** (`src/lib/gzip-json.ts`, `MAP_SONGS_GZIP_LEVEL`). 실제 1겹으로 재니 수준 3 은 561KB · 20ms, 수준 6 은 535KB · 47ms
  (개발 PC). 26KB 를 더 보내고 서버 CPU 를 절반 넘게 아낀다. 서버 코드가 브라우저 번들로 새지 않게 `api-response.ts` 와 떼어 뒀다.
- **ETag 재검증** (`src/lib/content-tag.ts`). 목록 내용으로 태그를 만들어 `ETag: W/"…"` + `Cache-Control: private, no-cache` 로
  보낸다. 브라우저는 방문할 때마다 `If-None-Match` 로 묻고, 같으면 서버가 본문 없이 304 로 답한다. 백엔드는 매번 부른다 —
  호출자 토큰 검사와 바뀐 목록 반영이 그대로다. 백엔드 1겹 조회에 `ORDER BY` 가 없어 태그는 musicId 로 정렬한 뒤 만든다.
- **버린 대안**
  - 브라우저 IndexedDB 에 저장해 두고 재방문에 먼저 그림(`8b0cbc94`): 재방문이 가장 빠르지만 목록이 바뀐 뒤 첫 방문 한 번은
    **옛 목록이 보인다.** 목록은 항상 최신이어야 해서 걷어냈다. 저장본을 갈아끼우려던 "로드 약 10초 뒤 새로 받기" 도 같이 없앴다.
  - BFF 메모리 캐시: 백엔드를 안 불러 빠르지만 호출자 토큰 검사를 건너뛰고 백엔드 변경을 놓칠 수 있어 하지 않았다.

  (`max-age=0`)에 처음 보는 주소로 물어도 304 가 온다 — nginx 가 헤더를 지웠다면 200 이 와야 한다.

## 남은 것

- **배포본에서 같은 방법으로 다시 잰다.** 로컬 개선 전 값이 배포본 기준선과 2~5% 안이라 크게 다르지 않을 것으로 본다(추정).
- 재방문도 백엔드는 매번 부른다. 폰 LTE 재방문에서 "바뀌었나" 확인 왕복(요청 → 304 도착 약 0.3초)은 남는다.
- **약한 신호 첫 방문은 여전히 13~15초다.** 첫 곡 전에 받는 2.2MB 중 유튜브 플레이어가 755~812KB 로 가장 크다. LTE·빠른 망에서는
  유튜브가 첫 곡 전에 60KB 이하만 받았지만 약한 신호에서는 지도와 망을 나눠 쓴다 — 다음 후보.
- 백엔드가 실패했다 살아나면 첫 방문은 전부 다시 받는다(압축본 561KB).
- 아이폰 사파리 실기기는 확인하지 못했다. 크롬 계열로만 쟀다.
