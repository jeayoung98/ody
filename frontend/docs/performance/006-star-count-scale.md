# 006. 곡 수를 늘리자 그리기가 프레임 예산을 넘던 문제

- 이슈: S15P21A405-438 (측정·분석). 배경을 줄인 조치는 S15P21A405-499 — [004](004-background-starfield.md)
- 커밋 / MR: 측정·분석 `79a17db3` · `9dec16a2` · `276d9968` · 배포본 전후 `16a310f7` · `9b2422fb` · MR !311
- 날짜: 2026-09-18 (측정·분석) · 2026-09-25~26 (배포본 전후)

## 증상

지도 첫 화면(1겹)이 비어 보였다. 화면이 차 보이게 하고 더 많은 곡을 보여 주려고 1겹 곡 수를 수천 곡으로 늘리려 했다.
늘리기 전에 그리기가 버티는지부터 쟀다.

## 측정 — 개선 전

### 곡 수를 올리면 (2026-09-18, 개발 서버, DPR 2)

| 화면 안 곡 | FPS | 그리기/프레임 | 예산(16.7ms) 대비 | 별 `drawImage`/프레임 |
| --- | --- | --- | --- | --- |
| 754 | 59.7 | 7.98ms | 47.8% | 5,924 |
| 3,000 | 48.8 | 13.61ms | 81.5% | 8,170 |
| 7,000 | **35.4** | **20.17ms** | **120.8%** | 12,170 |

- 3,000곡에서 60fps 가 깨지고, 7,000곡은 예산을 넘는다. 7,000곡의 프레임 간격 중앙값은 25.1ms, 33ms 넘는 프레임이 62개다.
- 9/11 기록(1,000곡에 예산 9.8%)은 낡았다. 같은 방법으로 다시 재니 754곡에 47.8% 였다 — 이유는 아래 "원인".

**측정 방법**: `scripts/perf-bench.js` 로 쟀다. 1겹 표본(`map_sample`)이 754곡뿐이라 2겹 실데이터를
`/bff/map/songs?level=2&…&size=N` 로 받아 `__odyEngine.setLayerSongs(0, points)` 로 주입했다. 7,000곡은 400×678,
나머지는 1024×768 이다. 754곡이 두 크기에서 7.98·8.1ms 로 거의 같아 화면 크기 차이는 무시했다. 원시값은
[`PERF-LOG.md`](../../PERF-LOG.md) 2026-09-18 행과 "곡 수 확장 실측" 블록.

### 배포본 기준선 (2026-09-25, 499 반영 전 `next-25`)

| 화면 | 배경 별밭 | 나머지 그리기 | 엔진(근사) | 프레임 합 | `drawImage`/프레임 |
| --- | --- | --- | --- | --- | --- |
| 데스크톱 1600×900 | **7.9ms (75%)** | 1.5ms | 1.0ms | 10.5ms | 6,051 |
| 폰 511×743 | **8.0ms (47%)** | 7.9ms | 0.9ms | **17.1ms** | 9,697 |

- 폰은 프레임 합이 예산(16.7ms)을 넘는다. 화면 안 곡 별이 데스크톱의 5배(4,465 대 855)이고, 그중 4,398개가 알파 0.15
  미만의 흐린 별이다.

**측정 방법**: 배포 빌드에는 엔진이 노출되지 않아 `perf-bench.js` 대신 같은 원리(캔버스·rAF 를 런타임에 가로채기)의
iframe 하네스로 쟀다. 배경 5,170회가 `drawMap` 앞쪽에 그려지는 순서를 이용해 5,170번째 `drawImage` 시각에서 구간을 잘랐다.
겹 0 정지, 데스크톱 CPU, 실데이터 1겹 5,745곡. 폰은 **화면 크기만** 폰이다 — 실제 폰 기기는 재지 않았다. 하네스 코드는
[`PERF-LOG.md`](../../PERF-LOG.md) 2026-09-25 "배포본 기준선" 블록에 있다.

**위 두 표는 서로 비교할 수 없다.** 9/18 의 "그리기" 는 `drawImage` 시간 합이고, 9/25 의 구간은 `drawMap` 벽시계 시간이다.
개선 전·후 비교는 같은 하네스로 잰 9/25 와 9/26 끼리만 한다.

004(499) 의 "배포본에서 지도 그리기는 프레임의 4%" 는 애니메이션 프레임 콜백 전체 시간 중 비율이라 이 문서의 ms 와 단위가
다르고, 배포본 함수 이름이 압축돼 있어 지도 그리기인지 확인하지 못한 값이다(499 "미확인"). 배포본 수치는 이 문서 것을 기준으로 본다.

## 원인

### 그리기 대부분이 곡이 아니라 배경 장식이었다

`drawBackground` 가 `field()` 를 네 번 부른다(S15P21A405-226·227, 9/12).

| 호출 | 개수 |
| --- | --- |
| 먼 별밭 | 1,100 |
| 중간 시차 | 1,100 |
| 먼 시차(70%) | 770 |
| 별먼지 `dustStars()` | 2,200 |
| **합** | **5,170 / 프레임** — 곡 수와 무관한 고정비 |

별 `drawImage` 호출 수가 세 측정 모두 정확히 **곡 + 5,170** 이다(754 → 5,924 · 3,000 → 8,170 · 7,000 → 12,170).
9/11 에는 `field()` 가 한 번이라 "별 2,100회 = 1,000 + 1,100" 이었다. 그때 PERF-LOG 에 적은 *"별 하나를 두 번 그리는
구간이 있다"* 는 오독이다 — 곡 별과 배경 별이 같은 48px 스프라이트를 써서 한 칸에 합산된 것이다.

### 곡을 늘려도 화면은 차지 않는다

7,000곡을 넣자 화면이 오히려 더 어두웠다.

| 무엇 | 알파 |
| --- | --- |
| 대표 곡 (`chosen`) | 0.42 ~ 1.0 |
| 장식 별 | 최대 0.25 |
| 대표가 아닌 곡 | 최대 0.13 |

대표 곡은 격자 한 칸당 1곡이라 754곡일 때 9개, 7,000곡일 때 19개뿐이다. 곡이 9배인데 밝은 별은 2배다. 나머지는 장식보다
흐린 먼지로 그려진다 — **비용은 다 내면서 안 보인다.** 화면 밝기를 정하는 것은 곡 수가 아니라 `pickRepresentatives()` 의
격자 선별과 알파 상한이고, 이 규칙은 누를 수 있는 별과 없는 별을 일부러 갈라놓은 것이다(S15P21A405-283).
2026-10-06 `frontend/dev` 의 `draw-map.ts` 에서도 대표 곡 0.42~1.0, 대표가 아닌 곡 최대 0.13 은 그대로다.

### 장식은 덜어도 티가 안 나고, 묶어 그릴 수 있다

곡을 754개로 고정하고 장식 개수에만 임시 배율을 걸어(실험 후 되돌림) 같은 화면을 비교했다.

| 장식 | `drawImage`/프레임 | 보이는 차이 |
| --- | --- | --- |
| 5,170 (100%) | 5,924 | 기준 |
| 2,585 (50%) | 3,339 | **눈으로 구분 안 됨** |
| 1,293 (25%) | 2,047 | 뭉치 바깥이 살짝 성겨짐 |
| 0 | 754 | 바깥이 확실히 빔 |

배경 별밭은 같은 배열을 오프셋만 바꿔 반복하는 타일이라, 한 장 구워 깔면 호출 수를 상수로 만들 수 있다고 봤다.

### 병목이 아닌 것

- 엔진 `frame()` 은 754 → 7,000곡에서 0.061 → 0.633ms(10배)지만 그리기에 비하면 작다
- 미니맵은 7,000곡에서도 0.2ms 다. 계측기가 제일 큰 캔버스만 보던 것을 고쳐 처음 쟀다(`79a17db3`)

## 측정 — 개선 후

2026-09-26, 499 가 배포된 `next-26` 을 9/25 기준선과 **같은 iframe 하네스·같은 PC·같은 망·같은 화면 크기**로 다시 쟀다.
화면 안 곡 수도 같다(폰 4,465 · 데스크톱 855). 겹 0 정지, 중앙값.

| 조건 | 개선 전 (`next-25`) | 개선 후 (`next-26`) | 변화 |
| --- | --- | --- | --- |
| **폰 511×743 — 프레임 합** | 17.1ms | **12.3ms** | **−28%** · 예산 초과 → 안쪽 |
| └ 배경 별밭 | 8.0ms | 2.6ms | −68% |
| └ 곡 별 등 나머지 | 7.9ms | 8.3ms | 거의 같음 |
| **데스크톱 1600×900 — 프레임 합** | 10.5ms | **9.0 · 9.3ms** (2회) | **−12~14%** |
| └ 배경 별밭 | 7.9ms | 2.6~2.8ms (3회) | −65% |
| 배경 `drawImage`/프레임 | 5,170 | 3,308 | −36% (004 와 같은 값) |

- **구간별 비교는 오해하기 쉽다.** 데스크톱 곡 별 구간이 1.5 → 5.2~5.8ms 로 늘어 보이지만 `drawStars` 는 이 배포에서
  바뀌지 않았다. 한 번의 호출이 혼자 3.7~3.9ms 를 기다리는데, 쌓인 그리기 명령이 GPU 로 넘어가는 지점의 대기로 본다(추정).
  예전엔 배경 안에서 일어나던 대기가 곡 별 구간으로 밀려난 것이라 **효과는 프레임 합으로 읽는다.**
- FPS 는 비교하지 않았다 — 이번 측정 때 화면 주사율이 85Hz 였다.
- 폰 390×844 도 16.1 → 12.3ms(−24%)였지만, 개선 전 값은 로딩 하네스의 프레임 p50 이라 방법이 조금 달라 표에서 뺐다.

## 남은 것

- **폰 프레임에서 이제 제일 큰 건 흐린 곡 별(8.3ms)이다.** 알파 0.15 미만의 대표가 아닌 곡 4,398개다. 폰에서 화면 안 곡이
  데스크톱의 5배인 이유는 겹 0 첫 카메라 배율로 보지만 **미확정**이다.
- 곡 수로 화면을 채우려면 대표 곡 선별·알파 상한을 바꿔야 한다 — 디자인 합의가 필요하다.
- 장식 50% 는 아직 후보다.
- 지도가 탭 화면에 가려져도, 멈춰 있어도 매 프레임 다시 그린다(9/25 기준선에서 확인).
- 실제 폰 기기는 재지 않았다. 데스크톱 CPU 로 폰 **화면 크기**를 잰 값이다. 한 번씩 잰 값이라(데스크톱만 2회)
  ±0.5ms 안팎의 흔들림이 있다.
- 같은 브랜치의 로딩 기준선은 [005](005-map-songs-gzip-etag.md) 가 비교에 쓴 "배포본 기준선"이고, `scripts/login-bench.mjs` 는
  005 측정 도구의 원본이다. 005 가 더해 썼다는 세 가지(대상 주소 설정·화면 가려짐 기록·와이파이 조건)는 이 스크립트에 없다.
