# 007. 탭 화면에 가려진 지도를 계속 그리던 문제

- 이슈: S15P21A405-737
- 커밋 / MR: 브랜치 `frontend/perf/S15P21A405-737-pause-covered-map` (작성 시점 미머지)
- 날짜: 2026-10-06 ~ 07 (측정·흉내) · 2026-10-07 (구현·비포·애프터)

## 증상

폰에서 하단 탭(주변 사람·랭킹·마이페이지)이나 검색 화면을 열면 그 화면이 지도를 통째로 덮는다. 그런데 지도는 그 뒤에서
매 프레임 다 그리고 있었다(폰 화면 기준 프레임당 `drawImage` 8,318회). 느린 폰 조건에서는 탭 화면에 있는 동안 메인 스레드가
꽉 차서, 화면이 초당 8~10번밖에 안 바뀌었다 — 탭 화면에서 누르거나 목록이 바뀌는 반응이 그만큼 늦는다.

## 측정 — 개선 전

폰 화면(390×844 DPR3), 랭킹 탭에 있는 8초 동안. 로컬 배포용 빌드(비포 `b6720130`).

| 지표 | 감속 없음 | CPU×4 |
| --- | --- | --- |
| 메인 스레드 (`TaskDuration`) | 초당 708ms | 초당 993ms (꽉 참) |
| 그중 스크립트 (`ScriptDuration`) | 628ms | 884ms |
| 화면 갱신 (rAF) | 초당 35번 | 초당 10번 |
| 프레임 간격 90% | 33.5ms | 108ms |
| 덮인 1초 동안 지도를 그린 프레임 | 27~38 | — |

**측정 방법**: 비포 빌드(3001)와 애프터 빌드(3000)를 동시에 띄우고, 측정용 크롬(CDP)으로 두 빌드를 번갈아 3회씩 쟀다.
한 회 = 지도를 띄운 뒤 지도 화면 6초 → 랭킹 탭 8초. 페이지에 계측을 끼우지 않는다. 충전기 연결, PostHog·GA 차단.
묶음 앞뒤 기준 측정(비포 빌드 지도 한 프레임, 폰·감속 없음)이 15% 넘게 흔들리면 버린다. 준비는 [`scripts/README.md`](../../scripts/README.md).

```
bash scripts/covered-map/run.sh                       # 기준 측정 → CPU×4 → 기준 측정 → 감속 없음 → 기준 측정
MODES=live node scripts/covered-map/check.mjs return  # 덮인 1초 동안 그린 프레임 · 돌아온 뒤 곡 별 밝기
```

## 원인

`map-canvas.tsx` 의 rAF 루프가 조건 없이 매 프레임 `engine.frame` → `drawMap` 을 불렀다. 탭 화면과 검색 화면은 지도와
따로 그려지는 라우트라, 지도(`main-screen.tsx` 의 `MapView`)는 그 뒤에 그대로 살아 있다.

탭 화면은 반투명 유리라(S15P21A405-703) 뒤의 지도가 흐리게 비친다 — "안 보이니까 안 그려도 된다" 가 아니다. 그래서 멈춰도
되는지부터 쟀다. 계속 그린 화면과 멈춘 화면을 6초 동안 캡처해 픽셀을 비교하니, 블러 18px·밑칠 60% 를 거친 뒤의 차이는
256단계 중 최대 랭킹 4 · 주변 사람 7 · 마이페이지 3 · 재생 중 곡을 넘겼을 때 7 이었다(원래 움직이는 화면 요소는 빼고 셈,
`scripts/covered-map/pixels*.mjs`·`check.mjs glass`). 눈으로 구별되지 않는다. 검색 화면은 바탕이 불투명해 아예 안 보인다.

## 조치

**덮은 화면이 있으면 그리지 않는다. 엔진은 66ms 간격으로 계속 굴린다.**

- 탭 화면(`panel-screen.tsx`)과 검색 화면(`search-screen.tsx`)이 `useCoverMap()` 으로 "지도를 덮었다" 고 알린다.
  `stores/use-map-cover-store.ts` 가 개수로 센다. 레이아웃 효과라 돌아오는 그 프레임부터 바로 그린다.
- 루프는 덮인 동안 `drawMap` 을 건너뛰고 `engine.frame` 만 `MAP_COVERED.engineStepMs`(66ms)마다 부른다.
- 건너뛰다 다시 그리는 첫 프레임에는 `draw-map.ts` 의 `settleAppear` 로 **건너뛴 시간을 "안 그려진 시간" 으로 치지 않는다** —
  보이던 별을 다시 밝히지도, 기억에서 잊지도 않는다. 처음 보는 별은 원래대로 0 부터 밝아진다.
  처음에는 이 프레임에 만나는 별을 전부 "다 밝아진 별" 로 쳤는데, 그러면 탭에서 곡을 눌러 돌아오며 지도가 날아가거나
  겹이 바뀔 때 새로 나타나는 별까지 한 번에 켜질 수 있어서 좁혔다.
- 덮인 동안 지도가 움직였다 멎으면 두 번 그린다 — 커버를 고르고 그림 받기를 시작해 둔다.
- 곡 목록이 새로 왔거나 캔버스가 비워졌으면 덮여 있어도 그린다(유리 뒤가 빈 하늘로 남지 않게).

### 왜 그냥 멈추지 않았나 — 흉내로 대안을 견줬다

코드를 고치기 전에, 페이지 안에서 지도 루프의 다음 프레임 예약만 붙잡았다 놓는 방식으로 대안을 흉내 냈다(`check.mjs`).
비용은 같은 랭킹 탭에서 8초씩 번갈아 3회씩, 2026-10-07 18시(기준 측정 32.4 → 34.0ms) — **아래 개선 후 표와는 날·시각이 달라
절대값을 맞대지 않는다.** 이 표 안에서만 비교한다.

| 방법 | 메인 스레드 CPU×4 | 감속 없음 | 화면에 생긴 차이 |
| --- | --- | --- | --- |
| 지금 (계속 그림) | 993ms | 567ms | — |
| 덮인 동안 루프를 통째로 멈춤 | 371ms | 109ms | 그냥 멈추면 돌아올 때 곡 별이 0 부터 0.38초 동안 다시 밝아진다(0.1초 24% · 0.2초 46~61% · 0.3초 72~86%). 멈춘 시간만큼 지도 시계를 빼 주면 그건 사라지지만, 따라가기("내 위치로 가기") 중 탭에서 곡이 넘어가면 돌아온 뒤 0.5초 동안 약 11px 미끄러진다 |
| 그리기만 쉬고 엔진은 매 프레임 | 894ms | 279ms | 없음 — 대신 거의 안 준다. `engine.frame` 한 번이 수 ms |
| **그리기만 쉬고 엔진은 66ms 간격** | **543ms** | **128ms** | 없음. 곡이 넘어가고 0.8초 만에 돌아와도 지도가 이미 새 곡에 가 있었다 |

다시 밝아지기는 `appear`(S15P21A405-284)가 "0.25초 넘게 안 그려진 별" 을 처음부터 밝히기 때문이다. 시계를 빼면 사라지지만,
그러면 따라가기의 지도 이동(프레임마다 다가가는 보간)도 덮인 동안 멈춘다. 엔진을 계속 굴리면 이동은 끝나 있고, 다시 밝아지기는
`settleAppear` 로 막는다.

### 같이 검토하고 버린 것 — 로딩 중 그리기 줄이기

첫 곡이 오기 전에도 루프는 배경 별밭을 매 프레임 그린다(첫 곡 전 메인 스레드의 17~19%). 곡 목록이 올 때까지 루프를 붙잡아
보니 **폰 첫 방문(CPU×4·LTE) 첫 곡이 2,707 → 3,716ms 로 늦어졌다**(짝 6쌍 모두, +521~+1,136, 중앙 +959). 재방문은 중앙
−115ms 였지만 짝마다 −829~+236 이라 잡음 수준이다(`scripts/covered-map/loading-hold.mjs`).

원인은 망이다. 브라우저 네트워크 기록(아이프레임 포함)으로 보니, 지금은 곡 목록(697KB, gzip)을 받는 동안 글꼴만 같이 받고
유튜브 플레이어는 첫 곡 뒤(3.67초)에 만들어진다. 메인 스레드를 비우면 플레이어가 1.9초에 만들어져 `base.js` 474KB 등
약 750KB 와 커버 그림이 곡 목록과 겹쳐 받아지고, 곡 목록 받는 시간이 0.65 → 1.2초로 는다. 바쁜 메인 스레드가 우연히
유튜브를 뒤로 미뤄 곡 목록을 지켜 주고 있었다. 유튜브를 늦추는 길은 이미 접었으므로(아이폰 재생 위험) 로딩 중 그리기는 그대로 둔다.

## 측정 — 개선 후

같은 방법, 같은 시각에 두 빌드를 번갈아 쟀다(애프터는 이 브랜치).

| 지표 (랭킹 탭에 있는 동안) | 개선 전 | 개선 후 | 변화 |
| --- | --- | --- | --- |
| 메인 스레드 — 감속 없음 | 초당 708ms | **초당 95ms** | −87% |
| 스크립트 — 감속 없음 | 628ms | 32ms | −95% |
| 화면 갱신 — 감속 없음 | 초당 35번 | **초당 120번** | 3.4배 |
| 프레임 간격 90% — 감속 없음 | 33.5ms | 8.5ms | |
| 메인 스레드 — CPU×4 | 초당 993ms (꽉 참) | **초당 344ms** | −65% |
| 스크립트 — CPU×4 | 884ms | 105ms | −88% |
| 화면 갱신 — CPU×4 | 초당 10번 | **초당 120번** | 12배 |
| 프레임 간격 90% — CPU×4 | 108ms | 8.4ms | |
| 덮인 1초 동안 지도를 그린 프레임 | 27~38 | **0** | |
| 지도 화면(안 덮임) 메인 스레드 — 감속 없음 / CPU×4 | 717 / 991ms | 717 / 992ms | 그대로 |

- 감속 없음은 기준 측정 17.1 → 16.8ms 묶음(최종 빌드)이다.
- CPU×4 는 기준 측정 17.7 → 17.3ms 묶음이다. 이 묶음의 애프터 빌드에는 "멎은 뒤 두 번 그리기" 가 아직 없었는데, 이 측정은
  재생도 지도 이동도 없어서 그 코드가 돌지 않는다. 최종 빌드로 5회씩 다시 잰 묶음은 애프터 중앙 394ms(370~417), 비포 992ms 로
  같은 쪽이지만, 첫 기준 측정이 22.7ms 로 튀어(→ 17.6ms, 29%) 규칙대로 주 수치로 쓰지 않았다. 비포는 어느 묶음이든 992~993ms 에
  붙어 있고(꽉 참), 애프터는 묶음에 따라 330~600ms 사이에서 흔들렸다 — PC 상태를 그대로 타는 쪽이 애프터다.
- 개선 후의 메인 스레드에는 덮인 동안에도 루프가 매 프레임 rAF 를 걸어(덮였는지 보려고) 화면을 초당 120번 만드는 비용이 들어 있다.
  화면 갱신 120번은 이 PC 모니터 주사율이다.

**화면이 안 바뀌었는지** — 실제 두 빌드로 확인했다(`check.mjs`, 각 2회).

| 확인 | 비포 | 애프터 |
| --- | --- | --- |
| 지도로 돌아온 뒤 곡 별 밝기 합 (0 / 0.1 / 0.2 / 0.3초) | 100% 그대로 | 100% 그대로 |
| 따라가기 중 탭에서 곡을 넘기고 3초 뒤 돌아왔을 때 돌아온 뒤 지도 이동 | 1px | 1px |
| 따라가기 중 덮인 동안 약 800px 떨어진 곡으로 옮긴 뒤 돌아왔을 때 이동 | 0~1px | 0px |
| 탭에서 곡 확대를 시키고 곧바로 돌아왔을 때 곡 별 평균 밝기 — 같은 겹 | 0.095~0.096 그대로 | 0.095~0.096 그대로 |
| 같은 경우 — 다음 겹으로 전환하며 | 새 겹 별이 0 에서 시작해 0.127 까지 | 같음 (0 부터 밝아짐) |
| 같은 경우 커버 그림 요청 (덮인 동안 / 돌아온 뒤) | 1 / 0건 | 1 / 0건 |

멎은 뒤 두 번 그리기를 넣기 전에는 마지막 경우에 돌아온 첫 프레임에 커버가 빈 적이 있다(2회 중 1회, 다음 프레임부터 참).
또 코드상 커버 그림은 그릴 때 고른 커버만 받기 시작하므로(`drawCovers` → `coverFor`), 돌아온 뒤에야 새 자리의 그림을 받는
구조였다 — 그림이 늦으면 대신 그린 무늬가 잠깐 보일 수 있어서 넣었다. 넣은 뒤 요청 시점은 위 표처럼 비포와 같다.

## 남은 것

- **실기기에서 안 쟀다.** 전부 PC 크롬에서 폰 화면을 흉내 낸 값이다. 배터리·발열과 탭 화면 스크롤의 매끄러움도 안 쟀다.
- 덮인 동안에도 루프가 매 프레임 rAF 를 건다. 타이머로 바꾸면 더 줄 수 있지만, 돌아오는 순간을 놓치지 않는 쪽을 골랐다.
- 데스크톱은 이 화면들(탭·검색 라우트)에 오지 않는다. 주소로 직접 들어와도 화면 전체를 덮으므로 멈춰도 같다.
- 엔진 66ms 는 따라가기의 지도 이동이 덮인 동안 끝나도록 고른 값이다. 곡이 넘어가고 0.8초 만에 돌아온 경우까지 확인했다.
  그보다 빨리(이동 중에) 돌아오면 남은 이동이 조금 보이고, 그 사이 화면에 들어온 별은 돌아온 뒤에야 밝아지기 시작할 수 있다 — 재 보지 않았다.
- 화면 확인의 "곡 별 밝기" 는 그려진 곡 별의 `globalAlpha` 를 프레임마다 모은 값이다. 수천 개를 합친 값이라 가장자리 몇 개의 차이는 묻힐 수 있다.
