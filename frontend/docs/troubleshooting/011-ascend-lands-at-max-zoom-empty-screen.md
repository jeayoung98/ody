# 011. 겹을 떠오르면 화면에 별이 하나도 없다

- 이슈: S15P21A405-327
- 커밋 / MR: (이 브랜치) · MR 미생성
- 날짜: 2026-09-14
- 앞 이야기: [006](006-layer-entry-scale-lost-on-ascend.md) — **같은 함수, 같은 계열, 반쯤만 고쳤던 것**

## 증상

> "레이어 위로 떠올랐을 때 별이 아예 없거든 화면에? 그래도 별 열개? 스무개?정도는 떠 있어야
> 되지 않을까?" / "화면에 아무 별도 없는 경우는 없어."

파고들었다 휠을 반대로 돌려 떠오르면 화면이 텅 빈다. 상주 집합은 1,000곡 그대로인데 보이지 않는다.

## 증거

`__odyEngine` 에서 직접 셌다. `pos` 는 화면 좌표이므로 `0 ≤ x ≤ W`, `0 ≤ y ≤ H` 로 거른다
(`posOut` 은 렌더 루프가 채우는 값이라 rAF 가 멈춘 패널에서는 못 쓴다 — [003](003-raf-paused-silent-test-failure.md)).

```js
const e = window.__odyEngine;
let res = 0, onPos = 0;
for (let i = 0; i < e.N; i++) {
  if (e.subset[i]) res++;
  if (e.alpha[i] > 0.5) {
    const x = e.pos[i * 2], y = e.pos[i * 2 + 1];
    if (x >= 0 && x <= e.W && y >= 0 && y <= e.H) onPos++;
  }
}
({ layer: e.layer, resident: res, onPos, camS: e.cam.s, entryS: e.entryS });
```

| 단계 | `layer` | `camS` | `entryS` | `camS/entryS` | 상주 | **화면 안** |
| --- | --- | --- | --- | --- | --- | --- |
| L1 진입 직후 | 1 | 46.07 | 46.07 | 1.0 | 1,000 | **979** |
| L2 → L3 파고듦 | 3 | 91.17 | 91.17 | 1.0 | 1,000 | 964 |
| L2 로 떠오름 | 2 | **639.93** | 83.17 | **7.7** | 1,000 | **65** |
| L1 로 떠오름 | 1 | **344.13** | 46.07 | **7.5** | 1,000 | **94** |
| (그 자리에서 `cam.s = entryS` 만 대입) | 1 | 46.07 | 46.07 | 1.0 | 1,000 | **979** |

마지막 줄이 전부다. 집합도 알파도 멀쩡하고 **배율 하나만 틀렸다.**

`camS/entryS` 가 7.5를 넘는다는 게 특히 이상하다 — 한 겹 안의 확대 한계는
`DRILL.zoomRange.max = 6` 이다. 사용자가 손으로는 절대 만들 수 없는 배율에 떠오르기가 데려다 놓고
있었다.

## 원인

`src/components/map/engine/map-engine.ts` `ascend()`

```ts
const p = this.stack.pop()!;
const c: MapCamera = { ...p.cam, cx: …, cy: … };   // 배율(p.cam.s)까지 그대로
```

`p.cam.s` 는 **파고들기 직전의 배율**이다. 그 값이 어떻게 만들어지는지 따라가 보면:

1. 게이트를 열려면 확대해야 한다 → `wheel()` 이 `entryS * zoomRange.max` = **6배**까지 올린다
2. 게이트가 열린 뒤 압력이 차는 동안 집합을 기다린다 → 프레임 루프가
   `cam.s = pending.s0 * (1 + DRILL.waitZoom * …)` 로 **더 확대한다**
3. 그 상태의 카메라가 `tryStartPending` 에서 스택에 쌓인다

그래서 `p.cam.s` ≈ 진입 배율의 **7.5~7.7배**다. **축소하려고 휠을 돌렸는데 그 겹의 최대 확대보다
더 확대된 좁은 구역에 착지한다.** 그 구역에 상주곡이 없으면 화면에 별이 하나도 없다.

같은 함수에 두 번째 구멍도 있었다.

```ts
const mi = this.myId != null ? this.index.get(this.myId) : undefined;
```

`p.subset` 을 보지 않는다. **그 겹에 상주하지 않는 곡**을 '나'로 들고 있으면 (깊은 겹에서 고른
이웃 곡, 못 박은 곡) 그 좌표를 화면 가운데로 잡는다 — 그 겹에는 아무것도 없는 자리다.

### 왜 이렇게 되어 있었나

[006](006-layer-entry-scale-lost-on-ascend.md) 에서 이 함수를 이미 한 번 고쳤다. 그때 문서에
이렇게 썼다.

> **카메라 위치·배율은 건드리지 않았다.** 떠났던 화면으로 돌아가는 연출은 의도한 동작이고,
> 고친 건 **줌아웃 기준점**뿐이다.

`entryS`(줌아웃 한계)는 되돌리고 `cam.s`(실제 배율)는 일부러 뒀다. "떠났던 화면으로 돌아간다"가
말이 되니까 그렇게 판단했다. 그런데 **떠날 때의 화면은 사용자가 보고 있던 화면이 아니다** —
게이트를 미느라 끝까지 확대돼 있던 한순간이다. 돌아갈 가치가 없는 상태였다.

## 조치

떠오르기는 **그 겹에 처음 들어왔던 배율**로 간다. 그 배율은 `fitCam` 이 그 겹을 화면에 맞춰
잡은 값이라, 거기 서면 상주곡이 화면을 채우는 게 정의상 보장된다.

```ts
const s = p.entryS;
const mi0 = this.myId != null ? this.index.get(this.myId) : undefined;
const mi = mi0 != null && p.subset[mi0] ? mi0 : undefined;   // 그 겹에 상주할 때만
const c: MapCamera =
  mi == null
    ? { ...p.cam, s }
    : { ...p.cam, s, cx: this.songs[mi].pc[dx] - (f.cx - this.W / 2) / s, cy: … };
```

중심 좌표 계산의 나눗셈도 `p.cam.s` 가 아니라 새 `s` 를 쓴다 — 배율이 바뀌었는데 예전 배율로
오프셋을 풀면 곡이 가운데에서 밀린다.

`p.entryS` 는 006 에서 이미 `Frame` 에 넣어 뒀다. 되살릴 값이 있었는데 안 쓰고 있었을 뿐이다.

**파고들기(`descend`)는 건드리지 않았다.** 거기서는 도착 배율이 곧 진입 배율이라 맞다.

## 확인

L0 → L1 → L2 파고든 뒤 그대로 떠오르기.

| 단계 | `layer` | `camS` | `entryS` | 상주 | **화면 안** |
| --- | --- | --- | --- | --- | --- |
| 시작 | 0 | 4.43 | 4.43 | 1,069 | 1,069 |
| 파고들기 | 1 | 41.68 | 41.68 | 1,000 | 982 |
| 파고들기 | 2 | 83.98 | 83.98 | 1,000 | 961 |
| **떠오르기** | 1 | **41.68** | 41.68 | 1,000 | **982** |
| **떠오르기** | 0 | **4.43** | 4.43 | 1,069 | **1,069** |

떠오른 뒤 숫자가 진입 직후와 **완전히 같다**. 고치기 전 같은 시나리오에서 94개였다.

회귀 확인 — 상주하지 않는 곡을 '나'로 들고 떠오르기:

```js
const up = e.stack[e.stack.length - 1];
let pick = -1;
for (let i = 0; i < e.N; i++) if (e.subset[i] && !up.subset[i]) { pick = i; break; }
e.myId = e.songs[pick].musicId;   // L3 에는 있고 L2 에는 없는 곡
```

| 시나리오 | 결과 |
| --- | --- |
| L3 에서 위 겹에 없는 곡을 '나'로 두고 떠오르기 | L2 도착, `camS` 83.98 = `entryS`, **화면 안 961** — 006 의 정상값과 동일 |

`npm run lint` · `npm test` · `npm run build` 통과.

## 배운 것

**"돌아간다"의 목적지가 사용자가 본 화면인지 확인한다.** 006 에서 "떠났던 화면으로 돌아가는
연출은 의도한 동작"이라며 배율을 일부러 남겼다. 그런데 떠나는 순간의 카메라는 사용자가 머물던
화면이 아니라 **전환을 일으키려고 시스템이 밀어붙인 한순간**이었다. 사람이 보고 있던 상태와
전이 직전 상태를 같은 것으로 본 게 잘못이다.

그리고 **불변식을 넘는 값이 보이면 그게 답이다.** `camS/entryS = 7.7` 은 `zoomRange.max = 6` 을
넘는다. 손으로는 만들 수 없는 값이 상태에 들어 있으면, 그 값을 넣은 경로가 버그다. 비율 하나만
찍어 봤으면 훨씬 빨리 찾았다.

006 이 반만 고친 자리다 — **한 함수에서 두 값(`entryS` 와 `cam.s`)이 같은 오염원에서 왔는데
하나만 씻었다.** 되돌리기 코드를 고칠 때는 그 프레임에 실려 온 값 전부를 한 번에 점검한다.
