# 012. 설문이 사라지거나 다음 곡이 멈추는 재생 수명주기

- 이슈: S15P21A405-369
- 기준 브랜치: `frontend/dev` / `582a095`
- 커밋 / MR: 아직 생성하지 않음
- 날짜: 2026-09-16

## 증상

1. A, B를 듣고 C를 재생해도 여정 설문이 안 뜬다.
2. 주변 탐색을 닫거나 다른 기준곡을 선택하면 아직 답하지 않은 질문이 사라진다.
3. 이전 버튼, 활동 교체, 자동 종료에서 설문 보류가 일관되지 않다.
4. 저장 요청이 실패해도 카드는 닫히고 이미 답한 것으로 처리된다.
5. 튜토리얼을 완료하거나 건너뛴 뒤 새 문서에서는 `isDone=false`로 돌아온다.
6. 주변 탐색에서 이웃을 수동으로 연달아 재생하면 두 번째 곡을 목록 밖으로 오판한다.
7. 주변 탐색 뒤 새 여정을 만든 다음 순차 재생하면 방금 만든 경로 별자리가 사라진다.

## 증거

- 기존 runner는 `markPlayed(B)` 뒤 `journeyEdge(B, trail)`를 호출했다. 이때 `lastPlayed=B`이므로 `j <= i` 조건에 걸렸다.
- `isPlaying`은 재생 요청인데 실제 청취로 사용했고, 현재 뷰가 바뀔 때 `setPending(null)`을 실행했다.
- 기존 `gate`는 이미 열려 있어도 `queued`를 덮어썼다. 사용자 목적지 99 뒤 자동 next가 오면 목적지가 다음 정거장으로 바뀌었다.
- 기존 카드는 `mutate()` 직후 `markAnswered()`와 `close()`를 호출했다.
- `finish()`는 `ody:tutorial-done=true`를 저장하지만 `TutorialGate`는 그 값을 store에 복원하지 않았다. 건너뛰기도 같은 finish 경로라 같은 문제였다. 홈 이동은 API의 `onSettled`에 매달렸다.
- 최초 조사한 `476708c`의 타입 오류 9건은 작업 브랜치 생성 시 최신 dev에 들어온 367/366 등에서 이미 일부 해결됐다. 그 수정을 본 작업 성과로 세지 않는다.

## 원인

선택/탐색 화면, 재생 의도, 실제 청취, 질문과 제출 결과의 수명주기를 React effect 순서로 엮었다. 순수 간선 검사만으로는 플레이어·뷰·저장 연결의 회귀를 발견하지 못했다.

## 조치

- 기본 재생은 `runPlaybackTransition` 하나로 보류/재개한다. 활동 종료와 다음 재생, 관련 후속 동작을 한 번에 실행한다. 끼어든 기능이 없으면 즉시 동작한다.
- YouTube는 실제 PLAYING/정지/확정 불가를 `playback-events`로 보고한다. 곡 ID·재생 세대·현재 영상·현재 상태를 대조해 늦은 이벤트를 걸러낸다. 요청만으로는 청취하지 않는다.
- `playback-connection`이 재생 요청 당시 탐색 출처를 보존한다. 지도 뷰는 질문을 변경하지 않는다. 추천 결과가 늦으면 다음 전환을 잠시 보류하고, 확인 실패/10초 초과는 그 평가를 제외한다.
- `listening-flow`가 청취 흐름과 모드별 규칙을 맡는다. 다른 탐색의 **실제 청취**가 시작되면 이전 기준곡 자격이 끝난다. 방금 들은 곡은 새 탐색의 출발 근거로 쓸 수 있다.
- 주변은 실제 들은 기준곡과 이웃, 여정은 정방향 인접 또는 확정 불가 정거장만 건너 이은 전환이다. 역순/임의 점프, 조회 중/실패/검색 전은 유효 간선으로 만들지 않는다.
- 최초 보류 목적지를 유지한다. 저장 성공 후 정확히 한 번 실행하며 다음 곡의 `isPlaying`을 명시한다.
- 이미 답한 문항 조회가 끝나기 전에는 중복 질문을 먼저 띄우지 않는다. 조회 실패는 알리고 이번 탭에서 확인된 답만 사용한다.
- 제출 본문은 최초 답 선택 때 고정한다. 성공 후에만 answered 처리. 실패 시 답·식별자를 보존하고 재시도/계속 듣기 제공. 15초 요청 타임아웃. 실패한 응답을 null로 재전송하지 않는다.
- pagehide는 제출 시도 없는 유효 질문만 best-effort 전송한다. bfcache 복귀 후에는 행 식별자를 갱신해 늦은 null 전송이 새 응답을 덮지 못하게 한다.
- 튜토리얼 완료/건너뛰기 모두 같은 `finish()`로 로컬 완료값을 저장한다. 홈 게이트는 `/me`보다 먼저 로컬 값을 store에 복원한다. 홈 이동은 서버 응답과 분리하고 서버 동기화는 keepalive로 시도한다.
- 큐가 없는 주변 탐색도 탐색 활동으로 유지하되, 같은 중심의 이웃을 수동 청취하는 것은 목록 이탈로 보지 않는다.
- 활동 종료 시 현재 지도 전체를 지우지 않고 그 활동이 소유한 주변 고리·별자리만 정리한다. 이미 새 여정 별자리로 교체됐다면 보존한다.
- 맵 선택·여정 목록 재생·하단 이전/다음·자동 다음은 모두 같은 재생 게이트를 지난다. store는 예상 밖의 늦은 PLAYING이 와도 가장 오래된 미응답 질문을 교체하지 않는다.
- 새 주변/별자리 화면을 연 직후에는 플레이어에 이전 활동이 남아 있을 수 있다. 맵 별 재생은 플레이어의 과거 컨텍스트가 아니라 클릭 순간 화면이 나타내는 탐색 출처를 스냅샷으로 넘긴다. 그래서 주변 별을 목록 밖 단일곡으로 오판하지 않고, 다른 활동에서 경로 별을 눌러도 해당 경로 큐가 복원되어 하단 다음 버튼이 유지된다.
- Fast Refresh가 `ready=true`만 보존하고 미완성 YouTube 객체를 교체하는 경우가 있어, 실제 API 메서드 존재까지 확인한 뒤 로드·재생·정지한다. 이 오류가 PLAYING 보고를 끊어 설문이 누락될 수 있었다.
- 설문은 홈 경로에서만 마운트한다. 튜토리얼 재실행 중에는 저장된 완료값이 있어도 설문/청취 기록이 붙지 않는다.

브라우저 카드 검증은 `tests/fixtures/survey-screen.tsx`로 **transport와 HTTP 경계만 모의 처리**했다. 개발용 임시 route는 검증 후 삭제했다. 운영 피드백 POST는 하지 않았다. 실제 YouTube 음원·자동재생 정책과 배포 DB까지 연결한 E2E 성공을 뜻하지 않는다.

제거 검증은 OS 임시 폴더를 사용한다. Windows sandbox 경로 추적 권한으로 두 차례 실패 후, 동일 검증을 권한 있는 프로세스에서 수행해 통과했다. 원본의 설문 파일은 삭제하지 않았다.

## 최종 배포에서 제거하는 방법

1. 기능만 끄기: `NEXT_PUBLIC_SURVEY_ENABLED=false`로 **다시 빌드**한다. 368의 스위치 통합은 이 브랜치에 섞지 않았다.
2. 실제 제거: `src/components/survey/`, `src/hooks/survey/`, `src/app/bff/feedback/`, `src/stores/use-survey-store.ts`, `src/constants/survey.ts`, `src/types/survey.ts`, `src/lib/anonymous-id.ts`를 제거한다.
3. `REMOVE-WITH-SURVEY` 표식이 있는 마운트/import/설정 줄을 제거한다. `tests/survey-lifecycle.test.cjs`, `tests/fixtures/survey-screen.tsx`, 제거 검증 스크립트도 함께 정리한다.
4. `use-player-store`, `use-blocking-store`, `playback-events`, 튜토리얼 완료 복원은 기본 기능이므로 남긴다. 설문 import가 없다. 새 패키지도 추가하지 않았다.
5. lint/test/build를 다시 실행한다. 원본을 건드리지 않는 사전 연습은 `node tests/check-survey-removal.cjs`.

브라우저 fixture를 다시 쓰려면 개발 환경에서만 임시 `src/app/dev-survey-check/page.tsx`가 `../../../tests/fixtures/survey-screen`을 렌더하도록 연결하고 검증 후 route를 삭제한다. 이 fixture의 요청은 첫 회 503, 다음 회 성공으로 브라우저 안에서 끝난다.

## 남은 위험 / 상대 파트에 알려야 할 점

- backend/dev의 346 구현은 읽었으나 backend/DB는 수정하지 않았다. `(session_id, rank)` upsert라 같은 자리의 비교 상대가 바뀌면 FE가 새 세션을 만든다. 분석 시 탐색 청취 흐름이 분절될 수 있다.
- 서버의 사람×문항 중복 검사는 SELECT→INSERT이므로 여러 탭의 동시 제출까지 원자적으로 막지는 못한다. BE 검토 필요(BACKEND-NOTES A-26).
- 전송 실패에는 서버 미저장과 **저장됐지만 응답만 유실**된 경우가 모두 있다. FE는 저장 확인 실패로 표현하고 같은 본문으로 재시도한다. 실패 자체를 DB의 무응답 행으로 남기지 않는다.
- pagehide 전송은 보장되지 않는다. 영속 재전송 큐는 추가하지 않았다.
- 로컬 저장소가 차단되고 서버 동기화도 실패하면 새 문서에서 완료를 복구할 근거가 없다. 현재 문서에서는 완료 처리하며 일반 저장소 환경의 완료/건너뛰기는 복원된다.
- 295 stash는 그대로 보존했다. 향후 분석 연결은 설문 store를 import하지 말고 일반 playback 이벤트를 구독해야 한다.

## 배운 것

추천 간선 규칙뿐 아니라 실제 재생 신호 → 전환 보류 → 서버 결과 → 재개까지 연결해 검사해야 한다. 임시 기능의 제거 가능성도 설명으로 끝내지 말고 파일을 뺀 빌드로 확인한다.
