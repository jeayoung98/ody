# Feature Specification: PC 레이어 상주 집합 조회

**Feature Branch**: `backend/feat/S15P21A405-50-music-major`

**Feature Directory**: `specs/001-pc-major-tracks`

**Created**: 2026-09-08

**Status**: Draft — 근거 기반 명세 작성본, 제품 정책·외부 계약 미결정 사항 및 충돌 해소 전

**Input**: 프론트엔드가 전달한 레벨과 이전 겹의 누적 범위로 지도 상주 집합을 반환한다.
2026-09-17 후속 요청 A-30~A-32는 응답 개수 측정용 `size`, 지도 응답의 `youtubeUrl` 제거,
`pc[16]` 응답값의 소수점 이하 최대 3자리 반올림을 추가한다. level·누적 범위 구조는 바꾸지 않는다.

기존 동일 기능 명세를 갱신한다. 이전 작성본의 범위 입력 요구사항·범위 경계 시나리오는 폐기한다.
이번 정정은 중심좌표 입력을 명시한 API 원문과 일치한다. 레벨과 현재 축 쌍의 대응은
아래 명확화 답변으로 확정했으며, 원본의 레벨별 축 개수 표현은 동기화가 필요하다.

## Clarifications

### Session 2026-09-18 (D20) — 1레이어 상주 집합 밀도 가중

- Q: 1레이어 상주 집합은 격자와 무관한가요? → A: **아니다. 1레이어는 격자 산출물이다(D20).**
  D16 의 "서버가 격자를 적용하지 않는다(MUST NOT)" 는 **줌에 따라 변하는 화면 격자**를 가리킨 것이고,
  1레이어 정적 표본은 처음부터 데이터 좌표 격자(간격 2.0)의 칸별 대표곡이었다. 두 격자는 다른 것이다.
  명세가 이를 구분하지 않아 밀도 가중 배분이 D16 위반으로 읽혔다 — 문구를 갈라 쓴다.
- Q: 칸당 몇 곡을 뽑나요? → A: **k = min(round(cbrt(n)), 40)** (D20). `n` 은 그 칸의 재생 가능한 곡 수.
  칸당 1곡은 칸 사이 밀도 차(운영 `map_sample.cnt` 전수 실집계 2026-09-18:
  25% 6곡 / 50% 66곡 / 75% 1,201곡 / 99% 86,651곡, 최대 98,660곡)를 전부 지운다.
  밀도 **정비례** 샘플링은 기각 — 칸의 63~69%가 사라지는데 그 칸들이 담은 곡은 0.85%뿐이다.
  계수·바닥 보정은 두지 않는다(이분 탐색 결과 계수가 1.002 로 수렴).
- Q: 칸 안에서 어떤 곡을 고르나요? → A: **무작위(D20).** `md5(id::text)` 순. **칸 중심 최근접을 버린다.**
  중심 최근접이 점의 81.8%를 칸 중심 0.25칸 안에 몰아 바둑판을 만들었다 — 밀도 가중 후 19.4%
  (균등분포 19.6%와 구별 불가, 나머지 χ² 1704→3).
- Q: 재생 불가 곡도 대표가 되나요? → A: **아니다(D20).** 대표 후보를 **재생 가능한 곡으로 한정**한다.
  판정의 정본은 `music.is_unplayable` 이다 — S15P21A405-454(MR 330)가 `video_id = 'none'` 표시값에서
  플래그로 옮겼다. 명세는 **의미("재생 가능한 곡")로 쓰고 판정식을 박아 두지 않는다**; 식은 454 가 정본이다.
  - ⚠️ **미해결 — 응답 단계 필터를 둘지.** spec 008(454)은 **지도가 재생 불가 곡을 뺀다**고 정했고,
    FR-009 는 **재생 불가라는 이유만으로 응답에서 빼지 않는다**(`playable: false` 로 내려보낸다)다.
    정면으로 갈리므로 한쪽을 고쳐야 한다. **결정 전까지 D20 은 응답 단계 필터에 대해 아무것도 요구하지 않는다.**
    초안의 "응답 단계 필터가 342칸(31%)을 삭제한다" 는 **철회**했다 — 아래 실측 참조.
- Q: 격자 간격을 줄이나요? → A: **아니다(D20).** 2.0 유지. 0.75 축소안은 바둑판도 밀도도 고치지 못해 철회.

### Session 2026-09-17 (A-30~A-32) — FE 요청

- Q: 정적 표본을 확장하기 전 레이어 1에서 `size`를 어떻게 처리할까요? → A: `size`를 반환 상한으로 적용한다. 요청값이 현재 정적 표본보다 크면 가용 표본 전체를 반환한다.
- Q: `size`의 허용 범위와 범위를 벗어난 값은 어떻게 처리할까요? → A: `1 ≤ size ≤ 10000`만 허용하고, 범위 밖 또는 비정수 값은 400 `INVALID_INPUT`을 반환한다.
- Q: PC 값이 정확히 네 번째 소수점 5에서 걸릴 때 어떤 반올림 규칙을 사용할까요? → A: `HALF_UP`을 적용한다. 예를 들어 `-1.2345`는 `-1.235`로 반환한다.
- Q: `level`은 PC 16차원에 맞춰 1부터 8까지만 허용할까요? → A: `1 ≤ level ≤ 8`만 허용하고, 범위 밖 또는 비정수 값은 400 `INVALID_INPUT`을 반환한다.
- Q: 누적 범위 안에 후보 곡이 하나도 없으면 어떤 응답을 반환할까요? → A: 정상 결과로 200과 `data.content: []`를 반환한다.
- **A-30**: optional `size`로 레이어별 상주 곡 수를 지정한다. 생략하면 현행 약 1,000곡 동작을 유지한다.
  1,000 → 3,000 → 10,000 실측이 목적이며, 값이 확정되면 파라미터를 닫고 고정값으로 전환한다.
- **A-31**: 지도 전용 `MapPoint`에서 `youtubeUrl`을 제거한다. `playable`은 유지하고,
  곡 상세(`/api/music/detail`)의 `youtubeUrl` 계약은 바꾸지 않는다.
- **A-32**: `MapPoint.pc[16]`은 응답에서 소수점 이하 최대 3자리로 반올림한다.
  저장 좌표와 후보 판정·누적 범위 계산의 정밀도는 바꾸지 않는다.
- **구현 선행 조건**: 2레이어 이후 조회 경로는 이미 개수 제한을 전달하지만, 1레이어 정적 표본은 약 1천 건뿐이다.
  1레이어에서 3,000·10,000곡을 측정하려면 공간 균등 성질을 유지한 더 큰 정적 표본이 필요하다.
  ⟲ *2026-09-18 D20 로 해소* — 칸당 밀도 가중 배분이 그 표본을 만든다.

- Q: 응답 항목 필드 구성과 상주 집합 크기를 어떻게 정하나요? → A: **FE `MapPoint` 기준으로 맞춘다(D18).**

### Session 2026-09-11 (3차)

- Q: 인기 지표가 없어서 FE 가 인기순 선별을 못 하는데, 서버가 상주 집합만 보낸다면 이건 FE 가 나중에 정해도 되나요?

  그러나 클라이언트는 전달받은 필드로만 정렬할 수 있으므로 **`weight` 필드는 지금 응답에 포함**한다.
  현재 값은 0/균일값이고, 지표가 생기면 서버만 채운다. 응답 스키마와 FE 는 그대로다.

### Session 2026-09-11 (2차)

- Q: 격자 단위가 데이터 좌표 고정값인가요, 화면 픽셀 기준인가요? → A: **FE 기준으로 맞춘다(D16).**
  격자는 화면 픽셀 기준(`REPRESENTATIVE_GRID_PX` = 86px)이며 **줌에 따라 가변**이다.

  **귀결 — 역할이 분리된다.** 화면 격자는 줌 배율마다 달라지므로 서버가 미리 계산할 수 없다.
  D15 의 "1레이어 정적 서빙" 과 양립하려면 서버가 내려주는 것이 *격자 대표곡*이 아니라
  **레이어 상주 집합**이어야 한다. 화면 격자 대표 선별은 클라이언트가 한다.
  FE 설계와 일치한다 — "상주 곡은 **전부 그린다**. 대부분은 작고 어두운 배경 별이고,
  `REPRESENTATIVE_GRID_PX` 격자에서 이긴 곡만 크고 밝게 뜬다. 확대하면 격자가 촘촘해져 더 많은 별이 도드라진다."

  ⚠️ 이 귀결이 의도와 다르면 **D15 의 정적 서빙 결정을 다시 열어야 한다.** 서버가 화면 격자로
  대표곡을 고르려면 요청마다 줌 배율을 받아 실시간 계산해야 하고, 1레이어 전역 집계 20,941 ms 가 되살아난다.

  **이 결정은 롤백 가능하도록 원안을 전문 보존한다 — "대체된 요구사항 — 롤백 기록" 절 참조.**

- Q: 원형 영역 안에서 어떤 곡을 대표곡으로 선정하나요? → A: C. 원형 영역 안의 곡을 유튜브 조회수 내림차순으로 정렬하여 상위 k곡을 선정·반환한다. k=1000은 현재 잠정 후보이며 확정값이 아니다. 조회수 순 인덱스 활용은 plan 단계의 구현 검토 후보다. 후속 사용자 보충: youtubeCnt가 유튜브 조회수다. playCnt는 동결된 값이며 AcousticBrainz 조회수라는 출처는 추정으로 남긴다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 중심좌표 주변 구역의 대표곡 확인 (Priority: P1)

음악 지도 사용자가 탐색 위치를 선택하면 프론트엔드는 레벨과 해당 PC 중심좌표를 전달하고,
그 조건에 대한 대표곡 목록을 받아 표시한다. 후보 구역은 요청 중심을 따라 이동하며 미리 정해진 그리드는 없다.
⟲ *2026-09-11 D15 로 개정.* 선택 영역은 **격자로 나눈 구역**이고, 구역의 선택·이동은 클라이언트 뷰포트가 한다.
1레이어는 정적 사전 계산 결과를 내려주고 2레이어 이후는 실시간 산정한다. 격자 단위·영역 파라미터·칸별 선정 규칙은 미정이다(FR-012·FR-013).
*(원안: "요청 중심과 반경으로 정하는 원형, 서버가 레벨별 반경 결정" — 롤백 기록 절 참조)*

**Why this priority**: 전체 곡 대신 해당 탐색 구역을 대표하는 곡을 제공하는 이번 조회의 핵심이다.

**Independent Test**: 선정 결과가 주어진 경우 공통 응답과 곡 정보·고정 좌표 보존을 독립 검증한다.
선정 우선순위는 유튜브 조회수 내림차순으로 확정했다. 정확한 후보·k·동률·누락 처리는 P1~P3의 잔여 결정 전에는 고정할 수 없다.

**Acceptance Scenarios — 원본 및 사용자 답변으로 확정한 검증**:

1. **A1**: **Given** 인증된 요청의 대표곡 조회가 성공했고,
   **When** 목록을 반환하면, **Then** 200 및 `success: true`, `data.content` 배열,
   `error: null`을 제공한다. 페이지 정보 유무는 C2 해소 전 판정하지 않는다. (FR-001, FR-005)
> ⟲ **A2 는 2026-09-11 D18 로 보류.** FR-006 원안(정본 §0.6 전 필드)의 검증이라 개정본에 해당하지 않는다.
> 삭제하지 않는다 — 롤백하면 그대로 쓴다. 새 수용 기준은 `MapPoint` 필드 대조로 T015 와 함께 쓴다.
> `location.pc1`~`pc16` 이 곡 기준선 좌표와 일치한다는 **좌표 불변 부분(FR-007)은 유효**하다.

### User Story 2 - 좌표 선택 전 최상위 조회 (Priority: P1)

사용자는 PC 중심좌표를 아직 선택하지 않아도 최상위 대표곡 조회를 시작할 수 있다.

**Why this priority**: API §3.4가 명시한 최상위 진입 동작을 보존한다.

**Independent Test**: 인증된 `GET /api/api/music/major?level=1` 요청에 PC 필드를 넣지 않고
PC 누락만으로 검증 오류가 발생하는지 확인한다. 구체적인 선정 목록은 별도 미정이다.

**Acceptance Scenarios**:

1. **A5**: **Given** 유효한 인증과 조회 의존 데이터가 준비되었고,
   **When** `level=1`에 PC 값 없이 조회하면, **Then** PC 값 생략만을 이유로
   `VALIDATION_ERROR`를 반환하지 않는다. (FR-004)

### User Story 3 - 실패를 정상 결과와 구분 (Priority: P2)

호출자는 인증 실패·잘못된 타입·내부 실패를 정상 대표곡 응답과 구분한다.

**Independent Test**: 인증 상태, 문서에 명시된 타입 위반, 내부 실패를 각각 구성하고 기존 오류 계약을 확인한다.

**Acceptance Scenarios**:

1. **A6**: **Given** 토큰이 없거나 위조·만료되었고, **When** 조회하면,

   토큰 없음의 세부 코드가 별도 명시되지 않았으므로 해당 경우는 상태·공통 실패 구조까지만 검증한다. (FR-002, FR-010)
2. **A7**: **Given** 유효한 인증이 있고, **When** `level=abc` 또는

   400·`VALIDATION_ERROR`와 공통 실패 구조를 반환한다. (FR-003, FR-010)
3. **A8**: **Given** 조회 중 서버 내부 실패가 발생했고, **When** 응답하면,
   **Then** 500·`INTERNAL_ERROR`와 공통 실패 구조를 반환한다. 성공 목록으로 응답하지 않는다. (FR-010)

### Functional Requirements

각 요구사항의 확정 범위만 규범으로 작성한다. P1~P3에 의존하는 세부 동작은 아직 규범이 아니다.

  대한 대표곡 목록을 반환해야 한다(MUST). 이번 요청의 입력 의도는 중심좌표 한 쌍이다.
  현재 단계의 축 쌍을 전달한다는 의미를 사용자 답변으로 확정했다. 원문 동기화는 C1에 기록한다.
  **근거**: 이번 사용자 요청 「목적과 범위」; [docs/api-spec.md §3.4 대표곡 조회](../../docs/api-spec.md).

  **근거**: [docs/api-spec.md §0.1·§0.7·§3.4](../../docs/api-spec.md);
  [docs/requirements.md §6 보안-인증·전송](../../docs/requirements.md).
- **FR-003 — 입력 이름·타입**: 입력 계약의 `level`(int), `pc1`~`pc16`(각 float 중심좌표)
  필드명을 유지해야 한다(MUST). PC 번호가 필드명에 포함되어 있다.
  `x/y`, 별도 축 ID, PC별 min/max 등의 새 필드를 임의로 계약에 추가하지 않는다.
  level은 현재 PC 조회 단계이며, 지원되는 정수 레벨 n은 PC(2n-1)·PC(2n)에 대응해야 한다(MUST).

  장르 단계나 이전 PC 단계의 중심을 뜻하지 않는다. 공개 지원 범위는 1~8이며,
  범위 밖 또는 비정수 값에는 400 `INVALID_INPUT`과 공통 실패 구조를 반환해야 한다(MUST).

  1레이어에서는 `size`를 현재 정적 표본에 대한 반환 상한으로 적용한다. 요청값이 표본 수보다 작으면
  요청 수만큼 반환하고, 크면 정적 표본 전체만 반환한다. `size`를 조용히 무시하지 않는다.
  이 파라미터는 레이어별 곡 수를 결정하기 위한 임시 측정 도구이며, 최종 값 확정 후 고정값으로 닫을 수 있다.
  10,000은 측정 단계의 운영 보호 상한이다.
- **FR-015 — 지도 URL 제거 (A-31)**: `MapPoint`는 `youtubeUrl` 키를 포함해서는 안 된다(MUST NOT).
  `playable`은 그대로 포함해야 하며(MUST), `/api/music/detail`의 `youtubeUrl` 계약은 변경하지 않는다(MUST NOT).
- **FR-016 — 지도 좌표 응답 정밀도 (A-32)**: `MapPoint.pc`의 16개 값은 응답에서 소수점 이하
  최대 3자리로 `HALF_UP` 반올림해야 한다(MUST). 반올림은 지도 응답 표현에만 적용하고, 저장 좌표·범위 판정·공간 샘플링·
  다른 API의 좌표 정밀도는 바꾸지 않는다(MUST NOT).
