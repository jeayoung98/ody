# 프론트엔드 전달 문서: 음악·아티스트 조건 검색

**기능 ID**: SEARCH-01
**연관 이슈**: S15P21A405-365
**기준 명세**: [spec.md](spec.md)
**대상 화면**: 지도 상단 검색바와 검색 결과 드롭다운
**백엔드 구현**: `backend/feat/S15P21A405-365-music-search-filter`
**상태**: 백엔드 구현·자동 테스트 완료, `backend/dev` 병합 및 배포 전

## 1. 변경 목적

현재 통합 검색은 입력 하나를 음악 제목과 아티스트 이름에 함께 적용한다. `Love`처럼 흔한 제목은 동명 음악이 많고, 아티스트 이름과 같은 제목의 음악이 있으면 원하는 아티스트의 결과가 뒤로 밀릴 수 있다.

검색바는 하나로 유지하면서 다음 세 경로를 제공한다.

1. **통합 검색**: 입력을 음악 제목 또는 아티스트 이름에서 찾는다.
2. **아티스트 검색**: 입력을 아티스트 조건으로 고정해 그 아티스트의 음악만 찾는다.
3. **음악+아티스트 검색**: 음악 제목과 아티스트 조건을 동시에 적용해 동명 음악을 좁힌다.

사용자 화면에서는 `곡명` 대신 **음악**, `가수` 대신 **아티스트**를 사용한다.

## 2. UI 요구사항

### 2.1 검색바

- 검색 입력 영역은 하나만 둔다.
- 기본 placeholder는 `음악 · 아티스트 검색`이다.
- 확정한 조건은 입력창 안의 제거 가능한 칩으로 표시한다.
  - `음악: Love`
  - `아티스트: Radiohead`
- 칩이 있으면 남은 입력 영역은 반대 조건을 받는다.
  - `아티스트: Radiohead` + 입력 `Creep` → Radiohead의 Creep 검색
  - `음악: Love` + 입력 `Lana Del Rey` → Lana Del Rey의 Love 검색
- 칩 제거 시 현재 남은 문자열을 통합 검색어로 유지하고 기본 상태로 돌아간다.
- 조건을 전환하거나 칩을 제거하면 페이지를 0으로 초기화한다.
- `Escape`는 입력과 칩을 모두 지우고 드롭다운을 닫는다.

### 2.2 결과 드롭다운

기본 통합 검색 상태에서 입력값이 있으면 결과 목록과 조건 전환 동작을 함께 표시한다.

```text
┌──────────────────────────────────────┐
│ 🔍 Love                              │
├──────────────────────────────────────┤
│ Love                         Lana Del Rey │
│ Love Story                   Taylor Swift │
│ ...                                  │
├──────────────────────────────────────┤
│ “Love”를 아티스트로 검색             │
│ “Love” 음악을 아티스트로 좁히기      │
└──────────────────────────────────────┘
```

- `“입력값”을 아티스트로 검색`
  - 입력값을 `아티스트` 칩으로 전환한다.
  - 아티스트 조건만으로 즉시 다시 조회한다.
- `“입력값” 음악을 아티스트로 좁히기`
  - 입력값을 `음악` 칩으로 전환한다.
  - 입력 포커스를 유지하고 아티스트 입력을 기다린다. 빈 입력에서는 API 요청 없이 아티스트 입력 안내를 표시한다.
- 결과 항목을 누르면 기존 SEARCH-01 동작을 유지한다.
  - 상세 패널을 연다.
  - 현재 겹에 있으면 해당 음악으로 확대 이동한다.
  - 현재 겹에 없으면 고스트별로 표시한다.
  - 레이어를 자동으로 바꾸지 않는다.
- 다음 페이지가 있으면 목록 하단에 `다음 결과 보기`를 표시한다. 클릭 시 다음 페이지를 이어 붙인다.
- 같은 음악 ID가 이미 표시되어 있으면 다음 페이지 결과에서 중복 추가하지 않는다.

### 2.3 상태별 표시

| 상태 | 검색바 | 드롭다운 안내 |
| --- | --- | --- |
| 통합 검색 | 칩 없음 + 일반 입력 | `음악 또는 아티스트 검색 결과` |
| 아티스트 검색 | `아티스트: {값}` | `{값}의 음악` |
| 아티스트 안에서 음악 검색 | `아티스트: {값}` + 음악 입력 | `{값}의 “입력값” 음악` |
| 음악을 아티스트로 좁히기 | `음악: {값}` + 아티스트 입력 | `“값” 음악의 아티스트 결과` |
| 조건 변경 후 로딩 | 이전 조건 결과 제거 | `검색 중...` |
| 다음 페이지 로딩 | 같은 조건 결과 유지 | 하단에 `검색 중...` |
| 빈 결과 | 조건 유지 | `일치하는 음악이 없습니다.` |
| 실패 | 조건 유지 | `검색하지 못했습니다. 다시 시도해 주세요.` + 재시도 |

빈 결과와 요청 실패를 같은 화면으로 처리하지 않는다.

## 3. 사용자 흐름

### 3.1 통합 검색

1. 사용자가 `Love`를 입력한다.
2. 디바운스 후 통합 검색을 요청한다.
3. 음악 제목 또는 아티스트 이름이 `Love`로 시작하는 결과를 보여준다.
4. 결과 선택 시 기존 지도 포커스와 상세 패널 동작을 실행한다.

### 3.2 아티스트만 검색

1. 사용자가 `Radiohead`를 입력한다.
2. 드롭다운에서 `“Radiohead”를 아티스트로 검색`을 선택한다.
3. 검색바가 `아티스트: Radiohead` 칩 상태로 바뀐다.
4. Radiohead와 이름이 같은 음악의 존재와 관계없이 해당 아티스트 조건의 음악만 보여준다.
5. 사용자가 칩을 제거하면 남은 입력만 통합 검색어로 사용한다. 남은 입력이 없으면 빈 검색 상태로 돌아가고 요청하지 않는다.

### 3.3 동명 음악을 아티스트로 좁히기

1. 사용자가 `Love`를 입력한다.
2. 드롭다운에서 `“Love” 음악을 아티스트로 좁히기`를 선택한다.
3. 검색바가 `음악: Love` 칩과 빈 아티스트 입력 상태로 바뀐다.
4. 사용자가 `Lana Del Rey`를 입력한다.
5. 음악 제목이 `Love`로 시작하고 아티스트 이름이 `Lana Del Rey`로 시작하는 결과만 보여준다.

### 3.4 아티스트 안에서 음악 좁히기

1. `아티스트: Radiohead` 상태에서 사용자가 `Creep`을 입력한다.
2. 아티스트 조건과 음악 조건을 함께 요청한다.
3. Radiohead의 음악 중 제목이 `Creep`으로 시작하는 결과만 보여준다.

## 4. 프론트엔드 상태 모델

별도 전역 저장소는 필요하지 않다. 검색바 내부 상태로 충분하다.

```ts
type SearchState =
  | { mode: "all"; input: string }
  | { mode: "artist"; artist: string; input: string }
  | { mode: "music"; music: string; input: string };
```

- `all.input`: 통합 검색어
- `artist.artist`: 확정된 아티스트 조건, `artist.input`: 선택적인 음악 조건
- `music.music`: 확정된 음악 조건, `music.input`: 아티스트 조건. 비어 있으면 요청하지 않는 입력 대기 상태

두 조건을 모두 별도 칩으로 확정하는 네 번째 상태는 만들지 않는다. 첫 조건만 칩으로 고정하고 두 번째 조건은 입력값으로 유지하면 세 경로를 모두 표현할 수 있다.

## 5. 백엔드 API 연동 기준

백엔드는 동일한 엔드포인트에서 아래 조건 조합을 구분하도록 구현됐다.

`GET /api/music/search`

| 경로 | 요청 예시 |
| --- | --- |
| 통합 검색 | `?query=Love&page=0` |
| 아티스트 검색 | `?artist=Radiohead&page=0` |
| 아티스트 안에서 음악 검색 | `?artist=Radiohead&music=Creep&page=0` |
| 음악을 아티스트로 좁히기 | `?music=Love&artist=Lana%20Del%20Rey&page=0` |

요청 규칙:

- `query`는 단독으로만 사용한다.
- 필터 검색에서는 `artist`가 필수이고 `music`은 선택이다. `music` 단독 요청은 400이다. 빈 선택 입력은 파라미터에서 생략한다.
- `query`와 `music`/`artist`를 섞지 않는다.
- 모든 문자열은 앞뒤 공백을 제거한 뒤 URL 인코딩한다.
- 조건이 바뀌면 `page=0`부터 요청한다.
- 페이지 크기는 서버 고정 10이며 프론트가 `size`를 보내지 않는다.

성공 응답의 `data`:

```ts
interface BackendSearchResponse {
  content: MusicSearchResult[];
  page: number;
  size: number;
  hasNext: boolean;
}
```

- `totalElements`와 `totalPages`는 제공되지 않는다.
- 결과 없음은 HTTP 200과 `content: []`이다.
- 잘못된 조건은 400 `INVALID_INPUT`이다.
- 인증 계약은 401이다. 현재 BE의 임시 permitAll로 미인증 거절이 보장되지 않으므로 Core 정책 복구 후 검증한다.
- 내부 실패는 500 `INTERNAL_SERVER_ERROR`이다.

> 확정 계약은 [contracts/music-search.md](contracts/music-search.md)를 따른다. 신규 파라미터는 구현됐지만 아직 `backend/dev` 병합·배포 전이다. FE 연동 배포 시 백엔드 포함 버전을 먼저 확인한다.

### 5.1 배포 FE의 BFF 계약

배포 FE는 브라우저에서 백엔드를 직접 호출하지 않고 `/bff/music/search`를 거친다. 현재 BFF가 `q`를 백엔드의 `query`로 바꾸고 `page`를 전달하므로 통합 검색 경로는 유지한다.

| 화면 → BFF | BFF → Backend |
| --- | --- |
| `?q=Love&page=0` | `?query=Love&page=0` |
| `?artist=Radiohead&page=0` | 같은 `artist`와 `page` 전달 |
| `?music=Love&artist=Lana%20Del%20Rey&page=0` | 같은 `music`, `artist`, `page` 전달 |

BFF는 Backend의 `content`를 기존 FE 타입의 `items`로 바꾼다. 화면과 `JourneyComposer`는 아래 타입을 계속 사용한다.

```ts
interface MusicSearchPage {
  items: MusicSearchResult[];
  page: number;
  hasNext: boolean;
}
```

## 6. 현재 프론트와 달라지는 지점

| 현재 | 변경 요구 |
| --- | --- |
| `useMusicSearchQuery(keyword)` | 조건 객체를 받는 검색 훅 |
| query key가 문자열 하나 | 검색 모드와 `query`/`music`/`artist` 조건을 포함 |
| BFF가 `q`만 받고 Backend `query`로 변환 | 통합 `q` 변환은 유지하고 `music`/`artist` 전달 추가 |
| `useInfiniteQuery`와 `MusicSearchPage.items` 사용 | 그대로 유지하고 조건 변경 시 페이지 누적만 초기화 |
| 단순 입력 한 개 | 칩 1개를 포함할 수 있는 상태 모델 |
| 결과 목록과 다음 페이지 표시 | 기존 페이지 동작을 유지하고 조건 전환 동작 추가 |
| 로딩/빈 결과만 처리 | 요청 실패와 재시도 상태 추가 |
| 입력마다 즉시 요청 | 기존 닉네임 검사와 같은 짧은 디바운스 적용 |
| 목 검색이 부분일치 | 실제 계약과 같이 대소문자 무시 앞일치로 변경 |
| placeholder `곡명 · 아티스트 검색` | `음악 · 아티스트 검색`으로 변경 |

영향 예상 파일:

- `frontend/src/components/layout/search-bar.tsx`
- `frontend/src/components/layout/search-result-list.tsx`
- `frontend/src/components/layout/journey-composer.tsx`
- `frontend/src/hooks/queries/use-music-search-query.ts`
- `frontend/src/constants/query-keys.ts`
- `frontend/src/types/music-detail.ts`
- `frontend/src/app/bff/music/search/route.ts`
- `frontend/src/mocks/music.ts`

`JourneyComposer`도 같은 검색 훅을 사용한다. 지도 검색바의 칩 UI를 넣지 않고 통합 검색 조건만 전달하며, 첫 페이지 관리는 기존 `useInfiniteQuery`에 맡긴다.

## 7. 구현 요구사항

- 화면 → BFF 파라미터 직렬화는 검색 훅 안의 한 함수에서만 처리한다. Backend 파라미터 변환은 BFF 라우트에서만 처리한다.
- 입력 요청에는 짧은 디바운스를 적용하고 이전 요청은 TanStack Query가 새 query key로 구분하도록 한다.
- 통합 검색은 trim한 `query`가 있을 때, 아티스트 검색은 `artist`가 있을 때만 활성화한다.
- 음악 칩 상태에서는 아티스트 입력이 생길 때까지 요청하지 않는다. 요청 시 `music`과 `artist`를 함께 보낸다.
- query key에는 검색 모드와 정규화한 조건 문자열을 포함한다. 페이지는 기존 `useInfiniteQuery`의 `pageParam`으로 관리한다.
- 조건 전환 직후 이전 모드의 결과를 새 조건의 결과처럼 표시하지 않는다.
- 다음 페이지를 이어 붙일 때 음악 ID 기준으로 중복을 제거한다.
- 검색 훅의 반환 타입과 화면 소비 형태는 기존 `MusicSearchPage.items`를 유지한다.
- `isError`일 때 빈 결과 문구를 표시하지 말고 재시도 버튼에서 query의 `refetch`를 호출한다.
- 아티스트 값이 `null`인 음악은 `-`로 표시하는 기존 동작을 유지한다.
- `%`, `_`, `\`를 프론트에서 와일드카드로 해석하지 않는다.
- 결과를 선택한 뒤에는 검색 상태를 초기화하고 기존 지도 이동 동작을 유지한다.
- 키보드로 입력, 조건 전환 동작, 결과 항목, 다음 페이지, 재시도에 접근할 수 있어야 한다.
- 칩 제거 버튼에는 `아티스트 조건 제거` 또는 `음악 조건 제거` 접근성 이름을 제공한다.

### 7.1 권장 구현 순서

1. 기존 `MusicSearchPage`는 유지하고 검색 조건 타입만 추가한다.
2. `QUERY_KEYS.music.search`가 검색 모드와 조건 문자열을 받도록 바꾼다.
3. `useMusicSearchQuery`의 기존 `useInfiniteQuery`를 유지하면서 통합 `q` 또는 `artist(+music)`를 BFF 요청으로 직렬화한다.
4. BFF의 기존 `q → query` 변환을 유지하고 `artist`와 `music` 전달 분기를 추가한다. 목 검색도 같은 조건과 `items/page/hasNext` 응답을 사용한다.
5. `SearchBar`에 세 상태와 조건 전환 칩을 추가한다.
6. `SearchResultList`에 조건 전환, 다음 페이지, 실패·재시도 UI를 추가한다.
7. `JourneyComposer`는 칩 UI 없이 통합 검색 조건만 전달하고 기존 `data.pages.flatMap(page => page.items)`를 유지한다.
8. 검색 결과 선택 시 기존 상세 패널·지도 포커스 동작이 유지되는지 확인한다.

### 7.2 Frontend 검증 항목

- 검색 훅: 세 유효 조합의 URL, `music` 단독 요청 보류, 조건별 query key를 검사한다.
- 검색바: 아티스트 전환, 음악+아티스트 좁히기, 칩 제거, Escape 초기화를 검사한다.
- 결과 목록: 빈 결과, 실패·재시도, `hasNext` 다음 페이지와 ID 중복 제거를 검사한다.
- 회귀: `JourneyComposer`가 통합 검색 첫 페이지 결과로 출발·도착 음악을 계속 선택할 수 있어야 한다.
- 완료 전 `npm run lint`, `npm test`, `npm run build`를 실행한다.

## 8. 인수 조건

1. `Love` 통합 검색 결과가 기존 관련성 순서로 표시된다.
2. `Radiohead`를 아티스트 조건으로 전환하면 Radiohead의 음악만 표시된다.
3. `음악: Love`와 아티스트 `Lana Del Rey`를 함께 사용하면 두 조건을 모두 만족하는 음악만 표시된다.
4. `아티스트: Radiohead` 상태에서 음악 `Creep`을 입력하면 해당 아티스트 안에서 결과가 좁혀진다.
5. 칩 제거 시 첫 페이지 통합 검색으로 돌아간다.
6. 조건 변경 후 이전 조건의 결과가 섞이지 않는다.
7. `hasNext=true`일 때 다음 페이지를 불러오고 중복 ID를 표시하지 않는다.
8. 빈 결과와 서버 오류가 서로 다른 메시지로 표시된다.
9. 결과 선택 시 상세 패널과 지도 포커스 동작이 기존과 동일하다.
10. 화면 문구에서 `곡명`과 `가수`를 사용하지 않고 `음악`과 `아티스트`를 사용한다.

## 10. 협업 체크포인트

- 구현된 `query`/`music`/`artist` 파라미터와 오류 규칙을 기준으로 작업하고, 이후 변경 시 이 문서와 `contracts/music-search.md`를 함께 갱신한다.
- 프론트는 실제 연동 전에 목 라우트도 같은 요청·페이지 응답 형태로 맞춘다.
- 성능 검증은 백엔드가 담당하며, 프론트는 입력마다 중복 요청이 발생하지 않도록 디바운스와 query key를 적용한다.
- SEARCH-01의 지도 포커스 동작은 변경하지 않는다.
- 백엔드 배포 전 환경에서는 신규 파라미터 호출이 동작하지 않으므로 FE 배포 순서를 맞춘다.
