# Feature Specification: 음악 검색

**Feature Branch**: `002-music-search`
**Created**: 2026-09-08
**Updated**: 2026-09-17
**Status**: Approved — 사용자 승인된 통합 검색·아티스트 검색·동명 음악 좁히기 Backend 계약. 실 DB·성능·인증·Frontend 검증 전에는 전체 완료로 판정하지 않는다.

**Input**: 인증된 사용자가 하나의 검색바에서 음악 제목과 아티스트 이름을 검색하고, 필요하면 입력을 아티스트 조건 또는 음악+아티스트 조건으로 전환해 원하는 음악을 찾는다. 기존 검색 응답과 페이지네이션은 유지하며, 검색 범위 확장이 기존 통합 검색의 성능을 후퇴시키지 않아야 한다.

## Clarifications

### Session 2026-09-08

- 최초 결정은 음악 제목·아티스트명 부분일치와 조회수 정렬이었다.
- 운영 데이터에서 전체 스캔과 전체 정렬이 발생해 이후 결정으로 대체됐다.

### Session 2026-09-14

- 검색은 대소문자를 구분하지 않는 앞일치로 제한한다.
- 통합 검색 순서는 음악 제목 완전일치 → 아티스트 완전일치 → 음악 제목 앞일치 → 아티스트 앞일치다.
- 전체 결과 개수는 세지 않고 `hasNext`만 제공한다.

### Session 2026-09-16

- 검색바는 하나만 사용한다. 먼저 확정한 조건은 검색바 안의 칩으로 표시하고, 남은 입력 공간에서 두 번째 조건을 받는다.
- 기본 입력은 음악 제목과 아티스트 이름을 함께 찾는 통합 검색이다.
- 사용자는 현재 입력을 아티스트 조건으로 전환해 해당 아티스트의 음악을 볼 수 있다.
- 사용자는 현재 입력을 음악 조건으로 고정한 뒤 아티스트를 추가해 동명 음악을 좁힐 수 있다.
- 아티스트 후보 목록이나 자동완성은 제공하지 않는다. 사용자가 입력한 문자열을 조건으로 사용한다.
- 사용자 화면에서는 `음악`과 `아티스트`라는 용어를 사용한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 통합 검색으로 음악 찾기 (Priority: P1)

사용자가 검색바에 문자열을 입력하면 음악 제목 또는 아티스트 이름이 일치하는 음악 목록을 볼 수 있다.

**Why this priority**: 기존 검색 경험이며 다른 두 흐름의 시작점이다. 이 동작이 유지되어야 기능 확장으로 인한 회귀가 없다.

**Independent Test**: `Love`를 입력했을 때 제목이 Love로 시작하는 음악과 이름이 Love로 시작하는 아티스트의 음악이 기존 관련성 순서와 페이지 구조로 반환되는지 검증한다.

**Acceptance Scenarios**:

1. **Given** 인증된 사용자가 기본 검색 상태에 있고, **When** `Love`를 입력하면, **Then** 음악 제목 또는 아티스트 이름이 `Love`로 시작하는 음악을 반환한다.
2. **Given** 음악 제목과 아티스트 이름 양쪽에 모두 일치하는 음악이 있고, **When** 통합 검색하면, **Then** 같은 음악은 한 번만 표시된다.
3. **Given** 음악 제목이 완전히 일치하는 결과와 아티스트 이름이 완전히 일치하는 결과가 있고, **When** 결과를 표시하면, **Then** 음악 제목 완전일치가 먼저 나오고 기존 관련성 순서를 유지한다.
4. **Given** 결과가 한 페이지를 넘고, **When** 다음 페이지를 요청하면, **Then** 결과가 중복되거나 누락되지 않고 이어진다.

### User Story 2 - 아티스트의 음악 보기 (Priority: P1)

사용자가 통합 검색 결과의 `‘검색어’를 아티스트로 검색` 동작을 선택하면, 입력이 아티스트 조건 칩으로 바뀌고 해당 아티스트의 음악을 볼 수 있다.

**Why this priority**: 아티스트 이름과 같은 제목의 음악 때문에 아티스트 결과가 뒤로 밀리는 문제를 직접 해결한다.

**Independent Test**: `Radiohead`를 아티스트 조건으로 전환했을 때 Radiohead와 이름이 같은 음악의 존재와 관계없이 Radiohead의 음악을 반환하는지 검증한다.

**Acceptance Scenarios**:

1. **Given** 사용자가 `Radiohead`를 입력했고, **When** `‘Radiohead’를 아티스트로 검색`을 선택하면, **Then** 검색바에 `아티스트: Radiohead` 칩이 표시되고 해당 아티스트 조건에 맞는 음악만 반환한다.
2. **Given** 아티스트 조건이 활성화되어 있고, **When** 남은 입력 공간에 `Creep`을 입력하면, **Then** 해당 아티스트 안에서 제목이 `Creep`으로 시작하는 음악만 반환한다.
3. **Given** 아티스트 조건이 활성화되어 있고, **When** 아티스트 칩을 제거하면, **Then** 기본 통합 검색 상태로 돌아간다.

### User Story 3 - 동명 음악을 아티스트로 좁히기 (Priority: P1)

사용자가 흔한 음악 제목을 검색한 뒤 `아티스트로 좁히기`를 선택하면, 입력한 제목이 음악 조건 칩으로 바뀌고 아티스트를 추가할 수 있다.

**Why this priority**: `Love`처럼 동명의 음악이 많은 경우 원하는 음악이 뒤 페이지로 밀리는 문제를 해결한다.

**Independent Test**: `Love`를 음악 조건으로 고정하고 `Lana Del Rey`를 입력했을 때 두 조건을 모두 만족하는 음악만 반환하는지 검증한다.

**Acceptance Scenarios**:

1. **Given** 사용자가 `Love`를 입력했고, **When** `아티스트로 좁히기`를 선택하면, **Then** 검색바에 `음악: Love` 칩이 표시되고 아티스트 입력 상태가 된다.
2. **Given** `음악: Love` 조건이 활성화되어 있고, **When** `Lana Del Rey`를 입력하면, **Then** 음악 제목과 아티스트 이름이 각각 해당 문자열로 시작하는 음악만 반환한다.
3. **Given** 두 조건을 모두 만족하는 음악이 없고, **When** 검색하면, **Then** 오류가 아닌 빈 결과를 표시한다.
4. **Given** 음악 조건이 활성화되어 있고, **When** 음악 칩을 제거하면, **Then** 남아 있는 문자열을 기본 통합 검색 입력으로 사용할 수 있다.

### User Story 4 - 결과 없음과 요청 실패 구분 (Priority: P2)

호출자는 매칭 결과 없음과 잘못된 요청·인증 실패·내부 실패를 구분할 수 있다.

**Acceptance Scenarios**:

1. **Given** 유효한 검색 조건이지만 매칭 음악이 없고, **When** 검색하면, **Then** 200과 빈 결과를 반환한다.
2. **Given** 검색 조건이 모두 없거나 전달된 조건이 공백이고, **When** 검색하면, **Then** 400 `INVALID_INPUT`을 반환한다.
3. **Given** 페이지 값이 음수 또는 숫자가 아니고, **When** 검색하면, **Then** 400 `INVALID_INPUT`을 반환한다.
4. **Given** 인증이 없거나 유효하지 않고, **When** 검색하면, **Then** 401을 반환한다.
5. **Given** 검색 처리 중 내부 실패가 발생하고, **When** 응답하면, **Then** 500 `INTERNAL_SERVER_ERROR`를 반환한다.

### Edge Cases

| 상황 | 동작 |
| --- | --- |
| 통합 검색어와 아티스트 이름이 동일 | 사용자가 선택한 검색 상태에 따라 통합 결과 또는 아티스트의 음악을 반환 |
| 음악 제목과 아티스트 조건이 모두 완전일치 | 두 조건을 모두 만족하는 결과 중 가장 먼저 표시 |
| 음악 또는 아티스트 조건에 `%`, `_`, `\\` 포함 | 와일드카드가 아닌 문자 그대로 검색 |
| 아티스트 값이 없는 음악 | 통합 검색의 음악 제목 조건에는 포함될 수 있으나 아티스트 조건에는 일치하지 않음 |
| 요청 페이지가 마지막 페이지를 초과 | 빈 결과와 200 반환 |
| 조건 변경 후 이전 페이지가 남아 있음 | 첫 페이지부터 다시 조회 |

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001 — 단일 검색 진입점**: 시스템은 하나의 음악 검색 진입점에서 통합 검색, 아티스트의 음악 보기, 음악+아티스트 동시 조건 검색을 제공해야 한다(MUST).
- **FR-002 — 통합 검색**: 일반 검색어만 있으면 음악 제목 또는 아티스트 이름이 검색어로 시작하는 음악을 반환해야 한다(MUST). 대소문자를 구분하지 않아야 한다(MUST).
- **FR-003 — 아티스트 검색**: 아티스트 조건만 있으면 이름이 해당 조건으로 시작하는 아티스트의 음악만 반환해야 한다(MUST). 완전히 일치하는 아티스트의 음악을 앞일치 아티스트의 음악보다 먼저 반환해야 한다(MUST).
- **FR-004 — 동시 조건 검색**: 음악 조건과 아티스트 조건이 함께 있으면 음악 제목과 아티스트 이름이 각각의 조건으로 시작하는 음악만 반환해야 한다(MUST). 결과 순서는 두 조건 모두 완전일치 → 아티스트 완전일치와 음악 앞일치 → 음악 완전일치와 아티스트 앞일치 → 두 조건 모두 앞일치여야 한다(MUST).
- **FR-005 — 통합 검색 관련성**: 통합 검색 결과는 음악 제목 완전일치 → 아티스트 완전일치 → 음악 제목 앞일치 → 아티스트 앞일치 순이어야 한다(MUST). 같은 순위에서는 음악 ID 오름차순으로 순서를 안정화해야 한다(MUST).
- **FR-006 — 조건 전환**: 사용자는 통합 검색어를 아티스트 조건 또는 음악 조건으로 전환할 수 있어야 하며, 확정한 조건은 제거 가능한 칩으로 식별할 수 있어야 한다(MUST).
- **FR-007 — 빈 결과**: 유효한 요청에 매칭되는 음악이 없으면 오류가 아닌 빈 결과를 반환해야 한다(MUST).
- **FR-008 — 입력 검증**: 검색 조건이 모두 없거나 전달된 조건이 공백이면 요청을 거절해야 한다(MUST). 앞뒤 공백은 무시하고 `%`, `_`, `\\`는 문자 그대로 취급해야 한다(MUST).
- **FR-009 — 페이지네이션**: 페이지 크기는 10으로 고정하고 page, size, hasNext를 제공해야 한다(MUST). 전체 결과 개수와 전체 페이지 수는 제공하지 않아야 한다(MUST NOT).
- **FR-010 — 결과 정보**: 각 결과는 기존 음악 요약 정보와 고정 좌표를 유지해야 하며, 검색이 좌표를 재계산하거나 검색 상태에 따라 응답 항목의 구조를 바꿔서는 안 된다(MUST NOT).
- **FR-011 — 중복 방지**: 하나의 음악이 여러 검색 조건에 일치하더라도 한 페이지에 한 번만 포함되어야 한다(MUST).
- **FR-012 — 기존 통합 검색 호환성**: 일반 검색어만 사용하는 기존 요청의 매칭·정렬·페이지네이션 결과는 기능 확장 전과 동일해야 한다(MUST).
- **FR-013 — 성능 보호**: 아티스트 검색 기능 때문에 기본 통합 검색에 추가 조회가 발생해서는 안 된다(MUST NOT). 아티스트 후보 목록, 자동완성, 전체 개수 계산은 이번 범위에 포함하지 않는다(MUST NOT).
- **FR-014 — 실패 계약**: 검증 실패는 400 `INVALID_INPUT`, 인증 실패는 401, 내부 실패는 500 `INTERNAL_SERVER_ERROR`로 구분해야 한다(MUST).

### Key Entities

- **통합 검색어**: 음악 제목 또는 아티스트 이름에 적용되는 문자열.
- **음악 조건**: 음악 제목에만 적용되는 문자열. 검색바에서는 `음악: {값}` 칩으로 표현된다.
- **아티스트 조건**: 아티스트 이름에만 적용되는 문자열. 검색바에서는 `아티스트: {값}` 칩으로 표현된다.
- **검색 결과**: 음악 ID, 제목, 아티스트, 앨범, 장르, 재생 정보, 고정 좌표를 포함하는 음악 요약 목록.
- **페이지 정보**: 현재 페이지, 고정 페이지 크기, 다음 페이지 존재 여부.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 통합 검색, 아티스트의 음악 보기, 동명 음악 좁히기의 인수 시나리오가 모두 통과한다.
- **SC-002**: `Love`와 `Radiohead` 사례에서 사용자는 두 번 이하의 검색 상태 전환으로 원하는 검색 범위를 지정할 수 있다.
- **SC-003**: 동일한 조건과 페이지를 반복 요청했을 때 결과 순서 차이는 0건이다.
- **SC-004**: 페이지를 이어서 조회했을 때 동일 음악의 중복과 누락은 0건이다.
- **SC-005**: 같은 데이터와 부하 조건에서 기존 통합 검색의 p95 응답 시간은 기능 확장 전 기준보다 10% 이상 나빠지지 않는다.
- **SC-006**: 아티스트 검색과 음악+아티스트 동시 조건 검색의 p95 응답 시간은 300ms 이하를 목표로 하며, 기준을 충족하지 못하면 구현 완료로 판정하지 않고 실행계획과 병목을 기록한다.
- **SC-007**: 검색 실패 로그와 지표에 비밀정보 및 불필요한 개인정보 노출은 0건이다.

## Assumptions

- 검색 대상은 현재 서빙 기준선의 음악 데이터이며 좌표를 재계산하거나 변경하지 않는다.
- 아티스트는 이번 범위에서 독립 엔티티가 아니라 음악에 포함된 이름 문자열이다.
- 아티스트 고유 ID, 별칭 통합, 자동완성, 아티스트 프로필, 별도 아티스트 목록은 범위 밖이다.
- 검색 조건은 앞일치만 지원한다. 단어 중간 일치와 오타 교정은 범위 밖이다.
- 기존 검색의 페이지 크기, 응답 항목, 인증 및 공통 오류 구조를 유지한다.
