### 산출 방식이 바뀐 것은 아니고, 후보를 모으는 방법이 바뀌었다

참조 구현은 660만 곡 전부의 진행도 `p`·축 이탈 `r` 을 계산해 통로를 만들었다. 그럴 필요가 없다 —
직선 위 k번째 지점을 `c_k = A + t_k·(B − A)`, `t_k = k/(n+1)` 라 하면

```text
‖x − c_k‖² = L²·(p − t_k)² + r²
```

**`c_k` 에 가까운 곡이 곧 그 층의 진행도에 있고 축 이탈이 작은 곡**이다. 통로 스캔 대신
HNSW 최근접 질의(`ORDER BY location <-> :ck LIMIT 200`)를 층마다 한 번씩 돌려 같은 후보 집합을 얻는다.

### 반드시 피해야 하는 두 가지 (실측 근거 있음)

1. **질의 벡터를 서브쿼리로 넘기지 않는다.** 실행계획에서 `InitPlan` 으로 들어가 HNSW 가 그 값을 쓰지 못한다.
   2026-09-10 실측 **recall 0.0000** — 자기 자신(거리 0) 대신 거리 23.3 짜리가 1위로 나왔다.
   오류가 아니라 **조용히 틀린 답**이라 더 위험하다. 좌표를 먼저 읽어 바인드 파라미터로 넘기면 recall 0.9995.
2. **후처리 조건을 SQL 에 넣지 않는다.** pgvector 0.7.0 에는 iterative index scan 이 없어
   HNSW 가 `ef_search` 개를 먼저 뽑고 그 뒤에 `WHERE` 를 적용한다. 필터를 걸면 `LIMIT` 보다 적게 돌아온다.
   그래서 후보를 넉넉히(층당 200) 뽑고 앱에서 거른다.

### D10 — 기본 방식이 `axis`(축 통로 + Viterbi)로 바뀌었다

A→B 축을 잡고 전곡에 **진행도 `p`**(A=0, B=1)와 **축 이탈 `r`**(축까지 수직거리)을 매긴다.
통로 = `0 < p < 1` 이고 `r ≤ R` 인 곡. 통로 안에서 진행도 구간(**층**)마다 후보를 뽑고
Viterbi로 비용 최소 열을 고른다. 비용 = `Σ 걸음² + λ·Σ 축이탈²` (λ = 2.0).

실제 번들 40쌍 측정 (`bench_journey_v2.1-pca16.json`, seed 42):

| | **axis** (기본) | linear (구 방식) |
| --- | --- | --- |
| 인접 역 거리 median — p50 | **2.949** | 3.430 |
| 인접 역 거리 median — p95 | **3.788** | 4.600 |
| 지연 p95 | 1.541s | 1.488s |
| 경로 실패 (`unreachable`) | 0 | 0 |
| 규칙 위반 | 0 | 0 |
| **진행도 단조 증가 위반** | **0** | **21 / 40** |
| far 여정 | 30 / 40 | 32 / 40 |

**rev.1이 전제한 등분 보간(`linear`)은 40쌍 중 21쌍에서 진행도가 단조 증가하지 않는다.**
보간 지점마다 독립으로 최근접을 고르므로 다음 지점의 최근접 곡이 앞 역보다 뒤에 있을 수 있다.
`axis`는 층이 진행도 구간으로 나뉘어 구조적으로 단조다. `linear`는 이식 검증·A/B용 모드로 남는다.

## 운영 DB 실측 — 2026-09-12

핸드오프를 믿고 쓰던 것을 실제 운영 DB(`ody`, PG 17.11)에서 확인했다. **두 가지가 문서와 달랐다.**

| 항목 | 결과 |
| --- | --- |
| `music` 행 수 / `location` NULL | 6,624,399 / 0 — 문서와 같음 |
| `music_location_hnsw_idx` | `hnsw (location vector_l2_ops)` — 문서와 같음 |
| 층 후보 질의 인덱스 사용 | **HNSW 탄다** (`Index Scan using music_location_hnsw_idx`) |

### ⚠️ 달랐던 것 1 — `ef_search` 기본값이 `LIMIT` 을 자른다

`hnsw.ef_search` 기본이 **40** 이라 `LIMIT 200` 을 요청해도 **40행만 온다.** HNSW 가 `ef_search` 개를
훑고 멈추기 때문이다. 핸드오프 §3.2 함정 2 는 이것을 "필터를 걸면" 생기는 문제로 적었는데,
**필터가 없어도 `LIMIT` 이 `ef_search` 를 넘으면 같은 일**이 난다. 층당 200을 뽑기로 한 이 기능이 정면으로 해당된다.

`LIMIT` 을 400·800 으로 올려도 여전히 40행이라 **재질의로는 풀리지 않는다**(FR-025 의 재질의 상한이
이 경우엔 헛돈다). 어댑터가 질의 앞에 `SET LOCAL hnsw.ef_search` 를 걸어야 한다.

| `ef_search` | 반환 | 웜 | 콜드 |
| --- | --- | --- | --- |
| 40 (기본) | 40 | 1.2 ms | — |
| 200 | 200 | **4.0 ms** | **350 ms** |

웜 기준 층 20개 × 4ms ≈ **80 ms** 로 종단 3초 예산에 여유가 있다. 핸드오프 §4.8 예상(층 질의 × 14ms)보다 오히려 빠르다.

**콜드 350 ms 가 B-Latency 의 실재 위험이다.** 첫 요청이나 인덱스가 캐시에서 밀린 뒤에 층마다 그만큼 날 수 있다.
최악값은 실부하에서 재측정해야 한다(T047).

### ⚠️ 달랐던 것 2 — 서브쿼리 함정이 재현되지 않았다

핸드오프 §3.2 함정 1 은 질의 벡터를 서브쿼리로 넘기면 `InitPlan` 이 되어 HNSW 를 못 쓰고
**recall 0.0000**(거리 0 인 자기 자신 대신 23.3 짜리가 1위)이 난다고 적었다.

2026-09-12 이 DB 에서는 `InitPlan` 이 뜨는데도 **HNSW 를 정상으로 타고 답도 맞았다** — 1위가 자기 자신,
0.9 ms. 그 사이 PostgreSQL·pgvector 동작이 달라진 것으로 보인다.

**그래도 바인드 파라미터로 넘긴다.** 플래너가 접어 주기를 기대하는 것보다 싸고, 문서가 경고하는 실패 양상이
"오류가 아니라 조용히 틀린 답"이라 되돌아왔을 때 알아채기 어렵다. → BE4 에 문서 정정을 알린다.

### 인덱스 구성이 문서와 다르다

핸드오프는 인덱스 3개(`music_location_hnsw_idx`·`music_l1_gist`·`music_l2_gist`)라고 적었으나 실제는 5개다.
`music_l2_gist` 가 없고 `idx_music_pc1_4`(btree, pc1~pc4 복합)와 `idx_music_vec_1_to_4`(btree, 배열 슬라이스)가 있다.
둘 다 `pc1~pc4` 범위 조회용으로 보이며 **지도 레이어(005·대표곡) 쪽 작업이고 여정과 무관하다** —
여정 질의는 `ORDER BY location <-> :point` 라 HNSW 만 탄다.

## Clarifications

### Session 2026-09-10

- Q: 중간 정거장 등분 수를 어떻게 정하나? → A: **등분 보간 자체가 기본이 아니다.** `axis`가 층을 `n_stations`개로 나누고, `n_stations`는 D3의 `endpoint_dist` 기반 `clamp(10, 20)`으로 정해진다. rev.1의 Q1은 `linear` 모드에만 해당하는 질문이었다. *(BE4 구현으로 해소)*
- Q: 아티스트 반복 억제 규칙은? → A: **총 등장 상한 `artist_cap` = 3**, 값은 `postprocess_rules.json`에서 읽는다(하드코딩 금지). 연속 금지가 아니다. 위반 시 그 아티스트 **전체**에 유한 벌점을 더해 DP를 다시 돌린다 — 행 하나만 막으면 같은 아티스트의 다른 곡을 집어 수렴하지 않는다(BE4 실측). *(BE4 구현으로 해소)*
- Q: detour를 이번 이슈에서 어떻게 다루나? → A: **API 계약에 넣지 않는다.** 통로 반경·λ·층 후보 상한은 BE4 엔진 내부 상수이고, 경로 실패 시 반경을 넓히는 완화 단계도 엔진이 갖고 있다(D3). BE2 게이트웨이는 detour를 알지 못한다. *(BE4 구현으로 해소, 정본 §3.3 파라미터 유지)*
- 결정: 균등성 지표를 rev.1이 제안한 **변동계수에서 BE4가 실제 측정하는 지표로 교체**한다 — 인접 역 거리 median(쌍별)의 p50/p95, `progress_not_monotonic` 건수, `rule_violations` 건수. 지표를 BE2가 새로 정의하면 BE4 벤치마크와 대조할 수 없다.
- 결정: **진행도 단조 증가를 인수 기준으로 승격**한다(FR-020). rev.1에는 없던 요구사항이며, BE4 스펙 11 AC2·D10의 핵심 근거다.
- 결정: 30곡 상한(FR-008)은 **게이트웨이 가드로 남기고 축소 알고리즘은 만들지 않는다.** 엔진이 20을 넘기지 않으므로(D3) 축소 경로는 실행되지 않는다. rev.1의 "30곡 초과 축소 + 도약 재평가"는 엔진 기본값과 맞지 않는 설계였다.

### Session 2026-09-11 — 산출 주체 전환 (rev.3)

**결정 주체**: 사용자 / 팀 (2026-09-11). rev.2 의 전제를 뒤집는 결정이므로 아래를 명시한다.

- 결정: **경로 산출(축 통로 + Viterbi)을 백엔드 프로세스 안에서 직접 수행한다.** 원격 파이썬 엔진을 HTTP 로 호출하지 않는다. 좌표·후보 조회는 저장소의 벡터 근사 인덱스로 한다. → **FR-017 · FR-019 개정**, FR-009·FR-010·FR-011 의 "보장 주체" 이전.
- 결정: 산출 방식은 rev.2 가 적은 `axis`(축 통로 + Viterbi) 그대로다. **방식이 아니라 실행 위치가 바뀐다.** 다만 층 후보를 모으는 방법이 구체화됐다 — "진행도 구간 전수 스캔" 대신 **A→B 직선을 n등분한 지점 `c_k` 에서 근사 이웃을 고정 개수만 뽑아 그 층의 후보로 삼는다**. `‖x − c_k‖² = L²(p − t_k)² + r²` 이므로 `c_k` 최근접은 그 층의 진행도에 있고 축에서 덜 벗어난 곡이다. 전곡 스캔이 필요하지 않다.
- 결정: 역 수는 rev.2 와 같은 식을 따른다 — `L ≤ 10.7` 이면 10, 초과하면 `clamp(round(10 + (L − 10.7)), 10, 20)`. **먼 곡을 거절하지 않고 역만 늘린다.** → FR-011 유지(주체만 이전).
- 결정: 비용 = `Σ 걸음² + 2.0 · Σ 축이탈²`. 걸음² 이 곡 사이 점프를 막고, 축이탈² 이 A→B 방향에서 새는 것을 막는다. λ 는 0.5·1·2 가 같은 경로를 내서 둔감하므로 **2.0 으로 고정**한다.
- 결정: 규칙 위반(같은 녹음 중복 / 아티스트 상한 초과)은 **고쳐서 재산출한다**(상한 있는 반복). 아티스트 위반은 **그 아티스트 전체에 큰 벌점**을 더한다 — 행 하나만 막으면 같은 아티스트의 다른 곡을 집어 수렴하지 않는다(rev.2 가 이미 확인한 사실이며, 이번엔 우리 구현의 의무가 된다).
- 결정: `linear`(지점마다 독립 최근접 1개)는 **폴백·비교용으로만 남긴다.** 진행도가 역행하는 방식이므로 기본 모드가 아니다. → FR-023 의 모드 미노출 유지.
- Q: 임계값(같은 녹음 컷 · 아티스트 상한 · 길이 범위)은 이제 누가 주는가? → A: **좌표계 버전에 귀속된 규칙 정의에서 읽는다.** 산출 주체가 백엔드로 와도 임계값을 애플리케이션 상수로 박지 않는다 — 데이터 파트가 같은 값을 규칙 파일에서 읽고 있어, 박아 놓으면 같은 규칙이 두 벌이 되어 갈라진다. → **FR-024 신설**. 005 주변 탐색의 FR-022 와 같은 요구이며 **로드 경로를 공유해야 한다**. 어떤 형태로 어느 위치에서 읽는지는 데이터 파트·BE4 협의 대상(**D-RULES**, 미해결).
- Q: 산출이 인프로세스가 되면 결정성은 어떻게 보장하나? → A: **후보 집합을 확정하는 단계에서 안정 정렬한다**(거리, 그리고 동률 시 곡 식별자). 근사 이웃 조회는 정확하지 않아 후보 경계가 호출마다 흔들릴 수 있고, DP 가 후보 집합에 의지하므로 그대로 두면 같은 A→B 가 호출마다 다른 경로를 낼 수 있다. PATH-01 은 "플레이리스트 모양이 상품" 이므로 같은 두 곡이면 같은 별자리가 나와야 한다. → **FR-013 개정**(안정 정렬 의무 신설). 005 FR-008 이 같은 요구를 담고 있다.

- Q: `mbid` 경유가 여전히 필요한가? → A: **이번 이슈에서 바꾸지 않는다.** 원격 엔진이 `mbid` 를 쓰기 때문에 든 경계이지만, 인프로세스면 정수 `id` 로 지를 수 있다. 다만 (a) `MusicDetail` 이 이미 둘 다 갖고 있고 (b) 나중에 다시 산출을 원격으로 빼낼 여지를 남기는 것이 싸므로 FR-022 를 유지한다. 식별자를 단일화하는 리팩터링은 별건(**D-ID2**, 기록만).

### User Story 1 - 두 곡 사이의 경로를 받는다 (Priority: P1)

### User Story 2 - 앞으로만 가고 낙차가 고른 경로 (Priority: P1)

### User Story 4 - 실패 원인을 구분해 받는다 (Priority: P2)

호출자는 "없는 곡을 지정했다", "요청이 잘못됐다", "곡은 있으나 경로를 못 만들었다", "서버 쪽 사정으로 못 만들었다"를 구분해 각각 다른 안내를 낼 수 있다.

**Why this priority**: 422(경로 연결 불가)는 이 기능에만 있는 상태다. 404·400·500과 섞이면 프론트가 "다른 곡을 골라보세요"와 "잠시 후 다시"를 구분할 수 없다. 핵심 흐름은 아니라 P2. **rev.3**: 500 의 원인 집합이 바뀌었다 — 원격 엔진 부재·타임아웃 대신 **조회 어댑터 부재·저장소 조회 실패·재산출 상한 소진**이다.

**Acceptance Scenarios**:

1. **Given** `start` 또는 `end`가 존재하지 않는 곡 ID이고, **When** 요청하면, **Then** 404와 `MUSIC_NOT_FOUND`, 공통 실패 구조(`success:false`, `data:null`, `error:{code,message}`)를 반환한다. (FR-003, FR-014)
2. **Given** 엔진이 `reachable:false`를 돌려주고, **When** 응답하면, **Then** 422와 `PATH_NOT_FOUND`("두 곡을 연결하는 경로를 찾을 수 없습니다.")를 반환한다. (FR-002, FR-014)
3. **Given** `start`/`end`가 누락·비정수·0 이하이고, **When** 요청하면, **Then** 400과 `INVALID_INPUT`을 반환한다(산출·조회 없음). (FR-014)
4. **Given** 토큰이 없거나 위조·만료되었고, **When** 요청하면, **Then** 401과 `UNAUTHENTICATED`/`INVALID_TOKEN`을 반환한다. (FR-015, FR-014)
5. **Given** 좌표·후보 조회 어댑터가 없거나 저장소 조회가 실패하고, **When** 응답하면, **Then** 500 `INTERNAL_SERVER_ERROR`로 응답하고 422로 내지 않는다. 부분 경로를 성공으로 내지 않는다. (FR-014, FR-019)
6. **Given** 산출 결과로 정본 계약을 조립할 수 없거나(정거장 상세 누락 등) 재산출 상한 안에 규칙을 지킨 경로를 얻지 못하고, **When** 응답하면, **Then** 500 `INTERNAL_SERVER_ERROR`로 응답한다(부분 경로·규칙 위반 경로 금지). (FR-014, FR-009, FR-025)

### Edge Cases

| 상황 | 동작 |
| --- | --- |
| `start`/`end` 누락·비정수·0 이하 | 400 `INVALID_INPUT` (산출·조회 없음) |
| `start` 또는 `end`가 없는 곡 | 404 `MUSIC_NOT_FOUND` |
| `start == end` | 200, `path` 1개(`step:0`), `musicCnt:1` — 게이트웨이가 처리 |
| `start != end`이나 좌표 동일 | 200, 2곡 경로 (축 길이 0 → 통로 없음) |
| 산출이 경로를 만들지 못함 | 422 `PATH_NOT_FOUND` (D3상 실측 0/40건) |
| 조회 어댑터 부재·저장소 조회 실패 | 500 `INTERNAL_SERVER_ERROR` (422 아님). 부분 경로 금지 |
| 재산출 상한 안에 규칙을 지킨 경로를 못 얻음 | 500 `INTERNAL_SERVER_ERROR` — 규칙 위반 경로를 성공으로 내지 않는다 (rev.3, FR-009·FR-025) |
| 층 후보가 재질의 상한까지 부족 | 그 층을 비우지 않고 있는 후보로 진행. 전 층이 비면 422 (rev.3) |
| `id` → `mbid` 해석 실패 | 404 `MUSIC_NOT_FOUND` |
| 산출 결과로 응답을 조립할 수 없음 | 500 `INTERNAL_SERVER_ERROR` |
| far 여정 (`endpoint_dist > 10.7`) | 정거장 수 자동 증가, 상한 20 |
| 정거장 20개(상한) | `musicCnt` 22 — 정본 상한 30 안, 축소 없음 |
| 경로 중 `youtubeUrl` null | 그대로 포함 (재생 불가 표시는 클라이언트 책임) |
| 경로 전체가 재생 불가 곡 | 그대로 200 (재생 가능 여부로 필터하지 않음) |
| 같은 아티스트가 아티스트 상한 초과 | 아티스트 전체 벌점 후 재산출 (상한 있는 반복, FR-025) |
| 인접 정거장 거리 < 같은 녹음 컷 | 같은 녹음으로 보고 전이에서 배제 |
| 출발·도착과 같은 canonical 곡 | 후보에서 제외 |
| 같은 두 곡 반복 요청 | 동일 곡 목록·동일 순서 (같은 번들 기준) |
| 번들이 v2.1-pca16 → v2.2-pca16으로 교체 | 결과가 달라질 수 있음 — 결정성 보장은 번들 안에서만 |
| 인증 실패 | 401 `UNAUTHENTICATED` / `INVALID_TOKEN` |

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001 — 경로 탐색 조회**: 시스템은 `GET /api/music/journey`에서 `start`·`end` 곡 ID로 두 곡을 잇는 경로를 반환해야 한다(MUST). **근거**: [api-spec §3.3](../../docs/api-spec.md).
- **FR-002 — 경로 연결 불가**: 산출이 경로를 만들지 못하면 422 `PATH_NOT_FOUND`로 응답해야 한다(MUST). **rev.3**: 산출 실패는 **예외가 아니라 "경로 없음" 이라는 결과**로 경계를 넘어야 한다(MUST) — 422 와 500 을 구분해야 하기 때문이다. **근거**: api-spec §0.4·§0.5·§3.3; `journey.py` 반환 계약. **[정정]** `PATH_NOT_FOUND`는 master `MusicErrorCode`에 미등록 → 본 기능에서 BE2 도메인 에러로 정의한다. **[주의]** D3("먼 곡도 항상 잇는다")과 통로 완화 단계 때문에 실측 실패는 40쌍 중 0건이다. 422는 계약상 유지하되 사실상 예외 경로다.
- **FR-003 — 없는 곡**: `start` 또는 `end`가 존재하지 않으면 404 `MUSIC_NOT_FOUND`로 응답해야 한다(MUST). **근거**: api-spec §0.5·§3.3.
- **FR-004 — 경로 원소 필드**: `path`의 각 원소는 `step`과 MusicDetail 필드(id, mbid, title, artist, bpm, duration, album, genres, youtubeUrl, location pc1~pc16, playCnt, youtubeCnt)를 포함해야 한다(MUST). 데이터 엔진은 정거장을 행 인덱스·`mbid`와 `rank`/`dist_from_prev`/`progress`로만 돌려주므로, **나머지 필드는 게이트웨이가 채워야 한다**(MUST). **근거**: api-spec §0.6·§3.3; `journey.py::journey` 반환 형태.
- **FR-005 — 순서와 step**: `path`는 출발곡을 `step:0`으로 시작해 도착곡까지 순서대로 나열해야 하며(MUST), `step`은 최종 목록 기준 0부터 1씩 증가하는 연속값이어야 한다(MUST). 엔진의 `stations`는 **출발·도착을 제외한 중간 정거장만** 담으므로 게이트웨이가 양 끝을 붙이고 번호를 부여한다(MUST). **근거**: api-spec §3.3; `journey.py`(`path[1:-1]`).
- **FR-006 — 집계값**: `musicCnt`는 `path` 길이(= `n_stations` + 2, 단 `start == end`면 1), `totalDuration`은 `path` 모든 곡 `duration`의 합(초)이어야 한다(MUST). **근거**: api-spec §3.3.
- **FR-007 — 재생 불가 곡 포함**: `youtubeUrl`이 null인 곡을 재생 불가만으로 경로에서 제외해서는 안 된다(MUST NOT). **근거**: api-spec §3.3; 요구사항 SONG-04.
- **FR-008 — 30곡 상한 가드**: `path`는 출발곡·도착곡 포함 최대 30곡이어야 한다(MUST). 게이트웨이는 이를 **검증 가드로 확인**하고 초과 시 오류로 처리해야 한다(MUST). **축소 알고리즘을 구현하지 않는다** — 엔진 정거장 수 상한이 20이므로(FR-011) 최대 22곡이고 축소 경로는 실행되지 않는다. **근거**: api-spec §3.3; 요구사항 JOURNEY-01(최대 30곡); D3 clamp(10, 20).
- **FR-009 — 후처리 규칙**: 경로는 다음을 지켜야 한다(MUST) — 출발·도착과 같은 녹음으로 판정되는 곡 제외, 같은 아티스트가 아티스트 상한 이하, 길이 범위 밖·제외 표시된 곡·제목 없는 곡 제외, 인접 정거장 거리가 같은 녹음 임계값 이상. **rev.3: 이 규칙의 보장 주체는 산출을 수행하는 백엔드다**(2026-09-11 결정, FR-017 개정). 위반이 발견되면 **고쳐서 재산출해야 하며**(MUST), 아티스트 상한 위반은 **그 아티스트의 모든 후보에 벌점을 더해** 다시 풀어야 한다(MUST) — 행 하나만 후보에서 빼면 같은 아티스트의 다른 곡을 집어 수렴하지 않는다. 재산출은 **상한 있는 반복**이어야 하고(MUST), 상한 안에 규칙을 지킨 경로를 얻지 못하면 성공으로 응답해서는 안 된다(MUST NOT). 임계값을 애플리케이션 코드에 하드코딩해서는 안 된다(MUST NOT, FR-024). 중복 제거로 중간 정거장이 모두 사라져도 출발·도착 2곡 경로를 200으로 반환해야 한다(MUST). **근거**: 2026-09-11 결정; data 파트 규칙 정의(현재 값 아티스트 상한 3, 같은 녹음 컷 1.6624, 길이 30~1200초); research R10. **[개정]** rev.2 의 "게이트웨이가 재검증하지 않는다"는 산출이 원격일 때만 성립했다.
- **FR-010 — 낙차 균등성 지표**: 경로 품질 지표는 **쌍별 인접 역 거리 median의 p50/p95, 진행도 단조 위반 건수, 규칙 위반 건수, 경로 실패 건수**다. 지표식은 데이터 파트 벤치마크가 정의한 것을 그대로 쓰고 새로 정의하지 않는다(MUST NOT) — 지표를 새로 정의하면 데이터 파트 수치와 대조할 수 없다. 데이터 파트 기준선: `axis` median p50 2.949 / p95 3.788, 위반 0건(40쌍); `linear` 는 같은 40쌍에서 단조 위반 21건. **rev.3: 산출이 인프로세스가 됐으므로 이 지표의 측정 주체도 백엔드다** — 단, **운영 요청 경로에서 인접 거리 median 을 계산하지 않는다**(MUST NOT). 요청마다 품질 지표를 재계산할 이유가 없다. 측정은 **합성 좌표 또는 실제 번들로 도는 별도 검증 경로**에서 하고(MUST), 운영 경로에는 진행도 단조 위반 카운터와 산출 구간 지연만 남긴다(MUST, FR-020). 어느 지표든 응답 본문에 노출하지 않는다(MUST NOT, 정본 §3.3에 해당 필드 없음). 합격 임계값은 데이터 파트와 합의 대상이다(B-Metric). **근거**: 2026-09-11 결정; 데이터 파트 벤치마크 기준선; research R10; 헌법 VIII.
- **FR-011 — 정거장 수와 산출 방식**: 경로 산출은 **기본 모드 `axis`**(축 통로 + Viterbi, D10)를 사용해야 한다(MUST). 정거장 수는 두 곡 사이 거리 `L ≤ 10.7`이면 10, 초과하면 `clamp(round(10 + (L − 10.7)), 10, 20)`이어야 한다(MUST, D3) — 먼 곡을 거절하지 않고 역만 늘린다(MUST NOT 거절). 층 후보 개수·비용 가중치 λ(2.0)·후보 부족 시 재질의 상한·규칙 재산출 상한은 **산출 내부 파라미터이며 API 계약에 넣거나 클라이언트에 노출하지 않는다**(MUST NOT). **rev.3: 이 파라미터의 소유자는 산출을 수행하는 백엔드로 바뀌었다** — 다만 `detour` 를 포함해 어떤 산출 파라미터도 요청 파라미터로 승격하지 않는다(MUST NOT, FR-023). **근거**: D3, D10; 2026-09-11 결정.
- **FR-012 — 경계 입력**: `start == end`이면 엔진을 호출하지 않고 200과 `path` 1개(해당 곡, `step:0`), `musicCnt:1`을 반환해야 한다(MUST). `start != end`이면서 좌표가 동일하면 축 길이가 0이라 통로가 성립하지 않으므로 두 곡만 포함한 2곡 경로를 200으로 반환해야 한다(MUST). **근거**: api-spec §3.3; `journey.py::axis_frame`(`length == 0.0` 분기).
- **FR-013 — 결정성**: 같은 `start`·`end`·같은 번들·같은 모드에서 반복 요청하면 동일한 곡 목록과 동일한 순서를 반환해야 한다(MUST). 산출 로직에 기록되지 않은 무작위성을 도입해서는 안 된다(MUST NOT). **번들 버전이 바뀌면 결과가 달라질 수 있으며 결정성 보장은 번들 안에서만 성립한다.** **rev.3 — 근사 후보에 대한 안정화 의무**: 층 후보를 **근사 최근접**으로 모으는 경우, 후보 집합을 확정하는 단계에서 **거리와 곡 식별자를 모두 기준으로 안정 정렬해야 한다**(MUST). 근사 조회는 정확하지 않아 후보 경계가 호출마다 흔들릴 수 있고, 경로 선택이 후보 집합에 의지하므로 안정화 없이는 같은 두 곡이 호출마다 다른 경로를 낸다. 동률 거리에서 순서를 미정의로 남겨서는 안 된다(MUST NOT). **근거**: 헌법 IV·V·VI; 2026-09-11 결정; PATH-01(경로 모양 자체가 산출물); 005 FR-008 과 동일 요구.
- **FR-014 — 오류 구조**: 검증 실패는 400 `INVALID_INPUT`, 없는 곡·식별자 해석 실패는 404 `MUSIC_NOT_FOUND`, 경로 불가는 422 `PATH_NOT_FOUND`, 인증 실패는 401 `UNAUTHENTICATED`/`INVALID_TOKEN`, **조회 어댑터 부재·저장소 조회 실패·응답 조립 불가·재산출 상한 소진·그 밖의 내부 실패는 500 `INTERNAL_SERVER_ERROR`** 로 응답하고(rev.3), 실패 본문은 `success:false`, `data:null`, `error:{code,message}`(master `ErrorResponse`)여야 한다(MUST). 부분 경로를 성공으로 응답해서는 안 된다(MUST NOT). **서버 쪽 사정을 422와 섞어서는 안 된다**(MUST NOT) — 사용자가 곡을 바꿔 해결할 수 있는 실패가 아니다. 새 에러 코드나 503을 정본 §0.5에 추가하지 않는다(2026-09-10 clarify); 500 하위 원인의 구분은 로그·지표로만 한다(MUST). **근거**: 2026-09-10 clarify; master `common.GlobalErrorCode`/`AuthErrorCode`/`MusicErrorCode`/`GlobalExceptionHandler`; api-spec §0.2·§0.4·§0.5.
- **FR-015 — 인증**: `Authorization: Bearer {accessToken}` 인증을 요구해야 한다(MUST). master `SecurityConfig`는 기본 거부(`anyRequest().authenticated()`)이므로 `/api/music/journey`는 별도 조치 없이 인증 대상이다. **근거**: api-spec §0.1·§0.7·§3.3; master `SecurityConfig`(S15P21A405-33).
- **FR-016 — 고정 좌표**: 경로 곡의 좌표는 서빙 번들(`v2.1-pca16`, PCA-16, D7) 기준으로 진입 경로와 무관하게 동일해야 하며(MUST), 경로 생성이 좌표·모델을 변경해서는 안 된다(MUST NOT). 서빙·요청 경로에서 차원 축소 모델을 재학습해서는 안 된다(MUST NOT). **근거**: 헌법 V·VII; D7.
- **FR-017 — 아키텍처 경계 [rev.3 개정]**: 경로 산출(축 통로·Viterbi·후처리 재산출)은 **백엔드 프로세스 안에서 수행해야 한다**(MUST). 산출을 위해 외부 산출 서비스를 HTTP 로 호출해서는 안 된다(MUST NOT). 좌표와 층 후보는 저장소의 벡터 근사 인덱스 조회로 얻어야 한다(MUST). BE2는 정본 계약 준수, 입력 검증, 식별자 해석, **경로 산출**, 응답 조립, 오류 매핑을 모두 소유한다(MUST). **근거**: **2026-09-11 팀 결정**; 헌법 X.

- **FR-021 — 정거장 범위 매핑**: 엔진의 `n_stations`는 **중간 정거장 수**이고 `stations`에는 출발·도착이 없다. 게이트웨이는 이를 정본의 `path`(출발·도착 포함)·`musicCnt`(전체 곡 수)로 변환해야 한다(MUST). 두 수를 혼용해서는 안 된다(MUST NOT). **근거**: `journey.py`(`path[1:-1]`); api-spec §3.3.
- **FR-022 — 식별자 해석**: 정본 계약은 `start`·`end`를 정수 `id`로 받지만 데이터 엔진과 data 소유 스키마는 `mbid`(text UUID)를 식별자로 쓴다. 게이트웨이는 `id ↔ mbid` 해석을 담당해야 한다(MUST). **BE 소유 곡 테이블이 정수 `id` PK와 `mbid` UNIQUE를 함께 갖는 것을 매핑 원천으로 한다**(2026-09-10 clarify). 따라서 정본 §3.3·§0.6의 정수 `id` 계약과 프론트는 바뀌지 않고(MUST), 엔진에 `id`를 받게 요청하지도 않는다(MUST NOT). 요청 경로에서 `start`·`end`를 `mbid`로 해석하고, 응답 조립에서 엔진 정거장의 `mbid`를 `id`로 역매핑해야 한다(MUST). 해석 실패(해당 `id` 없음 / `mbid` 없음)는 FR-003의 404로 처리해야 한다(MUST). **근거**: 2026-09-10 clarify; api-spec §0.6; master `MusicDetail`(id·mbid 동시 보유)·`MusicDetailReader.findDetail(long id)`; data 스펙 50(`track.mbid` PK). **[신규]**

### Key Entities *(include if feature involves data)*

- **경로 요청**: `start`(1 이상 정수, 출발곡 ID), `end`(1 이상 정수, 도착곡 ID).
- **경로(Journey Path)**: 순서 있는 정거장 목록. 출발곡 `step:0` ~ 도착곡. 길이 1~22(계약 상한 30). 집계값 `musicCnt`, `totalDuration`(초).
- **정거장(Stop)**: `step`(0-based) + MusicDetail(id, mbid, title, artist, bpm, duration, album, genres, youtubeUrl, location pc1~pc16, playCnt, youtubeCnt). 좌표는 번들 `v2.1-pca16` 고정.
- **산출 정거장(Station)**: 식별자 + `dist_from_prev`, `progress`. 출발·도착 제외. 내부 표현이며 응답에 그대로 나가지 않는다. **rev.3**: 원격 엔진 응답이 아니라 **인프로세스 산출 결과**다.
- **산출 메타**: `mode`, `endpointDist`, `far`, `reachable`, `bundle`. 응답에 싣지 않고 관측 지표·로그로만 쓴다(FR-023). 예외적으로 `reachable` 은 422 판정에 쓰인다. **rev.3**: `bundle`(좌표 아티팩트 버전)은 원격 엔진이 응답에 담아 주던 값이므로 **인프로세스에서는 어디서 읽을지 새로 정해야 한다** — FR-024 의 규칙 정의 로딩과 같은 문제다(D-RULES).
- **층(Layer)**: A→B 직선의 k번째 등분 지점 `c_k` 와 그 지점 근사 이웃으로 모은 후보 집합. 후보는 확정 전 안정 정렬된다(FR-013).
- **후처리 규칙(Rules)**: 같은 녹음 컷, 아티스트 상한, 길이 범위, 원거리 임계값. **좌표계 버전에 귀속된 규칙 정의가 정본이며 코드에 박지 않는다**(FR-024).
- **낙차 균등성 지표**: 인접 역 거리 median p50/p95, 단조 위반 건수, 규칙 위반 건수. 응답에 포함하지 않는 내부 측정값.

- **SC-009**: 실패 요청(400/401/404/422/500)을 코드별로 로그·지표에서 구분해 추적할 수 있다. **rev.3**: 500 의 하위 구분이 바뀐다 — "엔진 부재·타임아웃" 분기가 사라지고, **조회 어댑터 부재 / 저장소 조회 실패 / 상한 안에 규칙을 지킨 경로를 얻지 못함 / 그 밖의 내부 실패**를 지표로 구분한다. 산출 메타(`far`, `endpointDist`, `mode`, `bundle`)가 관측 지표·로그에 남고 응답 본문에는 0건 노출된다. 로그·지표에 비밀정보·불필요한 개인정보 노출은 0건이다. **근거**: 헌법 VIII; FR-014, FR-023; 요구사항 §6.

## Assumptions

- **기준 인프라 = master 통합본**: backend/ 단일 Gradle 프로젝트, 공통 레이어 `common.ApiResponse`/`ErrorCode`/`GlobalErrorCode`/`AuthErrorCode`/`MusicErrorCode`/`CustomException`/`GlobalExceptionHandler`, MyBatis + Postgres(+Neo4j/Redis).
- **rev.3: BE2 가 산출까지 소유한다**(2026-09-11 결정, FR-017). rev.2 의 "BE2 = 게이트웨이, BE4 = 엔진"(D4) 가정은 여정 산출에 관해 폐기됐다. 알고리즘 *방식*(모드 기본값, λ, 역 수 식, 완화 단계)은 데이터 파트가 정의한 것을 따르고 새로 설계하지 않으며, 임계값은 규칙 정의에서 읽는다(FR-024).
- **경로 산출 방식은 `axis`가 기본**(D10)이고 `linear`는 남아 있는 모드다. 정본 §3.3 본문("출발→도착 벡터를 등분한 각 지점에서 최근접 곡 선택")은 `linear`를 서술한 것이며 현재 기본 동작과 다르다 → 정본 갱신 필요(아래 알림).
- **인증은 블로커가 아니다**: 003이 남긴 B-A는 master `SecurityConfig` 기본 거부 전환(S15P21A405-33)과 `AuthErrorCode`로 해소됐다.
- 후처리 임계값은 **좌표계 버전에 귀속된 규칙 정의**가 정본이다(데이터 파트 `postprocess_rules.json`, 현재 `serving/v2.1-pca16/`). 값을 spec·코드에 고정하지 않는다(FR-024). **rev.3: 그 정의가 이 저장소에 없다** — `data/` 트리가 이 저장소에 없고, 백엔드가 어떻게 읽을지는 미결이다(D-RULES).
- 서빙 번들은 현재 `v2.1-pca16`이다. data 스펙 10 예시에 `v2.2-pca16`이 보이고 D1이 `serving/v2.2-pca16` 재적재를 예고하므로, 번들 교체 시 경로 결과와 지표 기준선이 함께 바뀐다고 본다.
- `PATH_NOT_FOUND`(422)는 정본 §0.5에 있으나 master 코드에 없다. 여정 도메인 에러는 BE2 소유이므로 본 기능에서 정의할 수 있고 타 팀 블로커가 아니다(003의 `MUSIC_NOT_FOUND` 선례).
- 엔진의 `far`·`endpoint_dist`·`mode`·`n_stations`·`last_to_end`·`rules`·`bundle`은 정본 §3.3 응답에 대응 필드가 없어 싣지 않는다(2026-09-10 clarify). 관측 지표·로그로만 남기고, 계약 추가가 필요해지면 별자리 뷰(-62)에서 FE1과 정한다(헌법 II).
- 프론트는 여정 곡 수를 고정값으로 가정하지 않는다고 본다. far 여정이 다수(실측 40쌍 중 30쌍)라 `musicCnt`가 12~22로 변동한다.
- 여정 이력 저장·조회(-64), 별자리 시각화(-62), 순차 재생(-63), 프론트 출발·도착 지정 UI, 주변 탐색(-59, data 스펙 10)은 범위 밖이다.
- **rev.3: 좌표 이웃 조회를 여정 산출이 직접 쓴다.** rev.2 는 "여정을 SQL로 옮기는 것은 스펙 17의 비범위이고 여정은 Python 엔진에 남는다"고 적었으나, 2026-09-11 결정이 이를 바꿨다. 층 후보 조회가 벡터 근사 인덱스를 쓰고, 선정(DP·규칙)은 애플리케이션에서 한다 — **여정 전체를 SQL로 옮기는 것이 아니다**.
- **rev.3: 근사 이웃 조회의 성질을 전제한다**(주변 탐색 005 가 같은 전제 위에 있다). (a) 후보를 필요한 개수보다 넉넉히 뽑는다 — 후처리가 중복·도배를 쳐내므로 상위 몇 개만 뽑으면 모자란다. (b) **필터를 조회에 넣으면 요청보다 적게 돌아올 수 있다** — 필터는 애플리케이션에서 건다. (c) **기준점을 조회 안에서 계산해 넘기면 근사 인덱스가 쓰이지 않는다** — 조회는 조용히 틀린 결과를 내므로, 지점 좌표 `c_k` 는 미리 계산해 값으로 바인딩한다. 이 세 가지는 조회 방식의 함정이며 계약이 아니라 구현 제약이다.
