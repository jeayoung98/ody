# Feature Specification: 별자리 배치 (musicIds → 2D 고정 좌표)

**Feature Branch**: `backend/feat/S15P21A405-265-constellation-layout-api`

**Jira**: S15P21A405-265

**Created**: 2026-09-13

**Status**: Draft — origin/backend/dev · origin/frontend/dev 기준

**Input**: 별자리 배치 API(BACKEND-NOTES A-9)가 없어 프론트가 목으로 계산 중이다. 지금은 프론트가 자기가 아는 16차원 좌표를 요청 본문에 실어 우회한다. 여러 사용자가 같은 플레이리스트를 **같은 모양**으로 보려면 서버가 `musicIds` → 2D 고정 좌표를 내려줘야 한다. 함께: 플레이리스트 별자리에도 좌표가 실려야 한다.

## 현재 상태 (코드 확인, 2026-09-13)

| 확인한 것 | 위치 | 상태 |
| --- | --- | --- |
| 배치 계산이 프론트 목이다 | `frontend/src/mocks/constellation.ts` (공분산 상위 2축 거듭제곱 반복) | 목 |
| 목 라우트가 요청 본문의 16차원 좌표를 받는다 | `frontend/src/app/api/constellations/layout/route.ts`, `use-constellation-layout-query.ts` | 우회 중 |
| 프론트 계약 타입은 이미 확정형이다 | `frontend/src/types/constellation.ts` (`{musicId, x, y}`, `-1~1`) | 그대로 사용 가능 |
| 백엔드에 배치 엔드포인트가 없다 | `backend/.../music/controller/` | 없음 |
| 곡 좌표 원천이 있다 | `music.location vector(16)`, `MusicDetailMapper.xml` 의 `locationColumns` | 있음 |
| **플레이리스트 상세 응답에 좌표가 이미 실려 있다** | `PlaylistDetailResponse.musics` = `List<MusicDetail>` → `MusicDetail.location` (pc1~pc16) | **이미 충족** |
| 다만 그 조립이 곡당 1회 조회다 | `PlaylistService.loadMusicDetails` — musicIds 를 돌며 `findDetail` 호출 (N+1) | 개선 필요 |

즉 **"플리 실데이터로 붙으면 좌표를 실어 보내야 한다"는 요구는 백엔드에서 이미 충족돼 있다.** 프론트가 보는 목(`mockPlaylists`)이 좌표를 안 실을 뿐이다. 남은 백엔드 작업은 (a) 배치 API 신설, (b) 플레이리스트 상세의 N+1 제거다.

## Clarifications

### Session 2026-09-13

- Q: 요청 본문에 좌표(`points`)를 계속 받을까? → A: **받지 않는다.** 좌표 원천은 서버의 서빙 baseline(`v2.1-pca16`) 하나여야 같은 곡 집합이 누구에게나 같은 모양으로 보인다. 본문에 좌표가 와도 무시한다(헌법 V 좌표 안정성).
- Q: 요청한 `musicId` 중 없는 곡이 있으면? → A: **전건 실패(404)**. 일부만으로 배치를 만들면 모양이 조용히 달라진다 — 003-music-detail 의 "부분 결과를 성공으로 내지 않는다" 와 같은 결정.
- Q: 곡이 1개 이하이면? → A: **400**. 두 점이 있어야 모양이 성립한다. 프론트도 이미 `musicIds.length >= 2` 에서만 호출한다.
- Q: 플레이리스트 곡이 30개를 넘으면? → A: **상한 30 유지, 400.** A-9 문서값을 그대로 쓴다. 지금 프론트 플레이리스트 패널이 곡 수 제한 없이 전부 보내고 있어(`playlist-panel.tsx` — `items.map(...)`, 상한 없음) **31곡 이상 플리는 별자리가 뜨지 않는다.** 프론트가 30곡으로 잘라 보내도록 고쳐야 한다 — FE 작업이며 아래 "상대 파트에 알려야 할 점" 참조.
- Q: 배치 API 의 응답 속도 목표는? → A: **요구사항 §6 의 "유사곡 검색 응답 1초" 를 준용한다.** 배치 전용 목표는 팀 문서에 없고, 지어낸 수치를 인수 기준으로 삼지 않는다(헌법 IX). **실측 후 변경 가능한 잠정 기준**이다 — 첫 측정값이 나오면 그것을 근거로 다시 정한다. §6 자체가 백분위·부하·측정 환경을 미정으로 두고 있다.
- Q: 플레이리스트 상세의 N+1 을 이번 작업에서 고쳐도 되나(`playlist/` 는 BE1 소유)? → A: **된다.** 이번 이슈 범위로 진행한다. 다만 `music/` 변경과 **커밋을 분리해** 리뷰·되돌리기가 독립적이게 한다.
- 결정: 경로는 A-9 문서와 프론트 상수를 그대로 따라 `POST /api/constellations/layout` 으로 낸다. 백엔드 다른 도메인이 단수 접두사(`/api/music`, `/api/playlist`)를 쓰는 것과 어긋나지만 표기 문제이며, FE 상수가 이미 이 경로다(S15P21A405-213·214 와 함께 정리 대상).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 같은 곡 집합은 누구에게나 같은 모양 (Priority: P1)

두 사용자가 같은 플레이리스트(또는 같은 여정 경로)의 별자리를 열면, 서로 다른 기기·다른 진입 경로·다른 레이어에서도 **같은 모양**을 본다.

**Why this priority**: "플리 모양이 상품이 된다"는 기획이 성립하려면 모양이 고정·재현 가능해야 한다. 이 스토리 하나만 되면 별자리 오버레이는 제 값을 한다.

**Independent Test**: 같은 `musicIds` 로 두 번 호출해 좌표가 완전히 동일한지, 순서를 섞어 호출해도 같은 모양인지 검증한다.

**Acceptance Scenarios**:

1. **Given** 존재하는 곡 10개, **When** 같은 집합으로 두 번 호출하면, **Then** 두 응답의 `points` 가 `musicId` 별로 완전히 동일한 `x`·`y` 를 갖는다. (FR-004)
2. **Given** 같은 곡 10개를 순서만 바꿔 보내고, **When** 호출하면, **Then** 각 `musicId` 의 `x`·`y` 가 앞 호출과 같다(응답 항목의 나열 순서만 요청 순서를 따른다). (FR-005, FR-009)
3. **Given** 요청 본문에 임의의 16차원 좌표를 함께 실어 보내고, **When** 호출하면, **Then** 응답은 그것을 싣지 않은 호출과 동일하다. (FR-003)
4. **Given** 어떤 곡 집합, **When** 응답을 받으면, **Then** 모든 `x`·`y` 가 `-1` 이상 `1` 이하이고, 적어도 한 점은 한 축에서 절댓값 1 에 닿는다(화면을 꽉 채운다). (FR-007)

### User Story 2 - 플레이리스트 별자리 (Priority: P2)

사용자가 자기 플레이리스트를 열면 그 곡들로 만든 별자리를 본다. 플레이리스트 상세 응답의 곡들은 별자리·지도가 쓸 좌표를 함께 갖는다.

**Why this priority**: P1 이 되면 플레이리스트 별자리는 "상세에서 `musicIds` 를 꺼내 배치 API 를 부른다"로 끝난다. 백엔드 쪽 좌표 전달은 이미 돼 있고 남은 것은 성능이다.

**Independent Test**: 30곡 플레이리스트 상세를 조회해 (a) 모든 곡에 16차원 좌표가 실려 오는지, (b) 곡 조회 왕복이 1회인지 검증한다.

**Acceptance Scenarios**:

1. **Given** 곡 30개가 담긴 플레이리스트, **When** 상세를 조회하면, **Then** 모든 곡에 좌표(pc1~pc16)가 실려 온다. (FR-010)
2. **Given** 곡 30개가 담긴 플레이리스트, **When** 상세를 조회하면, **Then** 곡 정보 조회가 **1회의 일괄 조회**로 끝난다(곡당 1회 아님). (FR-011)
3. **Given** 플레이리스트에 저장된 곡 순서, **When** 상세를 조회하면, **Then** `musics` 가 그 순서(`position`)를 유지한다. (FR-012)

### User Story 3 - 모양을 만들 수 없는 요청 (Priority: P2)

호출자는 "모양을 만들 수 없는 요청"과 "서버 오류"를 구분할 수 있다.

**Why this priority**: 배치 실패를 500 으로 뭉뚱그리면 프론트가 오버레이를 계속 재시도한다. 핵심 흐름은 아니라 P2.

**Acceptance Scenarios**:

1. **Given** `musicIds` 가 비었거나 1개, **When** 호출하면, **Then** 400 과 `INVALID_INPUT`. (FR-013)
2. **Given** `musicIds` 가 30개를 넘고, **When** 호출하면, **Then** 400 과 `INVALID_INPUT`. (FR-013)
3. **Given** `musicIds` 에 같은 값이 두 번 있고, **When** 호출하면, **Then** 400 과 `INVALID_INPUT`(조용히 합치지 않는다). (FR-013)
4. **Given** `musicIds` 중 하나라도 존재하지 않고, **When** 호출하면, **Then** 404 와 `MUSIC_NOT_FOUND` 를 반환하며, 있는 곡만으로 만든 부분 배치를 200 으로 내지 않는다. (FR-014)
5. **Given** 인증 토큰이 없거나 만료됐고, **When** 호출하면, **Then** 401. (FR-015)

### Edge Cases

- **모든 곡의 좌표가 같다(또는 거의 같다)**: 퍼뜨릴 방향이 없다 → 모든 점을 `(0, 0)` 으로 내리고 200. 0 으로 나누지 않는다. (FR-008)
- **곡들이 한 직선 위에 있다**: 두 번째 축의 분산이 0 이다 → 그 축 좌표를 모두 0 으로 두고 첫 축만으로 배치한다(오류 아님).
- **좌표 부호가 뒤집힌 모양**: 주축의 부호는 수학적으로 임의다. 부호 규약을 고정하지 않으면 같은 집합이 좌우·상하로 뒤집혀 나올 수 있다 → 결정적 부호 규약이 필요하다. (FR-006)
- **곡 좌표가 NULL 인 행**: 적재상 `location` 은 전 행 채워져 있으나, NULL 이면 "없는 곡"과 같이 404 로 다룬다(조용히 0 벡터로 채우지 않는다).
- **곡이 정확히 2개**: 두 점만으로도 배치는 성립한다 — 한 축 위의 `-1`, `1` 두 점.
- **31곡 이상인 플레이리스트**: 400 이다. 서버가 앞 30곡만 골라 배치하지 않는다 — 어느 30곡인지 서버가 정하면 사용자가 모르는 기준으로 곡이 빠진다. **자를 곳은 프론트다.**

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 곡 id 목록을 받아 각 곡의 2D 배치 좌표를 반환해야 한다 — `{ points: [{ musicId, x, y }] }`.
- **FR-002**: 배치 좌표의 원천은 서빙 baseline(`v2.1-pca16`)의 곡 16차원 좌표여야 한다.
- **FR-003**: 요청자가 보낸 좌표는 배치에 쓰지 않는다. 본문에 실려 와도 결과가 달라지지 않아야 한다.
- **FR-004**: 같은 곡 집합에 대한 반복 호출은 완전히 동일한 좌표를 반환해야 한다(결정성).
- **FR-005**: 결과는 요청의 **곡 순서에 의존하지 않아야** 한다.
- **FR-006**: 축의 방향(부호)은 곡 집합만으로 정해지는 규약을 따라야 한다 — 같은 집합이 뒤집힌 모양으로 나오지 않아야 한다.
- **FR-007**: 좌표는 `x`·`y` 에 **같은 배율**을 적용해 최대 절댓값이 1 이 되도록 정규화해야 한다(축별로 따로 늘리면 모양이 찌그러진다).
- **FR-008**: 퍼뜨릴 방향이 없는 집합(모든 좌표가 동일)은 오류 없이 모든 점을 `(0, 0)` 으로 반환해야 한다.
- **FR-009**: 응답 `points` 의 나열 순서는 요청 `musicIds` 의 순서를 따라야 한다.
- **FR-010**: 플레이리스트 상세 응답의 각 곡은 16차원 좌표를 포함해야 한다(현행 유지).
- **FR-011**: 플레이리스트 상세의 곡 정보 조회는 곡 수와 무관하게 **1회의 일괄 조회**여야 한다.
- **FR-012**: 플레이리스트 상세의 곡 순서는 저장된 순서를 유지해야 한다(일괄 조회는 순서를 보장하지 않으므로 호출자가 재조립한다).
- **FR-013**: 곡이 2개 미만, 30개 초과, 중복 포함이면 400 `INVALID_INPUT` 을 반환해야 한다.
- **FR-014**: 요청한 곡 중 하나라도 없으면 404 `MUSIC_NOT_FOUND` 를 반환해야 하며, 부분 배치를 성공으로 반환해서는 안 된다.
- **FR-015**: 인증되지 않은 요청은 401 이어야 한다(다른 음악 API 와 같은 규칙).
- **FR-016**: 배치는 부수효과가 없어야 한다(조회 전용).
- **FR-017**: 배치는 레이어와 무관해야 한다 — 요청에 레이어를 받지 않고, 레이어가 달라도 같은 모양을 반환한다.

### Key Entities

- **곡 좌표(Location)**: 곡 1개의 16차원 서빙 좌표. 원천은 `music.location`, 버전은 `v2.1-pca16`.
- **배치 점(ConstellationPoint)**: 곡 1개의 화면 좌표 `{ musicId, x, y }`. `x`·`y` 는 `-1 ~ 1`, `y` 는 위가 양수.
- **배치(ConstellationLayout)**: 요청한 곡 집합 전체의 배치 점 목록. 곡 집합이 같으면 같다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 같은 플레이리스트를 서로 다른 두 계정이 열었을 때 보이는 별자리 모양이 육안·수치 모두 동일하다(좌표 완전 일치).
- **SC-002**: 30곡 배치 요청이 **1초** 안에 응답한다 — 요구사항 §6 의 확정 목표 "유사곡 검색 응답 1초" 를 준용한다(별자리도 사용자가 목록을 열면 바로 떠야 하는 화면 요소다). **잠정 기준이며 실측 후 조정할 수 있다** — 백분위·부하·측정 환경이 §6 에서 미정이므로, 첫 실측값을 근거로 더 빡빡한 값으로 다시 정한다.
- **SC-003**: 30곡 배치 1건이 곡 좌표 조회를 위해 DB 를 1회만 왕복한다.
- **SC-004**: 30곡 플레이리스트 상세 조회가 곡 조회를 위해 DB 를 1회만 왕복한다(현행 30회에서 감소).
- **SC-005**: 프론트가 요청 본문에서 좌표를 빼도 화면의 별자리 모양이 달라지지 않는다 — 우회를 제거할 수 있음이 확인된다.
- **SC-006**: 잘못된 요청(개수·중복·없는 곡)이 500 으로 떨어지지 않는다 — 전부 400/404 로 구분된다.

## Assumptions

- 곡 상한 30개는 A-9 문서값을 그대로 쓴다. 여정 경로(최대 정거장 20)는 이 안에 들어오지만, **플레이리스트는 곡 수 상한이 없어 넘을 수 있다** — 프론트가 30곡으로 잘라 보내는 것을 전제한다.
- 인증 규칙은 다른 음악 API 와 같다(Bearer). 배치 결과는 사용자별로 달라지지 않으므로 사용자 식별은 쓰지 않는다.
- 응답 좌표의 소수 자릿수는 제한하지 않는다. 프론트가 화면 배율로 다시 곱하므로 반올림은 프론트 책임이다.
- 배치 방식은 "그 곡 집합만의 분산이 가장 큰 두 방향으로 투영"이다(프론트 목과 같은 계열). 곡 집합이 바뀌면 축도 바뀌는 것이 정상이다 — 부분집합이 전체집합 모양의 일부와 같을 필요는 없다.
- 모양의 저장·공유·거래(A-9 비고)는 이번 범위가 아니다. 이번 API 는 stateless 계산이다.
- 경로 `POST /api/constellations/layout` 은 FE 상수와 A-9 문서를 따른다. 접두사 정렬은 S15P21A405-213·214 에서 함께 다룬다.

## 상대 파트에 알려야 할 점

- **[프론트] ⚠️ 수정 필요** `playlist-panel.tsx` 가 플레이리스트 곡을 **개수 제한 없이** 배치 API 로 보낸다(`items.map((it) => it.musicId)`). 배치 API 상한은 30곡이라 **31곡 이상 플리는 400 이 되어 별자리가 아예 뜨지 않는다.** 프론트가 30곡으로 잘라 보내야 한다 — 어느 30곡을 남길지(앞에서부터 / 사용자 선택)는 FE 판단이다. 서버가 임의로 자르지 않는 이유는 사용자가 모르는 기준으로 곡이 사라지기 때문이다.
- **[프론트]** 백엔드 배치 API 가 붙으면 `use-constellation-layout-query.ts` 가 보내는 `points`(16차원 좌표 동봉)는 **보내도 무시된다.** 목 라우트 제거와 함께 빼면 된다.
- **[프론트]** 플레이리스트 좌표는 백엔드에서 이미 내려간다 — `GET /api/playlist/detail` 의 `musics[].location` 이 pc1~pc16 이다. `mockPlaylists` 를 실 API 로 바꾸면 별자리에 필요한 좌표가 함께 온다. 다만 프론트 상수 경로(`/api/playlists/{id}`)와 백엔드 실제 경로(`/api/playlist/detail?playlistId=`)가 다르다 — S15P21A405-214 범위다.
