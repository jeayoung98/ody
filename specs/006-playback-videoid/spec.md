# Feature Specification: 재생 가능 여부와 videoId (SONG-03 / SONG-04)

**Feature Branch**: `backend/feat/S15P21A405-57-videoid-contract`

**Created**: 2026-09-13

**Status**: Draft — 계약 정의 단계. 적재·저장소는 이번 범위가 아니다.

**Input**: 클라이언트가 곡을 재생할 때 무엇을 근거로 재생하는지를 정의한다. 현재는 `title`·`artist` 로 만든 **YouTube 검색 URL** 하나뿐이라 앱 밖(새 탭)으로 나갈 수밖에 없고, 검색 결과가 맞는 곡이라는 보장도 없다. 곡별 **`videoId`** 를 계약에 추가해 클라이언트가 확인된 영상으로 바로 갈 수 있게 한다. 이번 이슈는 **계약과 규칙만** 정한다 — 값을 채우는 적재는 후속이다.

## Clarifications

### Session 2026-09-13

- Q: `videoId` 를 어디서 얻는가? → A: YouTube Data API `search.list`. **MusicBrainz 무료 경로는 존재하지 않는다** — `recording?inc=url-rels` 가 map_sample 11곡·대조군(Radiohead "Creep") 전부 URL 관계 0개였고, 유튜브 링크는 아티스트 채널 단위로만 있다. 하루 100곡(100 units/call) 제약이 그대로 유효하다. *(실측 확정)*
- Q: 검색 결과 중 무엇을 채택하는가? → A: **곡 길이 ±3초** 일치. 단 **공식 채널(`- Topic`, VEVO)은 ±30초**. 그리고 `status.embeddable == true`. 50곡 실측으로 정한 값이다(아래 SC-002). *(실측 확정)*
- Q: 기존 `playable`·`youtubeUrl` 의 의미를 바꾸는가? → A: **바꾸지 않는다.** `videoId` 는 가산 필드이고, `playable` 은 지금처럼 "재생 링크 유무"를 뜻한다. 클라이언트는 `videoId` 유무로 **재생 방식**을 고르고, `playable` 로 **재생 가능 여부**를 판단한다. *(설계 결정)*
- Q: `videoId` 를 못 구한 곡을 지도에서 빼는가? → A: **빼지 않는다.** 매핑률 실측이 66%(S15P21A405-40 코멘트)라 3분의 1을 지우면 지도 밀도가 무너진다. 표시하되 재생 불가를 안내한다(SONG-04). *(실측 근거 결정)*
- 결정: 임베드 재생 자체는 `data/AGENTS.md` **규칙 6** 개정에 달려 있다. 이 스펙은 **`videoId` 를 내려주는 것까지**를 정의하고, 클라이언트가 그것을 임베드로 쓸지 새 탭으로 쓸지는 규칙 6 결정에 따른다. 계약은 두 경우 모두에서 유효하다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 확인된 영상으로 재생한다 (Priority: P1)

사용자가 곡을 재생하면, 검색 결과를 헤매지 않고 **그 곡의 영상**으로 간다.

1. **Given** `videoId` 가 있는 곡, **When** 재생을 누르면, **Then** 클라이언트는 그 `videoId` 로 재생한다. (FR-001, FR-002)
2. **Given** `videoId` 가 없는 곡이지만 `youtubeUrl` 이 있는 곡, **When** 재생을 누르면, **Then** 지금과 같이 검색 URL 로 넘어간다. (FR-003)

### User Story 2 - 재생할 수 없는 곡은 그 사실을 안내받는다 (Priority: P1, SONG-04)

1. **Given** `title`·`artist` 가 모두 비어 검색어를 만들 수 없는 곡, **When** 목록·지도·상세에 나타나면, **Then** `youtubeUrl:null`·`playable:false` 로 내려가고 **목록에서 제거되지 않는다**. (FR-004, FR-005)
2. **Given** 재생 불가 곡, **When** 클라이언트가 표시하면, **Then** 오류가 아니라 상태로 다룬다 — 200 응답이고 에러 코드가 아니다. (FR-005)

### User Story 3 - 잘못된 영상이 붙지 않는다 (Priority: P1)

1. **Given** 곡명으로 검색해도 그 곡이 유튜브에 없는 경우, **When** `videoId` 를 확보하려 하면, **Then** 확보 조건(FR-006)을 통과하지 못하므로 **비워 둔다**. 상위 검색 결과를 그대로 쓰지 않는다. (FR-006, FR-007)

### Edge Cases

- 확보 당시 임베드 가능했으나 이후 영상이 비공개·삭제된 경우 → 클라이언트에서 재생 실패. 재확인 주기는 이번 범위 밖(FR-009에 기록만).
- 같은 곡에 후보가 여러 개이고 둘 다 조건을 통과 → 검색 순위가 앞선 것을 쓴다(결정성).
- `duration` 이 없는 곡 → 길이 대조가 불가능하므로 **확보하지 않는다**.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001 — `videoId` 필드**: `MapPoint`·`MusicSummary`·`MusicDetail` 은 `videoId`(string \| null)를 포함해야 한다(MUST). 길이는 11자다. **근거**: api-spec §0.6; FE 요청.
- **FR-002 — 가산 변경**: 기존 필드(`youtubeUrl`·`playable`)의 의미와 타입을 바꿔서는 안 된다(MUST NOT). 클라이언트는 `videoId` 유무로 재생 **방식**을, `playable` 로 재생 **가능 여부**를 판단한다.
- **FR-003 — 폴백**: `videoId` 가 없어도 `youtubeUrl` 이 있으면 그대로 내려야 한다(MUST). `videoId` 도입이 기존 재생 경로를 없애서는 안 된다(MUST NOT).
- **FR-004 — 재생 불가 곡 유지**: 재생 링크가 없다는 이유로 곡을 목록·지도에서 제외해서는 안 된다(MUST NOT). **근거**: SONG-04; 매핑률 66% 실측 — 제외하면 지도 밀도가 무너진다.
- **FR-005 — 오류가 아니라 상태**: 재생 불가는 200 응답 + `playable:false` 로 표현해야 하며 에러 코드를 쓰지 않는다(MUST NOT). **근거**: S15P21A405-57 설계 결정.
- **FR-006 — 확보 조건**: `videoId` 는 다음을 모두 만족할 때만 저장해야 한다(MUST).
  1. 곡 길이 차이 ≤ **3초**. 단 채널이 `- Topic` 으로 끝나거나 이름에 `VEVO` 를 포함하면 ≤ **30초**
  2. `videos.list` 의 `status.embeddable == true`
  3. 곡의 `duration` 이 존재
- **FR-007 — 모르면 비운다**: 조건을 만족하는 후보가 없으면 `videoId` 를 **비워 둔다**(MUST). 상위 검색 결과를 무조건 채택해서는 안 된다(MUST NOT). **근거**: 스펙 15 "모르는 것을 재생 가능으로 만들지 않는다"; D5 매칭 오염.
- **FR-008 — 미조회와 없음의 구분**: 저장 구조는 "아직 조회하지 않음"과 "조회했으나 없음"을 구분할 수 있어야 한다(MUST). **근거**: 하루 100곡 할당량에서 재조회는 곧 낭비다.
- **FR-009 — 확보 이력**: 언제·무엇으로 확보했는지(조회 시각, 출처)를 남겨야 한다(MUST). 영상이 나중에 내려갈 수 있어 재확인의 근거가 된다.

### Key Entities

- **videoId**: YouTube 영상 식별자 11자. 곡당 0개 또는 1개.
- **확보 상태**: 미조회 / 확보 / 확보 실패(찾았으나 조건 미달 · 후보 없음).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `MapPoint`·`MusicSummary`·`MusicDetail` 세 응답 모두에 `videoId` 가 존재하고, 값이 없을 때 `null` 로 직렬화된다. 기존 필드의 이름·타입·의미 변경은 0건이다. **근거**: FR-001, FR-002.
- **SC-002**: 확보 조건(FR-006)을 50곡 표본에 적용했을 때 **오탐 0건**이다. 2026-09-13 실측. 관용치와 채널분류를 교차해 각각의 기여를 분리했다:

  | 관용치 | 전역 적용 | 오탐 | 비공식 ±3초 고정 + 공식만 완화 | 오탐 |
  | --- | --- | --- | --- | --- |
  | ±3초 | 31 / 50 | 0 | 31 / 50 | 0 |
  | ±5초 | 32 / 50 | 1 | 31 / 50 | 0 |
  | ±10초 | 32 / 50 | 1 | 32 / 50 | 0 |
  | **±30초** | 35 / 50 | 3 | **33 / 50** | **0** ← 채택 |
  | ±120초 | 42 / 50 | 10 | 34 / 50 | 1 |
  | ±300초 | 45 / 50 | 13 | 37 / 50 | 4 |

  채택값은 임의로 고른 것이 아니라 **채널분류가 오탐 0을 유지하는 최대 마진**이다. 그 이상 풀면 같은 공식 채널 안의 **다른 곡**이 붙는다 — RuPaul `itty Girl` → RuPaul Topic 채널의 `Cover Girl`(Δ91초), `Komet - Flip` → 다른 아티스트인 The Jamillas Topic 채널의 `Comet Flip`(Δ277초). 공식 채널은 "누군가의 공식"이지 "이 아티스트의 이 곡"이 아니고, 길이가 유일한 방어선이라 느슨해지면 막을 것이 없다. 전역 완화는 ±5초부터 이미 오염된다.

  **근거**: FR-006; `videoid_pilot.py`·`sweep.py` seed=7; S15P21A405-40 코멘트.
- **SC-003**: `videoId` 가 없는 곡이 목록·지도 응답에서 누락되는 일이 0건이다. **근거**: FR-004.
- **SC-004**: `videoId` 도입으로 `/api/music/major` 응답 시간이 **10 ms 이상 늘지 않는다**. 지도는 `map_sample` 에 `music` 을 PK 조인해 `videoId` 를 가져온다. 2026-09-13 운영 DB 실측: 조인 없음 0.24 ms, 조인 웜 **4.97 ms**, 콜드 19.6 ms (Nested Loop + `PK_MUSIC` Index Scan, 1,094 loops). 엔드포인트 전체가 240 ms 라 +5 ms 는 2% 다.
  - **비정규화하지 않는다.** 초안에서는 `map_sample.video_id` 로 복사하려 했으나, `build_map_layer.sql:46` 의 `322 ms → 0.4 ms` 주석을 이 조인 비용으로 잘못 읽은 것이었다. 그 수치는 대표곡을 `music` 에서 계산해 뽑던 원래 질의의 것이다.
  - 레이어 1(1,094행) 기준이다. 레이어가 늘면 행 수에 비례하므로 그때 다시 잰다.

**plan / 후속으로 미루는 사항**:
- 저장소 스키마 확정과 DDL 실행 — **BE4 실행 영역**(헌법 X). BE2 는 필요 형태만 제안한다.
- 하루 100곡 적재 배치의 위치·스케줄·담당 — 미정(데이터 파이프라인 vs 백엔드).
- 확보한 영상의 재확인 주기(비공개·삭제 대응).
- 할당량 증액 신청 — 구글 심사라 일정에 넣지 않는다.

## Assumptions

- 임베드 재생 가부는 `data/AGENTS.md` 규칙 6 개정 결과에 달려 있고, **이 스펙의 계약은 결과와 무관하게 유효하다** — `videoId` 는 임베드에도 쓰이고 `watch` URL 생성에도 쓰인다.
- 적재 전까지 `videoId` 는 전 곡 `null` 이다. 클라이언트는 null 을 정상 상태로 다룬다(FR-003 폴백).
- 매핑률 66%는 50곡 표본이다. 전체 1,094곡에서 같으리란 보장은 없으며 본 적재 시 실측을 기록한다.
