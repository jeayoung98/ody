# 계약 — videoId 값은 그대로, 다만 네 번째 상태가 생긴다

**Date**: 2026-09-18 (갱신) | **소비자**: 프론트엔드 (FE1 Exploration · FE2 Service)

## 바뀌지 않는 것

`POST /api/music/videoid` → `items[].videoId` 의 세 값은 **그대로다.** 백엔드 안에서 판정 기록이 `video_id = 'none'` 에서 `music.is_unplayable` 로 옮겨가지만, 바깥으로 나가는 값은 한 글자도 달라지지 않는다.

| 값 | 뜻 | 프론트 해석 (S15P21A405-364) |
| --- | --- | --- |
| 11자 문자열 | 재생 가능 | `found` |
| `"none"` | 찾아봤지만 없음 | `notFound` — 안내하고 재시도하지 않는다 |
| `null` | 아직 안 찾아봄 | `unsearched` — 다시 누르면 재조회 |

곡 상세·주변 탐색·경로 탐색 응답에도 `videoId` 가 실리지만 프론트는 매핑하지 않는다(`lib/backend.ts:242`). 전용 엔드포인트가 유일한 출처다(S15P21A405-340).

## 바뀌는 것 — 곡이 사라질 수 있다

재생 불가 곡을 **DB 에서 주기적으로 삭제**하기로 결정됐다(2026-09-18, DATA).

삭제된 곡을 일괄 조회하면 `items` 에서 **누락**된다. 현재 BFF 라우트는 이렇게 읽는다.

```ts
const raw = data.items?.find((v) => v.musicId === musicId)?.videoId ?? null;
//                                                              ^^^^^^^ 누락 → null → unsearched
```

그래서 **존재하지 않는 곡에 "재생 준비 중 · 잠시 후 다시 눌러 주세요"가 영원히 뜨고, `retryable: true` 라 누를 때마다 재조회가 나간다.** S15P21A405-364 에서 고친 증상이 삭제를 계기로 되살아난다.

걸리는 경로: 플레이리스트, 여정 결과, 공유 링크, 클라이언트 캐시 — 삭제 전에 얻은 id 를 들고 있는 모든 곳.

### 선택지 (FR-008, 회신 대기)

| 안 | 내용 | 변경 |
| --- | --- | --- |
| A | 백엔드가 "삭제됨"을 명시하고 프론트가 전용 문구 | BE + FE |
| B | 프론트가 "일괄 조회에서 누락 = `notFound`" 로 해석 | FE 만 |
| C | 그대로 둔다 | 없음 (위 증상 감수) |

**삭제 배치 가동 전에 정해야 한다.**

## 왜 `"none"` 을 `null` 로 정리하지 않았나

계약만 보면 정리하는 쪽이 깨끗하다 — `"none"` 은 `videoId` 타입에 없는 값이다. 그런데 바꾸면 재생 불가 곡이 `unsearched` 로 내려가 안내가 "잠시 후 다시"로 퇴행하고 클릭마다 재조회가 나간다. 얻는 것은 타입 청결뿐이고 사용자가 얻는 것은 없다.

정리하려면 값을 지울 게 아니라 **상태를 명시**해야 한다 — `videoId: null` + 상태 필드. 위 A안이 그 형태다.

## 별건 — `genres` 가 빈 배열이 된다

장르 테이블(`music_genre`·`music_genre_v1`)이 드롭 예정이라 백엔드가 조인을 걷어낸다. `genres` 는 항상 `[]` 가 된다 — 곡 상세 장르 칩, 헤더 색상, 여정 `genreName` 이 영향받는다.

다만 지금도 **98.8% 곡이 빈 배열**이다(장르 보유 58,259곡 / 전체 4,679,505곡). 이번 videoid 건과 원인이 다르므로 별도 이슈로 진행한다.

## 호환성

- videoId 계약에 깨는 변경 없음. 배포 순서 제약 없음
- 되돌리기: 백엔드 변경만 되돌리면 된다. 저장된 데이터는 건드리지 않는다
- 단 **백필(`'none'` 560행 → 플래그)은 되돌릴 대상이 아니다** — 플래그는 표시값과 같은 뜻이라 남아 있어도 무해하다
