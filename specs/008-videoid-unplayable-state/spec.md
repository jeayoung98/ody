# Feature Specification: 재생 불가 판정을 백엔드가 직접 기록한다

**Feature Branch**: `backend/fix/S15P21A405-454-videoid-unplayable-state`

**Created**: 2026-09-18 | **Revised**: 2026-09-18 (MR 326 코드 대조 후)

**Status**: Draft — FR-008 만 프론트 회신 대기

**Input**: DATA 파트가 videoid 조회 서비스를 저장소로 옮겼다(S15P21A405-441, MR 326). 조회 주소만 바꾸면 되는 전환처럼 보이지만, **바꾸는 순간 "찾아봤지만 없는 곡"이라는 판정이 사라진다.** 지금 그 판정은 외부 서비스가 videoId 자리에 넣어 주는 표시값에 얹혀 있고, 새 서비스는 그 자리를 비워서 보낸다. 판정을 백엔드가 직접 내리고 기록하도록 옮긴다.

## 왜 지금인가

세 상태가 사용자에게 서로 다른 안내로 이어진다. 프론트는 이미 이 셋을 구분해 쓴다(S15P21A405-364).

| 상태 | 사용자에게 보이는 것 | 다시 눌렀을 때 |
| --- | --- | --- |
| 재생 가능 | 재생된다 | — |
| **찾아봤지만 없음** | "재생 불가 — 아직 준비 중인 곡이에요. 신고해 주시면 채워 넣을게요" | 다시 묻지 않는다 |
| 아직 안 찾아봄 | "재생 준비 중 — 잠시 후 다시 눌러 주세요" | 다시 묻는다 |

가운데 상태를 만들어내는 것이 **현재는 외부 서비스**다. 새 서비스(MR 326)는 재생 불가면 `best` 를 비워 보내고, 지금 백엔드는 그것을 "결과 없음"으로 읽어 아무것도 기록하지 않는다. 그 결과 재생 불가 곡이 전부 "아직 안 찾아봄"으로 내려가고:

- 사용자는 영원히 "잠시 후 다시 눌러 주세요"를 본다. 그 곡은 잠시 후에도 되지 않는다
- 누를 때마다 조회가 다시 나간다
- 신고로 안내하던 길(SONG-04)이 사라진다

기존 표시값 행은 계속 동작하므로 **증상이 새 곡에만 천천히 나타난다.** 전환 전에 고쳐야 한다.

## Clarifications

### Session 2026-09-18

- Q: 재생 불가와 일시 실패를 무엇으로 가르는가? → A: **최상위 `retryable`(boolean)**. MR 326 코드 확인. `playable`(boolean)도 최상위에 있다. DATA 가 말한 `is_unplayable` 은 **응답 필드가 아니라 `music` 테이블 칼럼 이름**이다. *(코드 확인)*
- Q: 판정을 어디에 기록하는가? → A: **`music.is_unplayable`**(boolean NOT NULL DEFAULT false, 운영 실재 확인). 재생 불가 행을 주기적으로 삭제하기로 결정되면서 삭제 배치가 이 칼럼을 보기 때문이다. `video_id = 'none'` 쓰기는 **멈춘다.** *(2026-09-18 결정)*
- Q: 그러면 프론트가 보는 값은? → A: **바꾸지 않는다.** 플래그가 선 곡의 videoId 를 응답에서 `"none"` 으로 번역한다. 형태를 바꾸면 재생 불가 곡이 "재생 준비 중"으로 퇴행하고 클릭마다 재조회가 나간다. *(프론트 코드 확인)*
- Q: `best_guess`(유사도 0.6 이상 추측)를 영구 저장하는가? → A: **저장한다.** verified 와 같이 다룬다. 대가는 "알려진 한계"에 적는다. *(2026-09-18 결정)*
- Q: 판정이 불확실하면 어느 쪽으로 기우는가? → A: **재시도 쪽.** 영구 기록은 되돌릴 경로가 없다. *(설계 결정)*
- Q: 곡 길이를 조회에 실어 보내는 변경이 필요한가? → A: **이미 되어 있다**(S15P21A405-407). `album`·`isrc`·`releaseYear` 도 새 API 가 받지만 이번 범위에 넣지 않는다. *(코드 확인)*

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 재생할 수 없는 곡은 그 사실을 알려 준다 (Priority: P1, SONG-04)

사용자가 곡을 누른다. 쓸 만한 영상이 없다면 **없다는 것과 무엇을 할 수 있는지**를 안내받아야 한다. 기다리면 될 것처럼 보여서는 안 된다.

**Why this priority**: 조회 서비스를 교체하는 순간 이 안내가 사라진다.

**Independent Test**: 후보가 없는 곡을 두 번 조회해, 두 번째가 외부 호출 없이 같은 "재생 불가" 답을 주는지 본다.

**Acceptance Scenarios**:

1. **Given** 조회했지만 쓸 만한 후보가 없는 곡, **When** 조회하면, **Then** 판정이 **기록되고** 응답은 재생 불가 상태를 나타낸다.
2. **Given** 같은 곡, **When** 다시 조회하면, **Then** 외부 조회 없이 같은 답이 나온다.
3. **Given** 같은 곡, **When** 클라이언트가 응답을 받으면, **Then** 200 응답이고 오류 코드가 아니다.

---

### User Story 2 - 일시적 실패를 영구 판정으로 굳히지 않는다 (Priority: P1)

외부 조회가 시간 안에 답하지 못하거나 검색 자체가 실패할 수 있다. 그것은 "재생할 수 없다"와 다르다.

**Why this priority**: 잘못 굳은 판정을 되돌릴 경로가 없다 — 다시 묻는 코드가 없고 덮어쓰는 질의도 없다.

**Independent Test**: 조회가 실패하도록 두고 한 번 조회한 뒤, 아무것도 기록되지 않았고 다음 조회가 다시 시도하는지 본다.

**Acceptance Scenarios**:

1. **Given** 외부 조회가 시간 초과되는 곡, **When** 조회하면, **Then** 아무것도 기록하지 않는다.
2. **Given** 외부 조회가 "재시도 가능"으로 답하는 곡, **When** 조회하면, **Then** 재생 불가로 기록하지 않는다.
3. **Given** 응답만으로 가릴 수 없는 곡, **When** 조회하면, **Then** **기록하지 않는다**.

---

### User Story 3 - 이미 판정된 곡을 다시 찾지 않는다 (Priority: P2)

**Why this priority**: 사용자가 직접 보는 결함은 아니지만, US1 을 잘못 구현하면 함께 무너진다.

**Independent Test**: 판정된 곡을 연속 조회하고 외부 호출이 나가지 않는지 본다.

**Acceptance Scenarios**:

1. **Given** 재생 가능으로 판정된 곡, **When** 여러 번 조회하면, **Then** 외부 조회가 나가지 않는다.
2. **Given** 재생 불가로 판정된 곡, **When** 여러 번 조회하면, **Then** 외부 조회가 나가지 않는다.
3. **Given** 아직 판정되지 않은 곡, **When** 조회하면, **Then** 외부 조회가 나가고 결과가 기록된다.

### Edge Cases

- **판정을 가릴 수 없는 응답**: 재시도 가능으로 취급한다(FR-003). 잘못 굳히는 쪽보다 다시 묻는 쪽이 복구 가능하다.
- **외부 서비스가 실패를 200 으로 답한다**: MR 326 의 `api.py` 는 예외를 잡아 `200 + retryable: true` 로 돌려준다. HTTP 상태만으로 실패를 가릴 수 없으므로 **본문을 읽어야 한다**.
- **곡명·아티스트가 비어 있는 곡**: 새 API 가 400 을 준다. 클라이언트 오류로 취급해 기록하지 않는다.
- **전환 기간**: 조회 주소가 바뀌기 전까지는 기존 서비스가 판정값을 직접 넣어 준다. 두 경로가 공존해도 결과가 같아야 한다.
- **이미 기록된 곡**: 기존 판정은 그대로 유효하다. 이 변경이 기존 기록을 지우거나 다시 묻게 만들어서는 안 된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001 — 재생 불가를 기록한다**: 외부 조회가 쓸 만한 후보가 없다고 답하면 그 판정을 **`music.is_unplayable` 에 기록해야 한다**(MUST). 다음 조회는 외부 호출 없이 같은 답을 내야 한다(MUST). **근거**: 전환 후 이 기록이 사라지면 재생 불가 안내(SONG-04)가 함께 사라진다. 삭제 배치도 이 값을 본다.
- **FR-002 — 일시적 실패는 기록하지 않는다**: 시간 초과·연결 실패·재시도 가능 응답은 재생 불가로 기록해서는 안 된다(MUST NOT). 다음 요청에 다시 시도해야 한다(MUST).
- **FR-003 — 모르면 굳히지 않는다**: 응답만으로 FR-001 과 FR-002 를 가릴 수 없으면 기록하지 않아야 한다(MUST NOT). **근거**: 안 굳히면 조회 한 번이 낭비되고, 잘못 굳히면 곡 하나가 영구히 재생 불가가 된다.
- **FR-004 — 클라이언트가 보는 형태를 바꾸지 않는다**: 세 상태를 구분하는 기존 표현을 바꿔서는 안 된다(MUST NOT). 판정 기록이 다른 칼럼으로 옮겨가도 응답 값은 같아야 한다(MUST). **근거**: 프론트가 이 구분으로 안내 문구와 재시도 여부를 고른다(S15P21A405-364).
- **FR-005 — 목록 제외 규칙을 유지한다**: 검색·대표곡이 재생 불가 곡을 빼는 동작은 유지되어야 하며, 제외 조건도 정본인 플래그를 읽어야 한다(MUST). 전환 시 기존 표시값 행이 목록에 되살아나서는 안 된다(MUST NOT). **근거**: 운영 실측 — `video_id = 'none'` 560행, `is_unplayable = true` **0행**. 백필 없이 조건만 바꾸면 560곡이 되살아난다.
- **FR-006 — 판정 라벨에 따른 저장 차등을 두지 않는다**: 엄격 검증이든 유사도 추측이든 동일하게 저장해야 한다(MUST). **근거**: 2026-09-18 결정.
- **FR-007 — 응답 필드 증가에 깨지지 않는다**: 외부 응답에 새 필드가 추가되어도 기존 동작이 바뀌어서는 안 된다(MUST NOT).
- **FR-008 — 사라진 곡과 아직 안 찾아본 곡을 구분한다**: 삭제된 곡을 클라이언트가 참조했을 때 "아직 조회하지 않음"과 같은 답을 주어서는 안 된다(MUST NOT). **근거**: 일괄 조회는 없는 곡을 결과에서 누락시키고 프론트는 그것을 "아직 안 찾아봄"으로 읽는다. 존재하지 않는 곡에 "잠시 후 다시"가 영원히 뜨고 클릭마다 조회가 나간다. **프론트 회신 대기 중 — 삭제 배치 가동 전에 정한다.**

### Key Entities

- **판정 상태**: 곡마다 셋 중 하나 — **미판정** / **재생 가능** / **재생 불가**. 되돌아가는 전이는 없다.
- **일시 실패**: 상태가 아니다. 아무것도 기록하지 않고 미판정으로 남긴다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 조회 주소를 새 서비스로 바꾸기 전후로 재생 불가 곡에 대한 응답이 **동일하다**. 안내 문구가 바뀌는 곡이 0곡이다. **근거**: FR-001, FR-004.
- **SC-002**: 재생 불가로 판정된 곡을 10회 조회할 때 외부 조회는 **첫 1회뿐**이다. **근거**: FR-001, US3.
- **SC-003**: 외부 조회가 실패한 곡이 재생 불가로 기록되는 건수가 **0** 이다. **근거**: FR-002, FR-003.
- **SC-004**: 이 변경으로 검색·지도 목록에서 사라지거나 새로 나타나는 곡이 **0곡** 이다. **근거**: FR-005 (백필 선행이 전제).

## Assumptions

- 프론트는 `POST /api/music/videoid` 를 videoId 의 유일한 출처로 쓴다. 곡 상세·주변·경로 응답의 값은 매핑하지 않는다(프론트 코드 확인). 사용자 영향은 그 엔드포인트에 집중된다.
- 외부 캐시는 디스크 SQLite 라 재시작에 보존된다. TTL 은 확보 30일 / 재시도 대기 10분 / 그 외 1일이다(MR 326 `lookup.py` 확인).
- 백엔드 실시간 경로는 사용자가 연 곡만 판정한다 — 전체의 **0.10%**(4,707 / 4,679,505). 카탈로그 전반의 판정은 DATA 의 별도 채움 작업이 맡는다.
- 조회 주소는 환경변수로 주입되므로 서비스 전환에 코드 변경이 필요 없다.

## 알려진 한계 *(결정에 따른 대가)*

FR-006 에 따라 유사도 추측 판정도 영구 저장한다.

- **틀린 영상이 고착된다.** 값이 있으면 다시 묻지 않고 덮어쓰는 경로가 없다. 실측 근거는 spec 006 SC-002 — 유사도 매칭은 같은 채널의 다른 곡, 다른 아티스트의 비슷한 제목을 붙인다.
- **나중에 골라낼 수 없다.** 저장하는 것은 식별자뿐이라 추측으로 들어간 곡과 검증을 통과한 곡을 사후에 구분할 수 없다.
- 되돌리려면 저장 계층에 판정 라벨이 필요하다. 스키마 변경은 BE4 영역이라 이번 범위 밖이다.

## 선행 작업

**`video_id = 'none'` 560행에 플래그를 세운다.** 필터 전환보다 **먼저** 실행해야 한다.

```sql
UPDATE music SET is_unplayable = true WHERE video_id = 'none';
```

운영 쓰기이므로 사람이 직접 실행한다. `video_id` 값은 그대로 둔다 — 읽기에서 플래그를 정본으로 번역하므로 남아 있어도 무해하다.

## 상대 파트에 알려야 할 점

- **[FE]** videoId 응답 형태는 바꾸지 않습니다 — 세 상태 구분은 그대로 동작합니다. 다만 **재생 불가 곡이 DB 에서 삭제되기로 결정됐습니다.** 삭제된 곡은 일괄 조회에서 누락되고 현재 BFF 라우트가 그것을 `unsearched` 로 읽어 **"잠시 후 다시 눌러 주세요"를 영원히 보여주고 클릭마다 재조회합니다.** 네 번째 상태를 어떻게 다룰지 정해야 합니다(FR-008).
- **[FE]** 장르 테이블(`music_genre`·`music_genre_v1`)이 드롭 예정이라 백엔드가 조인을 걷어냅니다. `genres` 가 항상 빈 배열이 됩니다 — 곡 상세 장르 칩, 헤더 색상, 여정 `genreName` 이 영향받습니다. 다만 지금도 **98.8% 곡이 빈 배열**(장르 보유 58,259곡 / 4,679,505곡)이라 체감 변화는 작을 것으로 봅니다.
- **[기획]** 재생 불가 곡 **삭제는 spec 006 FR-004 와 어긋납니다** — "재생 링크가 없다는 이유로 곡을 목록·지도에서 제외해서는 안 된다"(매핑률 66% 실측 근거). 결정은 수용했으나 `FEATURES.md` 와 spec 006 갱신이 필요합니다.
- **[DATA]** 요청하신 곡 길이 전달은 **이미 반영돼 있습니다**(S15P21A405-407, `backend/dev` 머지 완료). `master` 기준으로 보셔서 미반영으로 보이신 것 같습니다.
