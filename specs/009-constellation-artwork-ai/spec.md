# Feature Specification: 별자리 작품 AI 평가와 회차 리더보드

**Feature Branch**: `backend/feat/S15P21A405-548-constellation-ai-leaderboard`

**Jira**: S15P21A405-548

**Created**: 2026-09-22

**Status**: Design — 설계 산출물만. 구현 코드는 이 이슈의 제외 범위다

**Input**: 사용자가 만든 플레이리스트 별자리 그림이 회차 주제(1회차: 고양이)를 얼마나 닮았는지 AI로 채점하고, 채점된 작품을 다른 사용자가 감상·좋아요하며 점수 순 리더보드로 겨루게 한다.

## 착수 시점의 코드 상태 (2026-09-22 확인)

| 확인한 것 | 위치 | 상태 |
| --- | --- | --- |
| 별자리 배치 API 가 있다 | `POST /api/constellations/layout` — `ConstellationController`, `ConstellationService` | 있음. 곡 2~30개 → `{musicId, x, y}` (-1~1). 같은 집합이면 항상 같은 좌표 |
| 좌표 원천은 서빙 baseline 하나다 | `PlanarProjection`, `music.location vector(16)` | 있음 (헌법 V) |
| 플레이리스트 도메인이 있다 | `playlist(id, email, playlist_name, like_cnt, …)`, `playlist_item(playlist_id, music_id, position)` | 있음 |
| 좋아요 패턴이 이미 있다 | `playlist_like(playlist_id, email, created_at)` 복합 PK + `playlist.like_cnt` 비정규화 사본 (S15P21A405-442) | **그대로 베낀다** |
| 외부 HTTP 호출 패턴이 있다 | `VideoIdApiClient` — `RestClient` + `SimpleClientHttpRequestFactory` 타임아웃 | **그대로 베낀다**. 새 의존성 없음 |
| 공통 응답·에러 봉투 | `ApiResponse{success,data,error}`, `ErrorCode` 구현 enum (`PlaylistErrorCode` 등) | 있음 |
| 작품·회차·AI 평가에 해당하는 것 | 백엔드 전체 | **없음**. 전부 신규 |
| GMS(LLM 게이트웨이) 호출 | 저장소 전체 (`grep -ri gms` 무결과) | **없음**. 첫 도입 |

### 기능 명세와의 관계 — 팀 상의 필요

`docs/rules/FEATURES.md` 에 **이 기능에 해당하는 항목이 없다.** 가장 가까운 것은 둘이다.

- `PATH-01` — "플레이리스트는 사용자가 만든 모양(예: 강아지)이 **상품으로 성립한다**". 이 기능의 전제가 여기 있다.
- `SOCIAL-12` — 랭킹 표시. **미확정**이고 탑 플레이리스트는 **주간 좋아요 수** 기준이다. 이 기능은 **AI 점수** 기준이라 같은 줄이 아니다.

따라서 이 스펙은 **명세에 없는 신규 기능**이다. 구현 착수 전에 기획 확인과 FEATURES.md 항목 신설이 필요하다
(CLAUDE.md §3, 헌법 IX). 아래 Clarifications 의 결정들도 그 확인 대상이다.

## Clarifications

### Session 2026-09-22

- Q: AI 가 볼 이미지를 누가 만드나? → A: **백엔드가 저장된 좌표로 렌더한다.** 프론트 캔버스 이미지를 받으면 제출자가 임의의 고양이 사진을 넣어 점수를 올릴 수 있다 — 리더보드는 경쟁이므로 채점 대상을 서버가 소유해야 한다. JDK 표준 `java.awt` + `javax.imageio` 로 그리며 의존성을 추가하지 않는다.
- Q: 순위 기준은? → A: **AI 점수 내림차순.** 좋아요는 보조 지표이자 동점 정렬 키다.
- Q: 목표 모양은? → A: **주제 회차제.** 회차마다 주제가 바뀐다(1회차 고양이). 리더보드는 회차별로 따로 존재한다.
- Q: 평가 모델은? → A: **GMS 게이트웨이의 `gpt-4o`, 기준 그림 4장 few-shot.** 경로: `gpt-5.4-mini`(이미지 입력 언급 없음) → `gpt-4o-mini`(2 Credit, 가장 싼 vision) → 실측에서 mini 는 어떤 프롬프트로도 그림 5종을 30점 동점으로 뭉쳐 리더보드가 성립하지 않았다 → `gpt-4o`(20 Credit). 문구·해상도로는 엉망 배치와 난수를 못 갈랐고 **점수가 붙은 기준 그림을 함께 보여주자** 갈렸다. 실험 6회 기록은 plan.md "변별력 진단". 알려진 한계: 부위 하나(꼬리) 빠진 것은 못 깎는다.
- Q: 채점 기준 그림은 어디에 두나? → A: **`artwork` 행으로** (`is_anchor = true`, 점수 고정). 좌표 저장과 렌더러를 그대로 쓰고 리더보드·내 작품·회차당 1작품 검사에서만 뺀다. 회차마다 사람이 SQL 로 넣는다.
- Q: 제출 뒤 플레이리스트가 바뀌면? → A: **작품은 제출 시점 스냅샷으로 고정된다.** 곡 목록·순서·좌표를 작품에 복사해 저장한다. 이후 원본을 고치거나 지워도 작품과 점수는 그대로다 — 점수를 받은 그림과 화면에 보이는 그림이 달라지면 리더보드가 거짓말이 된다.
- Q: 한 사람이 한 회차에 몇 개를 낼 수 있나? → A: **회차당 1작품.** 교체 제출은 허용하되 **기존 작품의 점수·좋아요는 함께 사라진다**(같은 행을 덮지 않고 삭제 후 신규 생성). 무제한 제출을 허용하면 점수가 잘 나올 때까지 다시 내는 것이 최적 전략이 되고, GMS 호출 비용이 사용자 수에 비례하지 않는다. **기획 확인 대상.**
- Q: 채점은 동기인가? → A: **비동기.** 제출은 즉시 `PENDING` 으로 201 을 돌려주고 평가는 뒤에서 한다. LLM 왕복을 제출 요청에 물리면 응답이 초 단위로 늘어지고 타임아웃이 곧 제출 실패가 된다.
- Q: 공개 범위는? → A: **제출 = 공개.** 단 리더보드·타인 조회에는 `SCORED` 만 보인다. `PENDING`·`FAILED` 는 소유자에게만 보인다. 비공개 보관은 이번 범위가 아니다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 내 별자리를 회차 주제로 채점받는다 (Priority: P1)

사용자가 자기 플레이리스트를 이번 회차에 제출하면, 잠시 뒤 "고양이를 얼마나 닮았는가" 점수와 한 줄 평이 붙는다.

**Why this priority**: 이것 하나만 되면 "내 플리 모양이 상품이 된다"(PATH-01)가 처음으로 눈에 보이는 값을 갖는다. 리더보드·좋아요는 그 위에 얹는 것이다.

**Independent Test**: 곡 10개짜리 플레이리스트를 제출하고 (a) 즉시 `PENDING` 이 돌아오는지, (b) 잠시 뒤 상세에 점수와 한 줄 평이 채워지는지, (c) 제출 뒤 플레이리스트에서 곡을 빼도 작품의 그림·점수가 그대로인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 곡 10개인 내 플레이리스트와 열려 있는 회차, **When** 제출하면, **Then** `201` 과 `{artworkId, status:"PENDING"}` 을 즉시 받는다. (FR-001, FR-013)
2. **Given** 제출한 작품, **When** 평가가 끝나면, **Then** 상태가 `SCORED` 가 되고 `score`(0~100 정수)와 한 줄 평이 채워진다. (FR-005)
3. **Given** 제출 직후 원본 플레이리스트에서 곡 3개를 빼고, **When** 작품 상세를 조회하면, **Then** 작품의 곡 목록·좌표·점수가 제출 시점 그대로다. (FR-003)
4. **Given** 제출 뒤 원본 플레이리스트를 **삭제**하고, **When** 작품 상세를 조회하면, **Then** 작품은 남아 있고 그림도 그대로다. (FR-004)
5. **Given** 남의 플레이리스트 id, **When** 제출하면, **Then** `403 FORBIDDEN` 이고 작품이 생기지 않는다. (FR-002)
6. **Given** 곡이 1개 이하이거나 31개 이상인 플레이리스트, **When** 제출하면, **Then** `400 INVALID_INPUT` 이다 — 배치 API 의 2~30 제약과 같은 값을 쓴다. (FR-002)

### User Story 2 - 회차 리더보드를 본다 (Priority: P1)

누구나 이번 회차 리더보드에서 점수가 높은 작품부터 본다. 작품을 열면 별자리 그림과 담긴 곡, AI 한 줄 평이 보이고 좋아요를 누를 수 있다.

**Why this priority**: 겨룰 상대가 보이지 않으면 점수는 혼잣말이다. P1 과 함께 있어야 기능이 성립한다.

**Independent Test**: 점수가 다른 작품 여럿을 만들어 리더보드 순서를 확인하고, 좋아요를 눌렀다 떼며 수가 맞게 움직이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 같은 회차에 `SCORED` 작품 여럿, **When** 리더보드를 조회하면, **Then** `score` 내림차순이고 동점이면 `likeCnt` 내림차순, 그래도 같으면 먼저 제출한 순이다. (FR-008)
2. **Given** `PENDING` 이거나 `FAILED` 인 작품, **When** 남이 리더보드를 조회하면, **Then** 그 작품은 목록에 없다. (FR-009)
3. **Given** 리더보드의 어떤 작품, **When** 상세를 조회하면, **Then** 좌표 목록·곡 목록(제출 순서)·점수·한 줄 평·좋아요 수·내가 눌렀는지 여부가 함께 온다. (FR-010)
4. **Given** 좋아요하지 않은 작품, **When** `liked=true` 로 두 번 연속 요청하면, **Then** 좋아요 수가 1 만 오른다(목표 상태 방식, 토글 아님). (FR-011)
5. **Given** 내 작품, **When** 삭제하면, **Then** 리더보드에서 사라지고 그 작품의 좋아요 기록도 함께 사라진다. (FR-012)
6. **Given** 지난 회차 id, **When** 리더보드를 조회하면, **Then** 그 회차의 순위가 그대로 보인다 — 회차가 끝나도 점수를 0 으로 초기화하지 않는다. (FR-014)

### User Story 3 - 채점이 실패했을 때 (Priority: P2)

AI 호출이 실패해도 사용자는 무엇이 일어났는지 알고 다시 시도할 수 있다. 실패한 작품이 0점으로 리더보드에 박히지 않는다.

**Why this priority**: 외부 LLM 호출은 실패한다. 실패를 0점으로 저장하면 사용자는 "못생겼다"는 뜻으로 읽고, 리더보드 바닥에 실패 작품이 쌓인다.

**Independent Test**: GMS 가 응답하지 않는 상태로 제출해 `FAILED` 가 되는지, 리더보드에서 빠지는지, 재시도로 복구되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** GMS 가 타임아웃·5xx·형식 위반 응답을 준 제출, **When** 평가가 끝나면, **Then** 상태는 `FAILED` 이고 `score` 는 **비어 있다**(0 이 아니다). (FR-006)
2. **Given** `FAILED` 작품, **When** 소유자가 재평가를 요청하면, **Then** 다시 `PENDING` 이 되고 재평가된다. (FR-007)
3. **Given** 재시도 상한(3회)을 채운 작품, **When** 다시 재평가를 요청하면, **Then** `409 ARTWORK_RETRY_EXHAUSTED` 다. (FR-007)
4. **Given** `FAILED` 작품, **When** 소유자가 아닌 사람이 재평가를 요청하면, **Then** `403 FORBIDDEN` 이다. (FR-007)
5. **Given** GMS 가 점수 범위를 벗어난 값이나 JSON 이 아닌 답을 준 경우, **When** 응답을 해석하면, **Then** 저장하지 않고 실패로 간주한다 — 모델이 뱉은 값을 검증 없이 점수로 쓰지 않는다. (FR-006)

### Edge Cases

- **열린 회차가 없다**: 제출은 `409 ARTWORK_ROUND_CLOSED`. 리더보드 조회는 지난 회차로 계속 된다.
- **같은 회차 재제출**: 기존 작품을 지우고 새로 만든다. 점수·좋아요는 승계하지 않는다. "지금 점수와 좋아요가 사라진다"를 프론트가 먼저 고지해야 한다.
- **평가 중 삭제**: `PENDING` 작품을 소유자가 지우면 평가 결과가 늦게 도착해도 **무시한다**(작품 행이 없으면 쓰지 않는다).
- **좌표를 만들 수 없다**: 제출 시 배치 계산이 실패하면(곡 누락 등) 제출 자체가 실패한다. 부분 배치로 작품을 만들지 않는다 — 006 의 "부분 결과를 성공으로 내지 않는다"와 같은 결정.
- **곡이 지워진 경우**: 작품은 `music_id` 를 스냅샷으로 들고 있다. 곡 행이 사라지면 좌표는 그대로 보이고 곡 정보만 빈다. 그림이 깨지지 않는 것이 우선이다.
- **GMS 비용 폭주**: 회차당 1작품 + 재시도 3회가 사용자당 호출 상한이다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 로그인 사용자는 자기 플레이리스트를 열려 있는 회차에 작품으로 제출할 수 있어야 한다(MUST).
- **FR-002**: 제출은 **소유자만** 가능해야 하며(MUST), 곡 수가 2~30 밖이면 거부해야 한다(MUST).
- **FR-003**: 제출 시 곡 목록·순서·2D 좌표를 작품에 **복사해 저장**해야 한다(MUST). 이후 원본 플레이리스트 변경이 작품에 반영되어서는 안 된다(MUST NOT).
- **FR-004**: 원본 플레이리스트가 삭제되어도 작품은 남아야 한다(MUST).
- **FR-005**: 평가가 끝난 작품은 0~100 정수 점수와 한 줄 평을 가져야 한다(MUST).
- **FR-006**: 평가 실패(타임아웃·오류 응답·형식 위반·범위 위반)는 `FAILED` 로 기록해야 하며(MUST), 점수를 0 으로 저장해서는 안 된다(MUST NOT).
- **FR-007**: 소유자는 `FAILED` 작품을 재평가할 수 있어야 한다(MUST). 재시도는 작품당 3회로 제한해야 한다(MUST).
- **FR-008**: 리더보드는 `score` 내림차순, 동점 시 `likeCnt` 내림차순, 그래도 동점이면 제출 시각 오름차순으로 정렬해야 한다(MUST).
- **FR-009**: 리더보드와 타인의 조회에는 `SCORED` 작품만 보여야 한다(MUST).
- **FR-010**: 작품 상세는 좌표 목록·곡 목록(제출 순서)·점수·한 줄 평·좋아요 수·요청자의 좋아요 여부를 포함해야 한다(MUST).
- **FR-011**: 좋아요는 **목표 상태**(`liked=true|false`)를 받아야 하며(MUST), 같은 요청을 반복해도 결과가 같아야 한다(MUST).
- **FR-012**: 소유자는 자기 작품을 삭제할 수 있어야 하고(MUST), 삭제 시 좌표·좋아요 기록이 함께 정리되어야 한다(MUST).
- **FR-013**: 제출 응답은 평가 완료를 기다려서는 안 된다(MUST NOT).
- **FR-014**: 회차가 끝나도 그 회차의 점수·순위는 보존되어야 한다(MUST) — SOCIAL-12 의 "0으로 갱신 X" 와 같은 규칙.
- **FR-015**: AI 가 채점하는 이미지는 **서버가 저장된 좌표로 렌더한 것**이어야 한다(MUST). 클라이언트가 보낸 이미지를 채점해서는 안 된다(MUST NOT).
- **FR-016**: GMS 인증 키는 설정에서 주입해야 하며(MUST), 로그·응답·문서·커밋에 남겨서는 안 된다(MUST NOT).

### Key Entities

- **회차 (Round)**: 하나의 주제와 기간. 리더보드의 단위. 1회차 주제는 고양이.
- **작품 (Artwork)**: 어떤 사용자가 어떤 회차에 낸 별자리 스냅샷 하나. 상태(`PENDING`/`SCORED`/`FAILED`), 점수, 한 줄 평, 좋아요 수를 갖는다.
- **작품 좌표 (Artwork Point)**: 작품에 속한 점 하나 — 순서·곡 id·x·y. 작품당 2~30개.
- **작품 좋아요 (Artwork Like)**: 누가 어떤 작품에 좋아요 했는지. `playlist_like` 와 같은 모양.

## Success Criteria *(mandatory)*

- **SC-001**: 제출 요청이 평가 완료를 기다리지 않는다 — 제출 응답 시간이 기존 플레이리스트 조회와 같은 급이다.
- **SC-002**: 제출 뒤 원본 플레이리스트를 어떻게 고쳐도 작품 상세의 좌표·곡 목록·점수가 변하지 않는다.
- **SC-003**: GMS 가 응답하지 않는 상태에서 제출해도 서버는 5xx 를 내지 않고 작품이 `FAILED` 로 남는다.
- **SC-004**: 리더보드에 `PENDING`·`FAILED` 작품이 한 건도 나타나지 않는다.
- **SC-005**: 같은 사용자가 같은 회차에 동시에 두 번 제출해도 작품은 1개다(DB 제약으로 보장).
- **SC-006**: 같은 사용자가 같은 작품에 동시에 좋아요를 두 번 눌러도 `like_cnt` 가 1 만 오른다(복합 PK 로 보장 — `playlist_like` 와 같은 방식).

## 상대 파트에 알려야 할 점

- **[기획]** FEATURES.md 에 이 기능 항목이 없다. `SOCIAL-12`(미확정)와 순위 기준이 다르다(좋아요 순 vs AI 점수 순). 항목 신설과 "회차당 1작품·교체 시 점수 소멸" 정책 확인이 필요하다.
- **[프론트]** 신규 엔드포인트 7개와 신규 에러 코드가 생긴다. 제출 응답이 `PENDING` 이라 **프론트가 상태를 다시 조회해야 한다**(폴링 또는 화면 재진입). 소켓 알림은 이번 범위가 아니다.
- **[프론트]** 같은 회차 재제출 시 기존 점수·좋아요가 사라지는 것을 누르기 전에 고지해야 한다.
- **[인프라]** GMS base URL·API 키를 백엔드 환경변수로 주입해야 한다. 키는 `.env` 로만 들어가고 저장소에 남기지 않는다.
- **[인프라/DB]** 신규 테이블 4개 + 시퀀스. DDL 은 `backend/src/main/resources/db/` 에 두고 **사람이 DBeaver 로 실행**한다(기존 관례).
