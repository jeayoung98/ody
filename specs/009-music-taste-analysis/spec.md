## User Scenarios & Testing *(mandatory)*

### User Story 1 - 내 좋아요 음악의 분포 확인 (Priority: P1)

로그인한 사용자는 취향 분석 화면에서 본인이 좋아요한 곡들이 음악 공간의 어느 영역에 모이는지 확인한다. 음악 특징별 중심과 분포 폭을 함께 보고, 일관된 취향과 폭넓게 듣는 특징을 구별한다.

**Why this priority**: AI 문장 생성 여부와 관계없이 좋아요 음악의 실제 분포를 확인하는 기본 가치를 제공한다.

**Independent Test**: 위치와 특징이 알려진 좋아요 곡 집합으로 분포 화면을 열어 곡 수, 점 위치, 축 설명과 특징별 분포를 확인한다. AI 연결 없이도 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 유효한 좌표를 가진 좋아요 곡이 있을 때, **When** 분포를 조회하면, **Then** 좋아요 총곡 수·분석 포함 수·제외 수와 해당 곡의 분포가 표시된다.
2. **Given** 동일한 좋아요 집합과 기준 데이터 버전일 때, **When** 다른 지도 레이어나 탐색 위치에서 분석 화면을 열면, **Then** 분석 통계와 동일 축 조합의 분포는 변하지 않는다.
3. **Given** 한 특징에서 높은 쪽에 좁게 모이는 집합과 양쪽으로 넓게 퍼진 집합일 때, **When** 특징별 분포를 확인하면, **Then** 중심의 치우침과 분포 폭을 별도로 읽을 수 있다.
4. **Given** 좋아요 곡이 1~9개일 때, **When** 분포를 조회하면, **Then** 존재하는 곡의 분포와 표본 부족 안내를 표시하고 AI 취향 리포트를 생성하지 않는다.
5. **Given** 유효한 좋아요 곡이 10~29개일 때, **When** 분포를 조회하면, **Then** 현재 표본으로 생성 가능한 결과가 초기 리포트임을 안내한다.
6. **Given** 사용자가 개별 곡에 좋아요를 표시했을 때, **When** 마이페이지의 좋아요 음악을 열면, **Then** 최근 좋아요한 순서의 전체 곡 목록을 플레이리스트처럼 조회하고 원하는 곡부터 기존 재생 큐로 순차 재생할 수 있다.

### User Story 2 - 근거를 갖춘 AI 취향 리포트 읽기 (Priority: P1)

사용자는 분석 가능한 곡이 충분할 때 리포트 생성을 요청하고, 자신의 음악적 취향을 설명하는 한국어 한줄 요약과 상세 설명을 읽는다. 각 설명은 실제 좋아요 곡 분포와 연결되어야 한다.

**Why this priority**: 음악 공간의 수치를 사용자가 이해할 수 있는 설명으로 바꾸는 핵심 기능이다.

**Independent Test**: 검증된 분석 결과를 입력으로 제공해 생성된 요약과 상세 설명이 수치·축 의미·분포 폭에 모순되지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 유효한 좋아요 곡이 10개 이상이고 비교 기준이 준비됐을 때, **When** 리포트 생성을 요청하면, **Then** 한국어 한 문장 요약, 근거가 있는 주요 특징 최대 3개, 분석 곡 수와 생성 시점을 제공한다. 10~29개는 초기 리포트, 30개 이상은 일반 리포트로 표시한다.
2. **Given** 특정 축을 따라 넓게 퍼져 있지만 중심의 치우침이 없는 집합일 때, **When** 리포트를 읽으면, **Then** 높은 방향을 선호한다고 단정하지 않고 해당 특징의 다양성으로 설명한다.
3. **Given** 낮은 쪽과 높은 쪽에 나뉘어 모인 집합일 때, **When** 중심값이 중간에 위치하더라도, **Then** 중간 성향에 집중한다고 서술하지 않고 양쪽 성향의 공존 또는 넓은 분포로 설명한다.
4. **Given** 의미가 검증되지 않은 축이나 근거가 없는 장르·감정 추론이 생성 결과에 포함되면, **When** 결과를 제공하려 할 때, **Then** 해당 설명을 최종 리포트로 제공하지 않고 통계 기반 기본 설명으로 대체한다.

### User Story 3 - 변경된 취향과 생성 실패 구분 (Priority: P2)

사용자는 기존 리포트와 마지막 갱신 시점을 확인하고, 좋아요 목록이 변경되면 일일 제한 안에서 분석 버튼으로 새 분석을 요청할 수 있다. AI 생성이 실패해도 현재 분포와 기본 설명을 확인할 수 있다.

**Why this priority**: 같은 리포트를 안정적으로 재열람하고 데이터 변경·외부 서비스 실패를 혼동하지 않게 한다.

**Independent Test**: 좋아요 추가·취소, 생성 중 변경, 반복 요청, AI 실패 상황을 각각 구성하여 최신성 표시와 대체 결과를 확인한다.

**Acceptance Scenarios**:

1. **Given** 좋아요 집합과 분석 기준·생성 정책 버전이 같을 때, **When** 다시 조회하면, **Then** 저장된 동일 리포트를 제공하며 새 생성으로 문구를 바꾸지 않는다.
2. **Given** 리포트 생성 후 좋아요 추가 또는 취소가 발생했을 때, **When** 다시 조회하면, **Then** 기존 리포트를 최신으로 표시하지 않고 갱신이 필요함을 안내한다.
3. **Given** 생성 중 좋아요가 변경됐을 때, **When** 생성이 끝나면, **Then** 결과가 사용한 시점의 분포와 함께 제공되고 최신 목록과 다르면 갱신 필요 상태가 표시된다.
4. **Given** AI 서비스의 시간 초과·한도 초과·잘못된 응답이 발생했을 때, **When** 생성이 종료되면, **Then** 분포와 통계 기반 기본 설명을 제공하고 AI 리포트 생성 실패 및 재시도 가능 상태를 구분한다.
5. **Given** 로그인하지 않았거나 다른 사용자의 분석을 요청했을 때, **When** 접근하면, **Then** 해당 사용자의 분포·리포트를 제공하지 않는다.
6. **Given** 일일 생성 한도를 사용한 사용자일 때, **When** 좋아요를 변경하고 분석 버튼을 다시 눌러도, **Then** 새 AI 리포트를 생성하지 않고 제한 안내와 기존 리포트의 마지막 갱신 시점을 표시한다.
7. **Given** 기존 리포트가 있을 때, **When** 화면 재조회 또는 좋아요 변경만 발생하면, **Then** AI 리포트를 자동 생성하지 않고 마지막 갱신 시점을 유지한다.

### Edge Cases

- 좋아요 0개: 빈 화면 안내와 좋아요가 필요한 이유를 표시한다. 임의의 취향 설명을 생성하지 않는다.
- 유효 곡 9개/10개 및 29개/30개: 리포트 생성 자격과 초기·일반 리포트 경계를 정확히 적용한다.
- 좋아요 기록 중복: 같은 곡은 한 번만 포함하고 반복 좋아요를 가중치로 쓰지 않는다.
- 삭제된 곡·좌표 누락·차원 불일치·유한하지 않은 값: 분석에서 제외하고 제외 수를 안내한다. 0 좌표로 대체하지 않는다.
- 좌표계 버전 불일치: 현재 비교 기준과 호환되지 않는 곡은 제외한다. 기준 자체가 준비되지 않았으면 분석 준비 중으로 안내한다.
- 동일 위치에 여러 곡: 겹친 곡의 개수를 확인할 수 있어야 하며 일부 곡만 존재하는 것처럼 표현하지 않는다.
- 모든 좋아요 곡의 좌표가 같음: 분포 폭 0을 처리하고 다양하다고 설명하지 않는다.
- 비교 모집단에서 변동이 없는 축: 해당 축을 비교·순위·문장 근거에서 제외한다.
- 극단값 또는 양봉 분포: 중심 하나로 전체 취향을 대표하지 않고 분포 범위를 함께 제공한다.
- 생성 연속 클릭: 같은 분석 스냅샷에 중복 생성 결과를 만들지 않는다.
- 분석 기준 갱신: 이전 버전 리포트를 최신 기준 리포트로 오인하게 표시하지 않는다.
- 생성 실패 뒤 재시도: AI 시간 초과·한도 초과·통신 오류·내용 또는 형식 검증 실패로 정상 저장되지 않으면 일일 횟수를 차감하지 않고 재시도를 허용한다. 성공 결과의 일반 재조회는 재생성하지 않는다.
- 일일 제한 경계: 한국시간(Asia/Seoul)의 날짜별로 한도를 적용하며 매일 00:00에 초기화한다. 생성 요청이 수락된 한국시간 날짜에 귀속하고 자정을 넘어 완료되어도 다음 날짜 한도를 차감하지 않는다. 진행 중에는 자정을 지나도 추가 생성을 시작하지 않는다. 연속 클릭·다른 기기에서의 동시 요청·좋아요 변경으로 제한을 우회할 수 없어야 한다.
- 갱신 이력 없음: 성공 리포트가 없으면 마지막 갱신 시점 대신 아직 생성된 리포트가 없음을 표시한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001 — 대상과 권한**: 본인 인증을 마친 사용자만 자신의 분포와 리포트를 조회·생성할 수 있어야 한다. 다른 사용자 리포트 공개·공유는 범위에 포함하지 않는다.
- **FR-002 — 좋아요 집합**: 분석 대상은 분석 시작 시점에 사용자가 직접 좋아요한 개별 곡의 중복 없는 전체 집합이어야 한다. 플레이리스트 좋아요·재생 이력·추천 노출을 곡 좋아요로 대체해서는 안 된다.
- **FR-003 — 유효 데이터**: 기존 16개 PC 좌표와 비교 기준의 호환성을 확인하고 유효한 곡만 계산해야 한다. 총곡 수·유효 곡 수·제외 곡 수와 제외 사유를 제공해야 한다.
- **FR-004 — 공통 비교 기준**: 사용자 간·조회 간 비교에는 동일 버전의 전체 유효 서빙 카탈로그를 기준으로 사용해야 한다. 현재 지도에 로드된 곡이나 사용자 자신의 집합을 비교 모집단으로 사용해서는 안 된다.
- **FR-005 — 축별 분석**: 기존 PC 축별로 중심, 가운데 50% 범위, 전체 범위와 비교 모집단에서의 상대 위치를 제공해야 한다. 중심은 중앙값으로, 가운데 50% 범위는 25~75백분위 구간으로 정의한다. 축별 분포 구간별 곡 수도 제공하여 중앙값만으로 양봉 분포를 숨기지 않아야 한다.
- **FR-006 — 좌표 보존**: 사용자별로 새로운 PCA 축을 생성하지 않고 기존 PC 축 의미와 부호를 보존해야 한다. 취향 비교를 위한 스케일 보정은 기존 지도·추천·별자리의 저장 좌표를 변경해서는 안 된다.
- **FR-007 — 분포 표현**: 기존 PC 축을 두 개씩 묶은 8개 조합에서 좋아요 곡의 2차원 분포를 확인할 수 있어야 한다. 초기 조합은 PC1·PC2이며 축 전환이 분석 대상 곡을 필터링해서는 안 된다. 각 점의 곡 정보와 겹친 곡 수, 현재 축을 확인할 수 있어야 한다.
- **FR-008 — 상대 비교 표시**: 선택 축의 좋아요 분포와 전체 기준에서의 상대 위치·퍼짐을 함께 확인할 수 있어야 한다. 화면 표현을 집계할 경우 집계 사실과 포함 곡 수를 명시하며 전체 집합의 분석 통계를 바꾸지 않아야 한다.
- **FR-009 — 해석 제한**: 데이터 담당이 검증한 축 해석과 강도를 따라야 한다. 강·중 등급 축을 주요 설명에 사용하고 약한 해석은 경향으로 구분하며, 의미가 없는 축은 음악 특징 이름을 임의로 붙이지 않아야 한다.
- **FR-010 — 위치와 폭의 구분**: 중심의 상대적 위치는 취향의 치우침으로, 퍼짐은 특징의 다양성으로 설명해야 한다. 길게 늘어선 방향을 곧바로 양의 방향 선호로 해석해서는 안 된다.
- **FR-011 — 리포트 구성**: AI 리포트는 한국어 한 문장 요약, 근거가 있는 주요 특징 최대 3개, 각 특징의 분포 근거, 분석 대상 수·기준 시점·생성 시점을 포함해야 한다. 뚜렷한 특징이 없으면 이를 명시하고 특징 개수를 채우려고 내용을 생성하지 않아야 한다.
- **FR-012 — AI 근거**: AI는 확정된 수치 분석 결과와 검증된 축 설명으로 문장을 작성해야 한다. 통계 수치·축 의미를 새로 만들어서는 안 되며 성격·정신 상태·가사·장르를 제공된 근거 없이 추론해서는 안 된다. AI가 작성한 결과임을 표시해야 한다.
- **FR-013 — 표본 규모와 표현 강도**: 유효 곡이 10개 미만이면 AI 취향 리포트를 생성하지 않고 초기 리포트까지 필요한 추가 곡 수를 안내해야 한다. 유효 곡이 1개 이상이면 현재 분포는 제공해야 한다. 10~29개에서는 결과를 `초기 리포트`로 표시하고 현재 좋아요 기준의 잠정 경향이라는 안내를 포함해야 하며 단정적인 표현을 사용해서는 안 된다. 30개 이상에서는 `일반 리포트`로 표시하되 통계적 대표성이 보장된다고 표현해서는 안 된다.
- **FR-014 — 최신성·재사용**: 동일한 좋아요 집합·좌표계·기준 통계·축 해석·분석 정책·생성 정책 버전에 대한 성공 리포트는 재사용해야 한다. 어느 하나가 바뀌면 갱신 필요 상태를 식별해야 한다.
- **FR-015 — 상태 일관성**: 생성 중·완료·표본 부족·기준 준비 중·갱신 필요·생성 실패를 사용자가 구별할 수 있어야 한다. 분포와 설명을 함께 제공할 때 같은 분석 스냅샷에 속해야 한다.
- **FR-016 — 장애 대응**: AI 생성 실패나 내용·형식 검증 실패 시 같은 통계에 근거한 기본 설명을 제공하고 AI 생성 성공으로 표시해서는 안 된다. 비교 통계 자체가 없으면 설명을 만들어내지 않아야 한다.
- **FR-017 — 정보 최소화**: 외부 AI에는 리포트 작성에 필요한 집계 통계와 축 해석만 전달해야 한다. 사용자 이메일·인증 정보·좋아요 목록 전체를 전달하지 않아야 한다. 탈퇴 시 개인과 연결된 분석 결과는 기존 계정 삭제 정책을 따라 제거해야 한다.
- **FR-018 — 비영향성**: 분포 조회와 리포트 생성은 좋아요 목록·플레이리스트·기존 탐색 위치·서빙 좌표를 변경해서는 안 된다.
- **FR-019 — 수동 생성·일일 제한**: 새 AI 리포트는 사용자가 분석 버튼을 눌렀을 때만 생성하며 사용자별 한국시간(Asia/Seoul) 날짜당 1회로 제한해야 한다. 한도는 매일 00:00에 초기화하며 성공한 요청의 수락 날짜에 귀속한다. 화면 조회·좋아요 변경·기준 버전 변경만으로 자동 생성해서는 안 된다. 동일 입력의 기존 성공 리포트 재사용은 새 생성으로 세지 않는다. 사용자별 생성은 동시에 하나만 진행하고, 한도 소진 시 다음 생성 가능 시점을 한국시간으로 안내해야 한다. AI 리포트가 내용·형식 검증을 통과해 정상 저장된 경우에만 횟수를 차감해야 한다. 실패하거나 기본 설명만 제공한 경우에는 차감하지 않고 재시도를 허용해야 한다.
- **FR-020 — 마지막 갱신 표시**: 마지막으로 AI 리포트 생성에 성공하여 저장한 시점을 날짜·시간으로 표시해야 한다. 단순 조회·재사용·생성 실패·기본 설명 제공으로 해당 시점을 변경해서는 안 된다. 기존 리포트가 없는 경우 갱신 시점을 임의로 만들지 않아야 한다.
- **FR-021 — 좋아요 음악 가상 플레이리스트**: 마이페이지에서 현재 사용자가 좋아요한 개별 곡 전체를 최근 좋아요한 순서로 조회하고 원하는 곡부터 기존 재생 큐로 순차 재생할 수 있어야 한다. 별도 플레이리스트와 항목을 자동 생성하거나 복제하지 않고 `music_like`를 단일 원천으로 사용해야 하며, 좋아요 해제는 다음 조회와 새 재생 큐에 반영되어야 한다.

### Key Entities *(include if feature involves data)*

- **좋아요 곡 집합**: 사용자, 중복 없는 곡 식별자 집합, 분석 기준 시점 및 변경 여부를 나타낸다.
- **카탈로그 비교 기준**: 포함되는 유효 곡 모집단, 좌표계 버전, 축별 비교 분포와 생성 시점. 서로 다른 좌표계와 혼합할 수 없다.
- **축 해석 사전**: 각 PC의 낮음·높음 의미, 해석 강도 및 버전. 의미 없는 축도 명시한다.
- **취향 분석 스냅샷**: 좋아요 집합과 비교 기준, 유효·제외 수, 축별 분포 및 통계. 분포 화면과 설명의 공통 근거다.
- **취향 리포트**: 소유 사용자와 분석 스냅샷, 한줄 요약·주요 특징·근거, 생성 시각과 마지막 성공 갱신 시점, AI 또는 기본 설명 구분, 생성 정책 버전과 최신성 상태.
- **사용자별 생성 한도**: 사용자, 일일 생성 횟수와 진행 중 요청 상태. 좋아요 변경·기기 변경과 관계없이 사용자 단위로 적용한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

아래 수치는 이번 초안의 제안 인수 목표이며 기존 프로젝트의 승인된 성능 정책을 대체하지 않는다.

- **SC-001**: 동일 데이터·기준 버전의 반복 조회 20회에서 분석 포함 곡 수와 통계가 모두 일치하며, 지도 탐색 위치를 바꿔도 결과가 같다.
- **SC-002**: 고저 집중·넓은 분포·양봉·동일 좌표·누락·표본 경계를 포함한 사전 정의 사례 20개에서 각 통계가 검증 기준과 일치하고 수치·축 방향을 반대로 설명한 최종 리포트가 0건이다.
- **SC-003**: 유효 곡 10~1,000개를 가진 사용자 기준, 동시 사용자 10명의 정상 연결 환경에서 100회 측정 시 분포 또는 기존 리포트는 95%가 3초 이내 표시된다. 새 리포트 요청은 95%가 30초 이내 AI 리포트 또는 실패를 명시한 기본 설명에 도달한다. AI 실패율은 별도로 보고하여 기본 설명으로 생성 품질을 대체 평가하지 않는다.
- **SC-004**: 비로그인·타 사용자 접근, 표본 부족, AI 시간 초과·한도 초과·형식 오류 사례에서 정의한 접근 제한 또는 안내가 모두 표시된다.
- **SC-005**: 사용성 검토 참가자 5명 중 4명 이상이 1분 이내 자신의 주요 경향과 취향 폭을 각각 하나 이상 설명하고, 리포트의 최신 여부를 구별한다.
- **SC-006**: 동일 사용자의 동시 요청·반복 클릭·좋아요 변경 사례에서 일일 한도 초과 생성이 0건이고, 조회·실패·재사용 후 마지막 성공 갱신 시점이 모두 유지된다. 실패 요청 뒤에는 같은 날짜에 재시도할 수 있고 성공 저장 뒤에는 다음 한국시간 자정까지 추가 생성이 거부된다.
- **SC-007**: 한국시간 23:59:59에는 소진된 당일 한도로 새 생성이 거부되고 다음 날 00:00:00에는 새 한도가 적용된다. 자정을 넘긴 진행 중 요청은 수락 날짜에 귀속되고 중복 생성이 시작되지 않는다.
- **SC-008**: 유효 곡 수 9·10·29·30개 경계 사례에서 각각 리포트 없음·초기·초기·일반 상태가 정확히 표시되고, 10~29개 결과에는 잠정 경향 안내가 누락되지 않는다.
- **SC-009**: 좋아요 음악 목록의 곡 수·순서가 `music_like`와 일치하고, 목록의 임의 곡에서 재생을 시작하면 해당 곡부터 마지막 곡까지 같은 순서로 기존 재생 큐에 들어간다.

## Assumptions

- **확정 기본 정책**: 본인 전용, 현재 좋아요 전체 기간, 곡별 동일 비중, 한국어, 비스트리밍 결과를 사용한다. 유효 곡 10~29개는 초기 리포트, 30개 이상은 일반 리포트로 제공하며 어느 구간도 통계적 대표성을 보장하는 표현을 사용하지 않는다.
- **범위**: 이 문서는 분포 화면과 취향 리포트의 제품 동작을 함께 정의한다. 현재 백엔드 이슈만으로 프론트 구현 완료를 뜻하지 않으며 파트별 구현 분리는 계획 단계에서 한다.
- **제외**: 별자리 모양 판별·리더보드·투표, 그림에서 플레이리스트 생성, 추천곡 생성, 사용자 간 비교·공유, 시계열 취향 변화 분석, 모델 재학습, 사용자별 PCA 재적용은 포함하지 않는다.
- **사용자 지정 서비스 제약**: AI 문장 생성은 GMS를 사용한다. 특정 모델은 아직 선정하지 않았으며 호출 방식·응답 계약·인증 설정·재시도 정책은 계획에서 정의한다. 사용 근거는 사용자가 제공한 [GMS Quickstart](https://gms.ssafy.io/web/guide/quickstart)이다.
- **입력 의존성 — 확정**: 개별 곡 좋아요 기능을 추가할 예정이다. 해당 기능을 분석의 선행 작업으로 두고 사용자가 직접 좋아요한 개별 곡만 분석한다. 플레이리스트 좋아요로 대체하지 않는다. 좋아요 추가·취소·본인 목록 조회 계약과 담당·이슈 분리는 계획 단계에서 정의한다. 이번 명세 작성은 개별 곡 좋아요 기능의 구현 완료를 의미하지 않는다.
- **해석 의존성**: 이전 프론트 브랜치에서 검토한 `docs/rules/PC-AXES.md`가 현재 백엔드 브랜치에는 없다. 검증된 축 해석·강도·버전과 전체 카탈로그 비교 통계를 데이터 담당으로부터 확보해야 한다. 과거 표를 현재 배포 기준으로 단정하지 않는다.
- **기존 명세 관계**: [FEATURES.md](../../docs/rules/FEATURES.md)의 USER-02 대시보드 제안과 관련 있지만, 이번 분석 리포트는 기존 확정 기능에 명시되어 있지 않다. 기능 명세와 다르므로 팀 상의가 필요하다. 본 문서는 승인 전 제안이며 공통 기능 ID·화면 계약은 계획 단계에서 조율하고 승인된 내용을 공통 명세에 반영한다.
- **인수 추적**: US1은 FR-002~010·013·018, US2는 FR-009~013·017, US3는 FR-001·014~020을 검증한다. Edge Cases는 FR-003~005·008·010·013~016·019~020의 경계 조건을 보완한다.
