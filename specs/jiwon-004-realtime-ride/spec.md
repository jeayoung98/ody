## 1. 목표

지도에서 탐색 중인 다른 사용자 한 명을 골라 그 사람의 화면과 재생을 그대로 따라간다. 따라가는 사람(동승자)은 선장의 곡·레이어·화면 범위·곡 상세 패널을 공유하고, 선장이 곡을 바꾸면 같이 움직인다. 동승 중에는 스스로 조작할 수 없고 하차만 할 수 있다. 선장이 나가면 전원이 그 자리에 남아 단독 사용자로 돌아온다.

핵심 설계 원칙은 **선단은 지도에서 한 점**이라는 것이다. 동승자를 개별 마커로 지도 인덱스에 넣지 않고 선장 위치에 `riderCount` 정수 하나만 실어 보낸다. 이 결정이 이 기능 전체의 부하 특성을 결정한다 — 선장이 곡을 바꿔도 위치 변경 이벤트는 인원수와 무관하게 1건이고, 뷰포트·근처사람 팬아웃에 증폭이 없다.

이 문서는 일곱 Jira 티켓을 하나의 계약으로 설계한다. 실제 구현과 커밋은 위 순서로 나누고, 각 티켓 완료 뒤 사용자 검토 전에는 다음 티켓으로 넘어가지 않는다.

### 기능 경계

- 따라가기는 재생 동기화 기능이 아니라 **이벤트 중계** 기능이다. 서버는 JSON 명령만 나르고 영상은 각 기기가 YouTube에서 직접 받는다.
- 선단 재생 스냅샷은 중간 탑승자 동기화의 유일한 근거이며, 주기 갱신(tick)을 하지 않는다.
- 뷰포트는 선장 것을 그대로 전달할 뿐 동승자별로 재계산하지 않는다.
- 곡 상세 본문은 서버가 나르지 않는다. 식별자와 탭만 보내고 각 동승자가 기존 엔드포인트로 조회한다.
- 동승자를 지도 인덱스에 개별 등록하지 않는다. 선장 위치의 `riderCount`가 동승자를 대표한다.
- 만남 기록은 따라가는 동안 발생하지 않고 하차 시점에만 계산한다.

### D19 보충 — 만남 판정의 근거

동승 중에는 같은 곡에 있어도 만남이 아니다. 따라다닌 결과이지 서로 찾아온 것이 아니기 때문이다. 그러나 하차하는 순간 그 사람은 보통 사용자가 되므로, 그 곡에 원래 있던 제3자와는 만남이 성립한다. 반대로 따라가기를 시작하기 **직전**에 같은 곡에 있었다면 그때 이미 만남으로 기록됐으므로 중복 계산하지 않는다.

전원 해체 시 순차 삽입하면 나중 사람이 먼저 삽입된 동료를 기존 거주자로 본다. 그래서 해체 **전에** 거주자 명단을 한 번 찍고 그 명단하고만 대조한다.

## 4. 선단 모델 계약

선단(fleet)은 선장 1명과 동승자 0~20명으로 이루어진다. Redis 표현은 네 개 키다.

```text
ride:captain:{rider}    String  - 이 사람이 따라가는 선장. 탑승 epoch 포함
ride:riders:{captain}   Set     - 이 선장을 따라가는 사람들
ride:playback:{captain} Hash    - {musicId, state, positionMs, updatedAt}
ride:panel:{captain}    Hash    - {open, musicId, tab}
```

`ride:captain`과 `ride:riders`는 서로의 역인덱스다. 둘이 어긋나면 하차할 수 없거나 유령 동승자가 남으므로, **두 키의 모든 변경은 한 Lua 스크립트 안에서 일어나야 한다.**

재생 위치는 저장된 값이 스스로 흐르지 않는다. 읽는 쪽이 계산한다.

```text
재생 중이면   현재 위치 = positionMs + (지금 - updatedAt)
정지 상태면   현재 위치 = positionMs
```

이 계산 덕분에 선단당 쓰기는 선장이 실제로 조작할 때만 일어난다. 20명 선단이 한 시간 동안 조용히 듣기만 하면 쓰기는 0이다.

## 5. User Scenarios & Testing

### User Story 1 - 활성 사용자를 골라 따라가기를 시작한다 (Priority: P1 · S15P21A405-82)

지도나 근처 사람 목록에서 곡을 듣고 있는 사용자를 보고 따라가기를 누른다. 요청이 받아들여지면 즉시 선장의 곡·레이어로 이동하고, 선장이 듣던 위치에서 같은 곡이 재생되기 시작한다.

**Why this priority**: 탑승 상태가 있어야 전파·차단·하차를 붙일 기준 상태가 생긴다.

**Independent Test**: A가 곡을 재생 중일 때 B가 `POST /api/realtime/ride`로 A를 지정하면 B의 위치가 A의 곡·레이어로 바뀌고 응답에 선장의 현재 재생 위치가 담긴다.

**Acceptance Scenarios**:

1. **R1** **Given** A가 활성 상태, **When** B가 A를 지정해 탑승, **Then** `ride:captain:{B}`와 `ride:riders:{A}`가 한 번에 생기고 B가 A의 곡·레이어에 배치된다.
2. **R2** **Given** A가 정지 상태(곡 위에 없음), **When** B가 탑승 시도, **Then** `RIDE_CAPTAIN_INACTIVE`로 거부하고 아무 키도 만들지 않는다.
3. **R3** **Given** B가 자기 자신을 지정, **When** 탑승 시도, **Then** `RIDE_SELF`로 거부한다.
4. **R4** **Given** B가 이미 C를 따라가는 중, **When** A에 탑승 시도, **Then** `RIDE_ALREADY_RIDING`으로 거부한다. 자동 환승하지 않는다.
5. **R5** **Given** B에게 이미 동승자가 있음, **When** B가 A에 탑승 시도, **Then** `RIDE_CHAIN_FORBIDDEN`으로 거부한다.
6. **R6** **Given** A의 동승자가 이미 20명, **When** 21번째 탑승 시도, **Then** `RIDE_FULL`로 거부한다.
7. **R7** **Given** 두 요청이 동시에 서로 다른 선장에 걸림, **When** Lua 실행, **Then** 하나만 성공하고 `ride:captain`이 두 개가 되지 않는다.
8. **R8** **Given** A가 재생 중이고 스냅샷의 `updatedAt`이 30초 전, **When** B가 탑승, **Then** 응답의 재생 위치가 저장값 + 30초다.
9. **R9** **Given** A가 정지 상태로 스냅샷에 기록됨, **When** B가 탑승, **Then** 경과를 더하지 않고 저장된 위치 그대로 준다.
10. **R10** **Given** 탑승 성공, **When** 만남 기록 판정, **Then** 탑승 자체는 만남으로 기록하지 않는다.
11. **R11** **Given** 탑승 성공, **When** 기준 순번 확정, **Then** `snapshotSeq`는 재생 스냅샷을 읽은 직후의 값으로 정한다.
12. **R12** **Given** 탑승 대상이 목록·뷰포트·팔로우 중 어디서 왔든, **When** 서버 처리, **Then** 출처를 구분하지 않는다.

### User Story 2 - 선장의 곡 선택과 재생 조작이 그대로 들린다 (Priority: P1 · S15P21A405-83)

선장이 다른 곡으로 옮기면 동승자 전원이 같은 곡으로 이동하고 재생이 이어진다. 선장이 멈추거나 재생바를 움직이면 동승자 화면도 같이 움직인다.

**Why this priority**: 따라가기의 본체다. 이게 없으면 탑승은 한 번 순간이동하고 끝난다.

**Independent Test**: A를 따라가는 B가 있을 때 A가 다른 곡을 재생하면 B의 위치와 재생 곡이 같이 바뀐다. A가 일시정지하면 B도 멈춘다.

**Acceptance Scenarios**:

1. **R20** **Given** B가 A를 따라가는 중, **When** A가 `POST /api/realtime/play`로 곡 변경, **Then** B도 같은 곡·레이어로 옮겨지고 `RIDE_TRACK`을 받는다.

### User Story 7 - 인솔자가 사라지면 선단이 자동 해체된다 (Priority: P1 · S15P21A405-87)

선장이 연결을 끊거나 접속이 만료되면 동승자 전원이 강제 하차한다. 선장에게는 따라오는 인원 수가 보인다.

**Why this priority**: 고아 선단이 남으면 다음 선단이 엉뚱한 상태를 물려받는다.

**Independent Test**: 10명이 따라가는 A가 연결을 끊으면 10명 모두 A의 마지막 곡 위에 남고 `RIDE_ENDED`를 받으며, Redis에 `ride:*` 키가 남지 않는다.

**Acceptance Scenarios**:

1. **R120** **Given** 선장이 연결 종료, **When** 해체, **Then** 동승자 전원이 강제 하차하고 `RIDE_ENDED`를 받는다.
2. **R121** **Given** 선장의 접속이 TTL 만료, **When** `PresenceCleanupScheduler` 실행, **Then** 같은 해체 경로를 탄다.
3. **R122** **Given** 해체로 한 점이던 선단이 N개 점으로 쪼개짐, **When** 위치 전파, **Then** 개별 이벤트 N건이 아니라 `VIEWPORT_BULK_ENTER` **한 덩어리**로 보낸다.
4. **R123** **Given** 동승자 본인의 접속만 만료, **When** 정리, **Then** 그 동승자만 제거하고 선단은 유지한다.
5. **R124** **Given** 해체 완료, **When** Redis 확인, **Then** `ride:captain` · `ride:riders` · `ride:playback` · `ride:panel`이 모두 없다.
6. **R125** **Given** 동승자가 재연결, **When** 복구, **Then** 탑승 상태를 복원하지 않고 단독으로 돌아온다.
7. **R126** **Given** 선장이 뷰포트·근처사람 응답에 나타남, **When** `riderCount` 확인, **Then** 0이 아니라 실제 인원수다.
8. **R127** **Given** `riderCount`를 보냄, **When** 페이로드 확인, **Then** 정수 하나뿐이고 동승자 명단은 보내지 않는다.
9. **R128** **Given** 탑승·하차 발생, **When** 선장 알림, **Then** `RIDE_RIDER_JOINED` · `RIDE_RIDER_LEFT`가 개인 큐로 간다.

### 5.8 동승자 상태 생명주기

1. `connect` 후 단독 상태 — 따라가기 버튼을 누를 수 있다.
2. 탑승 성공 — 선장 위치로 이동, 조작 차단 시작, 지도 인덱스에는 개별 등록되지 않는다.
3. 동승 중 — 선장의 곡·화면·패널을 받는다. 재생 기록은 계속 쌓인다.
4. 하차 또는 강제 하차 — 그 자리에 단독으로 남고 조작이 풀린다. 이 시점에만 만남을 계산한다.
5. 재연결 — 언제나 단독 상태로 시작한다.

## 6. Functional Requirements

### 6.1 공통 계약과 검증

- **FR-001** 서버는 `@Profile("realtime")`에서만 따라가기 기능을 활성화해야 한다.
- **FR-002** `ride:captain`과 `ride:riders`의 모든 변경은 한 Lua 스크립트 안에서 원자적으로 일어나야 한다.
- **FR-003** 탑승·하차 요청은 저장된 epoch와 현재 접속 epoch를 대조하고 다르면 무시해야 한다.
- **FR-004** 탑승·하차는 REST로 처리해야 한다. 실패가 사용자에게 반드시 보여야 하는 경로다.
- **FR-005** 선장의 조작 전파는 소켓으로 처리해야 한다. 응답이 필요 없고 빈도가 높다.
- **FR-006** 모든 선단 이벤트는 기존 봉투 `{type, seq, ts, payload}`를 따라야 한다.
- **FR-007** 선단 관련 Redis 키 네 개는 같은 수명을 가져야 한다. 해체 시 함께 사라져야 한다.

### 6.2 S15P21A405-82 — 탑승·자격 검사·스냅샷

- **FR-010** 서버는 선장이 활성(곡 위에 배치)인지 검사해야 한다.
- **FR-011** 서버는 자기 자신 지정, 중복 탑승, 체인 탑승, 20명 초과를 각각 거부해야 한다.
- **FR-012** 다섯 검사와 등록은 하나의 원자 작업이어야 한다. 검사 후 등록 사이에 상태가 바뀌면 안 된다.
- **FR-013** 선장 동의 절차를 두지 않아야 한다.
- **FR-014** 선단 재생 스냅샷은 `{musicId, state, positionMs, updatedAt}` 네 필드만 보관해야 한다.
- **FR-015** 재생 위치는 저장값이 아니라 읽는 시점에 `positionMs + (now - updatedAt)`로 계산해야 한다. 정지 상태면 경과를 더하지 않는다.
- **FR-016** 주기 갱신(tick)을 만들지 않아야 한다. 쓰기는 선장의 실제 조작 시에만 발생해야 한다.
- **FR-017** 탑승 응답의 `snapshotSeq`는 재생 스냅샷을 읽은 직후에 확정해야 한다.
- **FR-018** 탑승 대상의 출처(뷰포트·근처사람·팔로우)를 서버가 구분하지 않아야 한다.
- **FR-019** 탑승 자체를 만남으로 기록하지 않아야 한다.

### 6.3 S15P21A405-83 — 곡 이동·재생 전파

- **FR-020** 선장의 곡 변경은 별도 이벤트를 만들지 않고 기존 재생 선언 경로가 담당해야 한다.
- **FR-021** 선단의 위치 변경 이벤트는 동승자 수와 무관하게 1건이어야 한다.
- **FR-022** 재생수 갱신은 한 트랜잭션에서 `+N+1`을 한 번에 더해야 한다.
- **FR-023** 서버는 재생·정지·구간 이동·보정 이벤트를 받아 스냅샷을 갱신하고 동승자 개인 큐로 전달해야 한다.
- **FR-024** 서버는 JSON 명령만 중계해야 한다. 영상 스트림을 중계하지 않는다.
- **FR-025** 구간 이동 발행은 500ms 간격으로 제한하되 마지막 값의 전달을 보장해야 한다.
- **FR-026** 어긋남 감지는 선장 클라이언트에서만 수행하고 1.5초 이상일 때만 이벤트를 발행해야 한다.
- **FR-027** 광고 시작·종료 이벤트는 이번 범위에 포함하지 않아야 한다.
- **FR-028** 모든 재생 이벤트에 서버 시각을 실어야 한다.
- **FR-029** 동승자가 보낸 재생 이벤트는 `RIDE_NOT_CAPTAIN`으로 거부해야 한다.

### 6.4 S15P21A405-88 — 화면·패널 공유

- **FR-030** 선장의 뷰포트 결과를 동승자별로 재계산하지 않고 그대로 전달해야 한다.
- **FR-031** 선단 뷰포트는 기존 `VIEWPORT_SNAPSHOT`과 별도 타입으로 내려 순번 검사가 섞이지 않게 해야 한다.
- **FR-032** 선단 마커(선장·동승자 자신)는 프론트가 그려야 한다. 서버 목록에는 요청자 제외 규칙이 적용된다.
- **FR-033** 곡 상세는 식별자와 탭만 중계하고 본문을 나르지 않아야 한다.
- **FR-034** 탭 값은 프론트의 `nearby` · `info` · `playlists`를 그대로 써야 한다. 서버가 새 이름을 만들지 않는다.
- **FR-035** 받은 탭이 클라이언트 빌드에 없으면 `nearby`로 폴백해야 한다.
- **FR-036** 패널 스냅샷은 중간 탑승자 동기화에 사용해야 한다.
- **FR-037** 주변곡 탭 결과를 캐시하지 않아야 한다. 대신 20명 선단으로 `ody.nearby.candidates` p99와 커넥션 풀 대기를 1회 실측해야 한다.

### 6.5 S15P21A405-84 — 조작 차단

- **FR-040** 동승자의 화면 요청·레이어 이동·재생 선언·재생 종료·근처사람 열기·곡 상세 열기·닫기·탭 전환을 모두 거부해야 한다.
- **FR-041** 거부는 조용한 무시가 아니라 오류 응답이어야 한다.
- **FR-042** 직접 재생으로 자동 하차하지 않아야 한다.
- **FR-043** 하차 요청만 허용해야 한다.
- **FR-044** 선장이 동승자를 내보내는 기능을 만들지 않아야 한다.

### 6.6 S15P21A405-85 — 하차

- **FR-050** 하차는 `ride:riders` 제거와 `ride:captain` 삭제를 한 Lua 스크립트로 처리해야 한다.
- **FR-051** 하차 후 요청자는 선장의 마지막 곡·레이어에 남아야 한다. 탑승 전 위치로 되돌리지 않는다.
- **FR-052** 하차 시 서버는 어떤 재생 명령도 보내지 않아야 한다.
- **FR-053** 하차 시 재생 기록을 새로 만들지 않아야 한다.
- **FR-054** 하차는 선장에게 `RIDE_RIDER_LEFT`로 알려야 한다.
- **FR-055** 재연결 시 탑승 상태를 복원하지 않아야 한다.

### 6.7 S15P21A405-86 — 기록·만남

- **FR-060** 동승자의 재생도 `play_history`와 재생수에 남겨야 한다. 분기를 두지 않는다.
- **FR-061** 기록 삽입은 선단 단위 배치여야 한다. 사람마다 개별 INSERT를 돌리지 않는다.
- **FR-062** 최초 발견은 선장만 기록해야 한다.
- **FR-063** 만남은 탑승·동승 중에 기록하지 않고 하차 시점에만 계산해야 한다.
- **FR-064** 만남 기록에서 선단 구성원(선장·동료 동승자)은 언제나 제외해야 한다.
- **FR-065** 전원 해체 시 거주자 명단을 해체 전에 한 번 찍고 그 명단하고만 대조해야 한다.
- **FR-066** 1명 하차와 N명 해체는 같은 `recordOnDismount(하차자 목록, 기존 거주자 명단)`을 호출해야 한다.

### 6.8 S15P21A405-87 — 해체·인원수 노출

- **FR-070** 선장의 연결 종료와 TTL 만료는 같은 해체 경로를 타야 한다.
- **FR-071** 해체로 인한 위치 변경은 `VIEWPORT_BULK_ENTER` 한 덩어리로 전파해야 한다.
- **FR-072** 동승자 본인의 만료는 그 동승자만 제거해야 한다.
- **FR-073** 해체 후 `ride:*` 키가 남지 않아야 한다.
- **FR-074** `RiderCountService`의 0 반환 구현을 실제 인원수 조회로 교체해야 한다. 인터페이스는 바꾸지 않는다.
- **FR-075** 서버가 보내는 것은 정수 하나여야 한다. 동승자 명단을 보내지 않는다.
- **FR-076** 선장에게 탑승·하차·인원 변화를 개인 큐로 알려야 한다.
- **FR-077** 동승자에게 강제 하차 사유를 알려야 한다.

### 6.9 성능·관측성

- **FR-080** 선단 탑승 수, 해체 수, 평균 선단 크기, 거부된 탑승의 사유별 건수를 기록해야 한다.
- **FR-081** 해체 시 묶음 전파의 대상 수와 처리 시간을 기록해야 한다.
- **FR-082** 이메일·토큰을 로그나 metric tag에 남기지 않아야 한다.
- **FR-083** 현재 단일 서버의 인프로세스 이벤트 버스와 Simple Broker를 기준으로 한다.

## 7. Edge Cases

- 선장이 탑승 처리 도중 곡을 바꾸면 탑승자는 새 곡에 배치돼야 하며, 옛 곡과 새 곡에 동시에 있으면 안 된다.
- 선장이 정지 상태가 되면(재생 종료) 동승자는 그 자리에 남아 선장을 계속 따른다. 자동 하차하지 않는다.
- 20명째 탑승과 1명 하차가 동시에 오면 둘 다 성공해야 하며 인원수가 음수나 21이 되면 안 된다.
- 선장이 탑승 직후 즉시 이탈하면 방금 탑승한 사람도 해체 대상에 포함돼야 한다.
- 재연결 후 옛 탭의 하차 요청이 늦게 도착해도 새 탑승을 지우면 안 된다.
- 동승자가 브라우저를 닫으면 선장의 `riderCount`가 TTL 만료 시점에 줄어든다. 즉시 줄지 않는 것이 정상이다.
- 선장의 곡 변경과 동승자의 하차가 동시에 일어나면, 하차자는 변경 전과 후 중 한쪽 곡에만 있어야 한다.
- 해체 시 20명이 같은 곡에 나타나면 그 곡의 기존 거주자에게는 묶음 이벤트 1건만 가야 한다.
- 선장이 패널을 연 채 이탈하면 패널 스냅샷도 같이 지워져야 한다.
- 동승자의 곡 상세 조회가 실패해도 그 동승자만 빈 패널이고 선단 전체가 실패하면 안 된다.
- 선장과 동승자의 프론트 빌드 플래그가 다를 수 있다.
- 선장이 정지 상태에서 스냅샷을 읽으면 경과를 더하지 않아야 한다. 더하면 정지 중에도 재생 위치가 흐른다.

## 8. Key Entities

- **Fleet**: 선장 1명과 동승자 0~20명. 지도에서는 한 점으로 표현된다.
- **RideRegistration**: `ride:captain:{rider}`와 `ride:riders:{captain}`의 쌍. 항상 함께 변한다.
- **PlaybackSnapshot**: `{musicId, state, positionMs, updatedAt}`. 중간 탑승자 동기화의 유일한 근거.
- **PanelSnapshot**: `{open, musicId, tab}`. 재생 스냅샷과 같은 수명.
- **RideEvent**: 선장의 조작이 동승자에게 전달되는 소켓 메시지. 재생·곡·화면·패널 네 종류.
- **DismountContext**: 하차자 목록과 해체 전에 찍은 거주자 명단. 만남 계산의 입력.
- **RiderCount**: 뷰포트·근처사람 응답에 실리는 정수. 동승자 명단을 대체한다.

## 9. Success Criteria

- **SC-001** 탑승 요청의 응답이 로컬 기준 1초 이내 도착하고 재생이 3초 이내 맞춰진다.
- **SC-002** 동시 탑승 요청 100건에서 `ride:captain`이 두 개인 사용자가 0명이다.
- **SC-003** 동승자 20명 선단의 곡 변경에서 위치 변경 이벤트가 정확히 1건이다.
- **SC-004** 동승자 20명 선단의 곡 변경에서 `play_history` INSERT가 1회 배치, 재생수 UPDATE가 1회다.
- **SC-005** 선장의 재생 조작이 동승자 화면에 1초 이내 반영된다.
- **SC-006** 3초 구간 드래그에서 발행 이벤트가 10건 이하이고 마지막 위치가 항상 포함된다.
- **SC-007** 동승 중 차단된 8개 진입점에서 선단 상태가 변경되는 경우가 0건이다.
- **SC-008** 하차·해체 후 `ride:*` 키 잔존이 0건이다.
- **SC-009** 하차 시 같은 곡에 `play_history` 중복 행이 생기는 경우가 0건이다.
- **SC-010** 20명 전원 해체에서 선단 구성원 간 만남이 기록되는 경우가 0건이다.
- **SC-011** 해체 시 기존 거주자가 받는 위치 이벤트가 인원수와 무관하게 1건이다.
- **SC-012** 20명 선단의 주변곡 탭 열기에서 `ody.nearby.candidates` p99와 커넥션 풀 대기가 허용 범위 안이다.
- **SC-013** realtime 프로파일이 없을 때 기존 동작이 바뀌지 않는다.

## 10. Assumptions & Dependencies

- 로그인 완료 이후 기능이며 `Principal.getName()`이 email을 제공한다.
- 활성 판정은 기존 presence의 곡 배치 여부를 그대로 쓴다. 별도 활성 개념을 만들지 않는다.
- 계정 공개·비공개 정책은 현재 MVP의 전원 공개 가정을 유지한다. 비공개 정책이 확정되면 탑승 자격 검사에 조건 하나를 추가한다.
- YouTube IFrame Player API의 재생 제어를 프론트가 담당한다. 서버는 명령만 나른다.
- 브라우저 자동재생 정책상 음소거 자동재생 후 탭 한 번으로 소리를 켜는 흐름을 프론트가 처리한다.
- 주변곡 조회(`NearbyService`)는 캐시가 없고 무상태 조회 전용 계약이다. 이번 범위에서 바꾸지 않는다.
- 커넥션 풀은 현재 `maximum-pool-size: 5`다. 실측에서 대기가 보이면 풀 크기 조정을 별도 안건으로 올린다.
- 프론트엔드는 선단 마커 직접 렌더, 재생 명령 수신, 1.5초 어긋남 폴링, 동승 중 UI 잠금을 함께 구현해야 한다.
- `recordOnDismount`는 `MeetingService`가 소유하며 하차·해체 두 경로가 공유한다.

## 11. Out of Scope

- 광고 시작·종료 이벤트 전파
- 선장의 동승자 내보내기
- 체인 탑승(동승자를 따라가기)
- 재연결 시 탑승 상태 복원
- 동승자 명단 노출 — 인원수만 보낸다
- 주변곡 조회 캐시 도입
- 프론트엔드 코드 직접 수정
- Redis Pub/Sub 또는 외부 브로커를 이용한 다중 서버 fanout
- 따라가기 UI 디자인과 선단 마커 시각 표현
